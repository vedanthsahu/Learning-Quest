## 71. Pattern Catalog IV: Memory & Context Patterns

### 71.1 Working Memory Pattern

**Business Problem:** Within a single reasoning or agent turn, intermediate results (tool outputs, sub-calculations) need to be tracked without being lost before the final answer is produced. **Engineering Motivation:** The most local, short-lived form of memory — everything held within the current context window (§15.5) for the duration of a single turn or agent loop iteration (§25.11), distinct from anything persisting beyond it. **Architecture:** Simply the accumulating message list within a single request/agent-loop execution (§25.11's `messages` list growing with each tool result). **Tradeoffs:** No engineering cost beyond ordinary context-window budget (§24.7) — this is the baseline, not an optional addition. **Failure Modes:** Losing track of earlier working-memory content within a very long agent loop as it competes with other context consumers, directly §24.7's allocation tension. **Production Signals:** N/A as a distinct metric — working memory health is really just context-window management health (§32's latency diagnostics apply). **When NOT to Use It:** Never applicable to skip — every agent loop and every multi-step generation inherently has working memory; the only design question is how well it's managed, not whether to have it. **Real-World Examples:** §25.11's agent loop's `messages` accumulation. **Interview Discussion:** Rarely needs to be named explicitly in an interview — it's the assumed baseline every other memory pattern in this chapter builds on top of. **Cross-References:** §15.5, §24.7, §25.11.

### 71.2 Semantic Memory Pattern

**Business Problem:** A system needs to recall stable facts about a user or domain (preferences, attributes) across sessions, not just within one conversation. **Engineering Motivation:** Directly §25.5/§48's semantic-memory category — distilled, stable facts stored and retrieved independently of when they were learned. **Architecture:** A background extraction process (§48.9) distills facts from interactions into a retrievable store (§22), retrieved by topical similarity at the start of future relevant interactions. **Tradeoffs:** Precise, context-efficient recall of stable facts versus the engineering cost of an extraction pipeline and the risk of stale or contradicted facts persisting incorrectly (§48.6's staleness risk). **Failure Modes:** Extracted facts becoming outdated (a stated preference changes but the old fact remains stored and retrieved) with no mechanism to detect or supersede it. **Production Signals:** Fact-retrieval relevance (§21.8's recall/precision, applied to the semantic-memory store specifically) and, ideally, a contradiction-detection signal comparing newly stated facts against previously stored ones. **When NOT to Use It:** Products with no meaningful cross-session personalization need (a single-session tool has no use for this pattern at all). **Real-World Examples:** §48's Nova Stage 5; a support assistant remembering a customer's stated communication preferences across separate contacts. **Interview Discussion:** The correct answer to "how does the assistant remember my preferences between conversations" — should be explicitly distinguished from Conversation Memory (§71.4) in the answer. **Cross-References:** §25.5, §48.

### 71.3 Episodic Memory Pattern

**Business Problem:** A system needs to recall specific past events or interactions (not just stable facts) — "what did we discuss last time" rather than "what does this user prefer." **Engineering Motivation:** Directly §25.5/§48's episodic-memory category — distilled summaries of specific past interactions, filterable by both topical similarity and time/session. **Architecture:** Background extraction (§48.9) producing a per-session summary, stored with a timestamp, retrieved via combined similarity-plus-recency filtering rather than similarity alone. **Tradeoffs:** Enables genuinely useful "remember when we discussed X" functionality versus added retrieval complexity (two filtering dimensions instead of one) and the same staleness/extraction-quality risk as semantic memory (§71.2). **Failure Modes:** Retrieving an episodic memory that's topically similar but from a stale, superseded context (a past conversation about a since-resolved issue resurfacing as if still relevant). **Production Signals:** Same retrieval-quality metrics as semantic memory (§21.8), plus recency-relevance specifically — are retrieved episodic memories actually still contextually appropriate for the current interaction. **When NOT to Use It:** Products where past-interaction recall isn't a valued feature, or where session count per user is too low for this infrastructure to pay for itself. **Real-World Examples:** §48's Nova Stage 5's episodic component. **Interview Discussion:** Correctly distinguishing this from semantic memory in an interview answer (§67.9's related trap about conflating memory types) is a strong, specific signal of genuine understanding. **Cross-References:** §25.5, §48.

### 71.4 Conversation Memory Pattern

**Business Problem:** Within an ongoing, currently-active conversation, the system must recall what's already been said to avoid asking users to repeat themselves. **Engineering Motivation:** Directly §45's Nova Stage 2 mechanism — distinct from working memory (§71.1, single-turn) and long-term memory (§71.2-71.3, cross-session) specifically because it persists across turns within one conversation but not beyond it. **Architecture:** §45.4's hybrid verbatim-recent-plus-summarized-older approach. **Tradeoffs:** §45.6's stated tradeoff — bounded context growth versus potential loss of specific detail in the summarized portion. **Failure Modes:** §32.6's unmanaged-history-growth root cause if this pattern isn't actively bounded. **Production Signals:** Context length per conversation over time, prompt-cache hit rate (§46.6). **When NOT to Use It:** Never skip for any multi-turn product — the design question is how to bound it (§71.6's compression), not whether to have it. **Real-World Examples:** §45's Nova Stage 2. **Interview Discussion:** §67.9's trap directly — a candidate conflating this with long-term memory (§71.2-71.3) has missed a basic but important distinction. **Cross-References:** §25.5, §45.

### 71.5 Memory Compression Pattern

**Business Problem:** Long-term memory stores (§71.2-71.3) can accumulate an unbounded number of facts/episodes over a long user relationship, eventually making retrieval slower and less precise even with good filtering. **Engineering Motivation:** Periodically consolidating, deduplicating, or summarizing older memory entries — directly analogous to conversation summarization (§71.7) but applied to the long-term store rather than the active conversation. **Architecture:** A periodic background job merging redundant or superseded memory entries, potentially demoting very old, rarely-retrieved entries to a lower-priority or archived tier. **Tradeoffs:** Keeps the long-term memory store efficient and precise indefinitely versus the risk of over-aggressive consolidation losing genuinely distinct, still-relevant detail. **Failure Modes:** Consolidation merging two genuinely distinct facts/events into one blurred, less accurate memory entry. **Production Signals:** Long-term memory store size growth rate and retrieval-latency trend (§21.8) over the lifetime of long-tenured users — a rising trend without corresponding compression is the signal this pattern addresses. **When NOT to Use It:** Products with short user lifetimes or low interaction frequency, where the long-term store never grows large enough for this to matter. **Real-World Examples:** An extension of §48.9's extraction pipeline, run periodically rather than only per-conversation. **Interview Discussion:** A good answer to "what happens to Nova's memory system after a user has been active for two years" — a candidate who addresses long-term store growth explicitly is demonstrating scale-awareness (§61's Step 11). **Cross-References:** §48.6, §71.2-71.3.

### 71.6 Context Compression Pattern

**Business Problem:** Retrieved documents (§47) or other injected context can consume disproportionate context-window budget relative to their actual relevance to the current query. **Engineering Motivation:** Directly §24.5's mechanism — extractive or abstractive summarization of retrieved content, or simply retrieving smaller, more targeted chunks (§21.6), before inclusion in the prompt. **Architecture, Tradeoffs, Failure Modes:** See §24.5 in full. **Production Signals:** Retrieved-context token count relative to total context budget, tracked as a dimension of §31.4's token analytics. **When NOT to Use It:** When retrieved chunks are already small and precisely targeted (§21.6's well-tuned chunking may make this pattern unnecessary). **Real-World Examples:** §24.5's general mechanism, applied throughout Nova's RAG stage (§47). **Interview Discussion:** A strong, specific answer to "the retrieved context is too large" follow-up questions, distinct from simply "use a bigger context window" (§67.3's trap). **Cross-References:** §24.5, §47.6.

### 71.7 Sliding Context / Conversation Summarization Pattern

**Business Problem:** A specific, common implementation of conversation memory (§71.4) bounding: as a conversation grows, older turns must be either dropped or condensed to stay within budget. **Engineering Motivation:** §45.3's three named options (full history, truncation, summarization) — this pattern names the specific "sliding window" implementation (keep the most recent N turns, drop everything older) versus the "summarization" implementation (condense older turns into a running summary) as two distinct, nameable sub-patterns within conversation-memory management. **Architecture:** Sliding window: a simple fixed-size buffer of recent turns, oldest dropped as new ones arrive. Summarization: §45.9's hybrid approach, periodically compressing dropped-from-the-window turns into a persistent running summary rather than discarding them outright. **Tradeoffs:** Sliding window alone is simpler and cheaper (no summarization model calls) but loses older information completely (§45.3's Option B cost); summarization preserves the gist at the cost of an additional model call and irrecoverable detail loss within the summary itself. **Failure Modes:** A sliding window too narrow for the product's actual need, causing the exact "Nova forgot what I said three messages ago" complaint (§44.6) summarization was built to prevent. **Production Signals:** User complaints/evaluation failures (§29) specifically correlated with conversation length exceeding the window size. **When NOT to Use It:** Very short-lived, single-purpose conversations where a sliding window's simplicity is sufficient and summarization's added engineering cost isn't justified. **Real-World Examples:** §45.9's Nova Stage 2 implementation, which is precisely a hybrid of both sub-patterns. **Interview Discussion:** Being able to name and contrast these two specific sub-patterns (not just say "we manage context somehow") is a concrete, specific signal of real implementation experience. **Cross-References:** §45.3-45.4, §24.7.

### 71.8 Engineering Intuition

> **What's the fastest way to keep these five memory-related patterns straight?** Ask "does this need to survive past the current conversation?" — no (Working Memory, §71.1; Conversation Memory, §71.4) versus yes (Semantic, §71.2; Episodic, §71.3) — then, for the "yes" branch, ask "is it a stable fact or a specific past event?" to choose between Semantic and Episodic.

> **What would over-engineering look like across this chapter?** Building full Semantic and Episodic long-term memory infrastructure (§71.2-71.3) for a product where users have only ever had one session each — directly mirroring §43.6's premature-architecture warning, now specifically for memory infrastructure.
