## 78. Failure Catalog II: Generation & Reasoning Failures

### 78.1 Hallucination

**Symptoms:** Model states facts not present in provided context; fabricates citations; confidently answers outside the context's actual coverage. **Possible Causes:** Retrieval failure misdiagnosed as generation failure (§77.2); weak/poorly-positioned grounding instructions (§77.5); no uncertainty-expression mechanism; temperature too high for a grounding-dependent task (§19.3). **Metrics:** Faithfulness/groundedness (§29.6) alongside retrieval recall (§35.4's paired check). **Logs:** Full prompt logs (§31.3) showing exactly what context the model had. **Investigation Steps:** §35.5's process — check retrieval recall first, then grounding-instruction strength/placement. **Root Cause:** Most often retrieval failure (redirect to §77.2) or weak grounding (§77.5); less often a genuine out-of-coverage question with no uncertainty mechanism. **Mitigation:** §35.7 in full. **Prevention:** Continuous faithfulness evaluation (§29.6, §35.9) plus a golden dataset explicitly including known coverage gaps. **Lessons Learned:** Full treatment at §35 — the single most-cited AI failure mode, and the one most often misdiagnosed by skipping the retrieval-recall check first.

### 78.2 Prompt Drift

**Symptoms:** A prompt template that worked well in evaluation gradually or suddenly produces lower-quality output in production, without any explicit prompt change. **Possible Causes:** Underlying model provider silently updated the model version behind an API alias, changing its response behavior to the same prompt (§57.2's model-tier considerations); accumulated small, unreviewed prompt edits over time (a version-control/change-management gap, not a single root cause); context composition changing (more history, different retrieved-content characteristics) altering effective prompt behavior even though the literal template text didn't change. **Metrics:** Golden-dataset regression scores (§29.5) tracked over time, not just at deployment moments — a genuinely useful signal here is periodic (e.g., nightly) re-running of the golden dataset even absent any deployment, to catch provider-side drift. **Logs:** Prompt template version history (§31.3), model version/alias used per request. **Investigation Steps:** Re-run the exact golden dataset against the exact same prompt template from a known-good baseline period; if scores differ, the model version behind the API (not the prompt) is the suspect. **Root Cause:** Frequently an unannounced or under-communicated provider-side model update behind a "latest" alias, rather than any change on the product team's side at all. **Mitigation:** Pin to a specific, versioned model rather than a "latest" alias where the provider supports it; re-validate prompts against golden data after any provider-communicated update. **Prevention:** Periodic (not just deployment-triggered) regression testing (§39.5's scoped/incremental evaluation-cadence discussion) specifically to catch drift with no corresponding internal change. **Lessons Learned:** A reminder that "we didn't change anything" doesn't mean nothing changed — the model provider is part of the system too.

### 78.3 Tool Hallucination

**Symptoms:** The model requests a tool call with fabricated or invalid arguments, invokes a tool that doesn't exist, or reports a tool result that doesn't match what the tool actually returned. **Possible Causes:** Tool descriptions/schemas (§25.2) are ambiguous or incomplete, leading the model to guess at parameters; the model's context is missing information about which tools are actually available for the current situation; a genuine model capability limitation for complex tool-argument construction. **Metrics:** Tool-call validation failure rate (calls rejected by schema validation before execution, §30.6); rate of tool-call arguments not matching any plausible source in context. **Logs:** Full tool-call requests and their outcome (executed, rejected, or errored) via distributed tracing (§31.2). **Investigation Steps:** Inspect a sample of failed/rejected tool calls to determine whether arguments were plausible-but-wrong (a description-clarity problem) or nonsensical (a capability-limitation or context-gap problem). **Root Cause:** Most often ambiguous tool descriptions/schemas rather than a fundamental model limitation. **Mitigation:** Clarify and tighten tool schemas and descriptions (§30.6's structural constraints do double duty here — they also reject clearly-invalid hallucinated calls before execution); ensure tool availability is explicitly and unambiguously communicated in context. **Prevention:** Schema-level validation of every tool call before execution (§30.10) as a non-negotiable safety net regardless of how well-described tools are. **Lessons Learned:** Structurally similar to document hallucination (§78.1) but for actions rather than facts — the same "ground the model clearly, validate before trusting" discipline applies to both.

### 78.4 Model Regression

**Symptoms:** After a model version upgrade (intentional or provider-driven), quality metrics decline for some or all request types. **Possible Causes:** The new model version genuinely performs worse on your specific task distribution despite improving on general benchmarks (§20.7's "benchmark doesn't transfer" lesson, applied to generation models rather than embedding models); prompt engineering tuned specifically for the old model's quirks doesn't transfer cleanly to the new model's different response tendencies. **Metrics:** Golden-dataset regression scores (§29.5) compared old-model-version versus new, ideally via win-rate evaluation (§29.8) for a direct comparative signal. **Logs:** Model version per request (§31.3), enabling before/after comparison on identical inputs. **Investigation Steps:** Run win-rate evaluation (§29.8) with the old and new model on the same golden dataset before fully committing to the upgrade, not after. **Root Cause:** Most often a genuine, domain-specific capability difference not captured by the general benchmarks that motivated the upgrade in the first place. **Mitigation:** Roll back to the prior model version for affected request types, or re-tune prompts specifically for the new model's behavior; consider a canary rollout (§31.9) rather than a full cutover next time. **Prevention:** Never adopt a new model version without running the full evaluation suite (§29.5) first — treat model upgrades with the same regression-testing rigor as a prompt change, not as an assumed improvement. **Lessons Learned:** A specific, generation-side instance of the same discipline §77.3's embedding-drift prevention requires on the retrieval side — validate before trusting, for any component upgrade.

### 78.5 Long Context Latency

**Symptoms:** Time-to-first-token rises specifically as conversation or retrieved-context length grows; the relationship is nonlinear, not proportional. **Possible Causes:** Attention's quadratic scaling with context length (§17.5); prompt-cache hit-rate loss as context grows past what's effectively cacheable (§32.6); unmanaged context growth (§45.6) rather than deliberate, bounded context. **Metrics:** Time-to-first-token percentiles segmented by input-context-length bucket (§32.12). **Logs:** Input token count per request, prompt-cache hit/miss status. **Investigation Steps:** §32.5's process — segment latency by context length to confirm the nonlinear relationship before assuming a general, uniform slowdown. **Root Cause:** Usually unmanaged context growth (§77's retrieval-adjacent causes, or §45's conversation-history growth) rather than a model or infrastructure problem per se. **Mitigation:** Context compression (§24.5), better chunking (§21.6) to reduce retrieved-context size, prompt-cache-preserving structure (§24.6, §46.4). **Prevention:** Context-window budget monitoring (§31.4) as a standing dashboard, not a reactive investigation. **Lessons Learned:** Full treatment at §32 — this specific symptom is one of the clearest, most measurable illustrations of §15.6's quadratic-scaling warning actually manifesting in production.

### 78.6 Engineering Intuition

> **What's the fastest way to distinguish Hallucination (§78.1) from Tool Hallucination (§78.3)?** Ask whether the fabrication is about a *fact* (text claim not grounded in retrieved content) or an *action* (a tool call with invalid/fabricated arguments) — the same underlying "model confidently generates something not actually grounded" mechanism, applied to two different output types with two different validation mechanisms (grounding instructions versus schema validation).

> **What's the common thread across Prompt Drift (§78.2) and Model Regression (§78.4)?** Both are failures of *not re-validating after an external change* — a provider model update in one case, a deliberate model upgrade in the other — the fix in both cases is the same: never trust that "upstream" is stable; regression-test against it.
