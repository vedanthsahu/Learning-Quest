## 70. Pattern Catalog III: Workflow & Multi-Agent Patterns

### 70.1 Workflow Pattern

**Business Problem:** A business process has a known, fixed sequence of steps, some of which involve AI generation and some of which don't — the process itself shouldn't be left to a model's runtime discretion. **Engineering Motivation:** Directly §8.2's deterministic-workflow-versus-agent distinction — a workflow is application code that calls a model at specific, predetermined points, rather than handing control over sequencing to the model itself. **Architecture:** Ordinary application logic (conditionals, loops, sequencing) with one or more embedded model calls at fixed points — structurally the same shape as the Prompt Pipeline pattern (§68.3) but explicitly including non-AI business logic steps interleaved with AI steps. **Tradeoffs:** Maximum predictability, cost-control, and ease of testing (each step is independently testable, companion §15.2's unit-testing discipline applies directly) at the cost of inflexibility if the process's actual steps turn out to vary more than anticipated. **Failure Modes:** Forcing a genuinely variable process into a rigid workflow, producing frequent edge-case failures the fixed sequence can't handle. **Production Signals:** A high rate of edge-case/exception handling being invoked is a signal the process may need agentic flexibility (§70.5-70.6) rather than a rigid workflow. **When NOT to Use It:** Processes whose steps genuinely can't be known in advance — this is precisely the deterministic-workflow-vs-agent decision from §61's Step 6, and §67.2's trap warns against defaulting to the more flexible option unnecessarily. **Real-World Examples:** Nova's Stage 1-6 architecture (§44-49) before agentic behavior was introduced in Stage 7-8; most production RAG pipelines (§47) are workflows, not agents, at their core. **Interview Discussion:** The correct default answer whenever a task's steps are knowable in advance — a candidate proposing a workflow rather than an agent for a well-specified process demonstrates the judgment §67.2 rewards. **Cross-References:** §8.2, §68.3, §44-49.

### 70.2 Tool Calling / Function Calling Pattern

**Business Problem:** A model needs to trigger a real action or retrieve real-time information beyond what's in its context. **Engineering Motivation:** Directly §8.2/§25.2's core mechanism — already covered extensively in Parts I-IV; included here as this catalog's foundational building block for every pattern in the rest of this chapter. **Architecture:** §25.2's request-response contract — the model requests a tool invocation, the application executes it and returns the result. **Tradeoffs, Failure Modes, Production Signals:** See §25.2, §13.6, §30.6, §36 in full. **When NOT to Use It:** Tasks requiring no real action or external real-time data — a plain generation task doesn't need tool calling regardless of how sophisticated the surrounding architecture is. **Real-World Examples:** §49's Nova Stage 6. **Interview Discussion:** Foundational vocabulary every subsequent pattern in this chapter assumes fluency with. **Cross-References:** §8.2, §25.2, §49.

### 70.3 Planner-Executor Pattern

**Business Problem:** A complex task benefits from separating "deciding what to do" from "actually doing it," so each concern can be reasoned about, tested, and improved independently. **Engineering Motivation:** A specific architectural instantiation of the Planning pattern (§69.4) that splits planning and execution into genuinely distinct components — often a stronger, more expensive model for planning and a cheaper, more constrained model or deterministic executor for carrying out each planned step. **Architecture:** Planner generates a structured, step-by-step plan; a separate Executor component (which may itself be a simpler model or fixed application logic) carries out each step, reporting results back for the Planner to assess before proceeding. **Tradeoffs:** Cleaner separation of concerns (easier to test/improve each component independently, easier to swap a cheaper executor model for cost savings, §68.4's routing logic applied at the role level) versus the coordination overhead and latency of two distinct components communicating. **Failure Modes:** The Executor's constrained capability meaning it can't actually carry out a step the Planner assumed it could — a capability mismatch between the two roles, distinct from but related to §36.6's general capability-mismatch failure. **Production Signals:** Executor failure/rejection rate per planned step — a rising rate signals a Planner/Executor capability mismatch needing resolution (either a more capable Executor or a Planner that plans within the Executor's actual known constraints). **When NOT to Use It:** Simpler tasks where a single ReAct loop (§69.5) already handles both planning and execution adequately without the added architectural complexity of separate components. **Real-World Examples:** A coding agent (§59.5) where a planning step outlines file changes and a separate, more constrained execution step actually applies them with validation. **Interview Discussion:** A sophisticated answer for tasks combining high-stakes planning with cost-sensitive, high-volume execution — explicitly naming the cost-routing benefit (cheaper executor model) is a strong signal. **Cross-References:** §69.4, §68.4, §25.3.

### 70.4 Supervisor-Worker Pattern (Multi-Agent)

**Business Problem:** A task genuinely spans multiple distinct specializations or an unwieldy tool surface, and a single agent handling everything becomes hard to reason about, test, or improve. **Engineering Motivation:** Directly §25.6's supervisor/delegation pattern — a top-level Supervisor agent decomposes the overall goal and delegates sub-tasks to specialized Worker agents, then synthesizes their results. **Architecture:** Supervisor receives the goal, breaks it into sub-tasks, invokes Workers (each often with a narrower tool set/prompt/specialization), and combines their outputs into a final response. **Tradeoffs:** §25.6's stated tradeoff — narrower scope per Worker is easier to reason about and improve independently (mirroring the companion handbook's microservices-decomposition rationale, companion §8/§33.2) at the cost of coordination complexity and a real risk of inconsistent final synthesis (§25.9's diagnostic). **Failure Modes:** Workers producing contradictory results the Supervisor's synthesis step fails to reconcile (§25.9); coordination overhead making the system slower and more expensive than a single well-scoped agent would have been. **Production Signals:** Synthesis-inconsistency rate (final answers containing visibly conflicting information from different Workers) is the primary quality signal specific to this pattern. **When NOT to Use It:** Directly §25.9's warning — a task a single agent with a focused tool set already handles reliably should not be decomposed into multi-agent complexity without demonstrated need. **Real-World Examples:** A research assistant decomposing a broad question into sub-questions handled by specialized retrieval/analysis Workers before a Supervisor synthesizes a final report (§58.4's deep-research pattern). **Interview Discussion:** The correct escalation from a single agent specifically when task breadth, not task depth, is the limiting factor — a candidate should explicitly justify *why* decomposition is needed here, not propose it by default. **Cross-References:** §25.6, §25.9, §58.4.

### 70.5 Debate Pattern

**Business Problem:** A single model's answer (even with reflection, §69.1) may share systematic biases or blind spots that self-critique can't catch, especially for judgment-heavy or contestable questions. **Engineering Motivation:** Two or more model instances (or differently-prompted roles) argue different positions or independently produce answers, with a final synthesis or judge step comparing their arguments — directly extending the Generator-Critic pattern's (§69.2) independence argument to a genuinely adversarial, multi-perspective structure rather than a single critique pass. **Architecture:** Multiple independent generations (potentially arguing explicitly opposing positions), followed by a judge or synthesis step (§29.3's LLM-as-judge mechanism, applied inline) selecting or combining the strongest position. **Tradeoffs:** Better coverage of a contestable question's different angles versus multiplied cost (several independent generations plus a judging step) and added latency. **Failure Modes:** The judge step inheriting the same biases (§29.3's position/verbosity bias) that a debate structure was meant to work around, undermining the pattern's core benefit if not explicitly guarded against. **Production Signals:** Judge-decision consistency when debate order is randomized (§29.3's position-bias check, applied here) — inconsistency suggests the judging step itself needs the same bias-mitigation rigor as any evaluation judge. **When NOT to Use It:** Factual questions with a single clearly correct answer, where debate adds cost without addressing a genuine ambiguity or contestability the question doesn't actually have. **Real-World Examples:** Research or analysis tools presenting multiple perspectives on a genuinely contested question before synthesizing a balanced final answer. **Interview Discussion:** A sophisticated, less commonly proposed pattern — naming it specifically for genuinely contestable/judgment-heavy questions (not factual lookups) demonstrates nuanced understanding. **Cross-References:** §69.1-69.2, §29.3.

### 70.6 Voting Pattern

**Business Problem:** For tasks with meaningful output variance (§19.3's temperature/sampling randomness), a single generation may be an outlier; aggregating multiple independent attempts can improve reliability. **Engineering Motivation:** Generate multiple independent responses to the same input (via repeated sampling, §19.3-19.4) and select the most common/consistent answer (a form of self-consistency) rather than trusting a single generation. **Architecture:** N independent generations at a nonzero temperature → an aggregation step (majority vote for discrete answers, or a judge/synthesis step for open-ended text) → final selected or synthesized answer. **Tradeoffs:** Improved reliability and reduced variance versus directly multiplied cost (N times the generation cost for N samples) — a straightforward, quantifiable cost/reliability tradeoff. **Failure Modes:** Applying voting to tasks where the model's errors are systematic rather than random — voting only helps when errors are due to sampling variance, not a consistent, repeated misunderstanding that every sample would share equally. **Production Signals:** Agreement rate across the N samples — low agreement suggests genuine task difficulty or ambiguity (a signal worth surfacing, not just papering over via majority vote); consistently high agreement suggests voting's added cost isn't purchasing much additional reliability over a single sample. **When NOT to Use It:** Low-stakes tasks where a single sample's occasional variance is an acceptable cost of avoiding N-times the generation expense; tasks with systematic (not random) error patterns, where voting doesn't help at all. **Real-World Examples:** Self-consistency techniques for math/logic problems where the correct final answer is often the most common one across multiple independent reasoning attempts. **Interview Discussion:** Worth mentioning specifically for high-stakes, discrete-answer tasks (classification-like outputs) where cost tolerance allows multiple samples — less appropriate for open-ended chat responses where "most common" isn't well-defined. **Cross-References:** §19.3-19.4, §29.8 (win-rate evaluation's related aggregation logic).

### 70.7 Engineering Intuition

> **When does multi-agent complexity (Supervisor-Worker, Debate) actually pay for itself?** When the task genuinely spans multiple specializations, requires adversarial perspective-taking, or benefits from independent verification that a single model/role structurally cannot provide — never as a default upgrade from a working single-agent system.

> **What would over-engineering look like across this chapter?** Building a Supervisor-Worker architecture with a Debate-pattern judge and Voting-based aggregation for a task a single well-scoped agent (§69.5's ReAct) already handles reliably — each additional pattern in this chapter multiplies cost and complexity, and should be added only in response to a specific, evaluated gap the simpler predecessor doesn't close.
