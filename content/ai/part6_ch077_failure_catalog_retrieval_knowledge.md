## 77. Failure Catalog I: Retrieval & Knowledge Failures

### 77.1 How to Use This Catalog

Unlike Part III's diagnostic chapters (§32-42), which teach the *process* of investigation in narrative depth, this catalog (§77-80) is a fast-lookup reference: given a named symptom, jump directly to likely causes and mitigations. Every entry cross-references the Part III chapter with the full diagnostic treatment rather than repeating it. Each entry follows: Symptoms, Possible Causes, Metrics, Logs, Investigation Steps, Root Cause, Mitigation, Prevention, Lessons Learned.

### 77.2 Retrieval Failure

**Symptoms:** Correct information exists in the corpus but isn't surfaced in retrieved results; answers miss known-available information. **Possible Causes:** Chunking mismatch (§21.6), missing hybrid search for exact-term queries (§21.4), stale/mistuned ANN index (§21.5). **Metrics:** Recall@k, Precision@k (§21.8). **Logs:** Query, retrieved document IDs, similarity scores (§31.2's retrieval span). **Investigation Steps:** Run golden retrieval dataset (§29.2) directly against the pipeline; manually inspect failing queries' retrieved chunks. **Root Cause:** Most often chunking/embedding/index-tuning mismatch to actual query patterns. **Mitigation:** Adjust chunking, add hybrid search, re-tune ANN parameters (§34.7). **Prevention:** Automated retrieval regression testing (§34.9, §34.12) on every pipeline change. **Lessons Learned:** Full treatment at §34 — always rule this out before investigating generation quality (§67.5's trap).

### 77.3 Embedding Drift

**Symptoms:** Retrieval quality degrades suddenly and specifically after a model/provider update, or degrades gradually as corpus content ages relative to the current embedding model version. **Possible Causes:** Embedding model upgraded without a full corpus re-embed (§20.7). **Metrics:** Recall/precision segmented by document embedding-version (§38.6). **Logs:** Per-document embedding model version, last re-embed timestamp. **Investigation Steps:** Check whether degradation is concentrated on older, previously-indexed content (§38.2's diagnostic pattern). **Root Cause:** Incomplete or failed re-embed job. **Mitigation:** Complete the re-embed, verify zero stale-version items remain (§38.14). **Prevention:** Treat embedding-model-version as a mandatory deployment checklist item (§34.9); embedding-cache keying on model version (§72.3). **Lessons Learned:** Full treatment at §38 — the single most common silent RAG-quality incident in production.

### 77.4 Context Poisoning

**Symptoms:** A model's response is corrupted or steered by earlier, incorrect, or malicious content that entered its context (via retrieval, conversation history, or tool output) and was never corrected. **Possible Causes:** An indirect prompt injection (§13.2) embedded in a retrieved document; an earlier turn's incorrect assumption persisting uncorrected through subsequent conversation history (§45); a tool result containing misleading data that the model treats as ground truth for the rest of the interaction. **Metrics:** Faithfulness/groundedness scores (§29.6) dropping specifically for conversations/queries involving a specific document or tool source. **Logs:** Full prompt logs (§31.3) showing exactly what entered context and when. **Investigation Steps:** Trace back through the conversation/retrieval history to find the first point the poisoned content entered context; check whether it originated from an untrusted source (§13.1). **Root Cause:** Usually either an injection attack (§13.2) or an unvalidated tool/retrieval result treated as authoritative without a grounding check (§23.9). **Mitigation:** Injection-pattern scanning on untrusted content before it enters context (§30.2); explicit conflict/contradiction handling instructions (§35.7) so new information can override poisoned earlier context. **Prevention:** Treat all retrieved and tool-sourced content as untrusted by default (§13.1's trust-boundary discipline). **Lessons Learned:** A distinct failure mode from hallucination (§78.2) — the model may be accurately reflecting what's in its context, but that context itself is the problem, not the model's generation behavior.

### 77.5 Poor Grounding

**Symptoms:** The model has access to correct, relevant retrieved content but still produces answers not well-supported by it. **Possible Causes:** Weak or poorly-positioned grounding instructions (§23.9, §35.3); conflicting information across retrieved chunks with no resolution instruction; grounding instructions diluted by attention behavior over a long context (§17.5, §30.2). **Metrics:** Faithfulness score low despite high retrieval recall (§35.4's key diagnostic pairing). **Logs:** Full prompt showing grounding-instruction placement relative to retrieved content. **Investigation Steps:** §35.5's process — confirm retrieval recall is actually good first, then inspect prompt structure specifically. **Root Cause:** Usually grounding instructions present but too weak, too distant from the relevant content, or absent entirely. **Mitigation:** Strengthen and reposition grounding instructions (§35.7, §30.2's instructional reinforcement). **Prevention:** Faithfulness regression testing (§29.6) on every prompt-structure change. **Lessons Learned:** Full treatment at §35 — this is the "generation half" of the retrieval-vs-generation diagnostic split (§34.1).

### 77.6 Embedding Migration Failure

**Symptoms:** A planned embedding-model upgrade produces a partial, inconsistent index — some documents on the new model, some still on the old — with degraded and confusing retrieval behavior during and after the migration. **Possible Causes:** A re-embed job that failed silently partway through; no verification step confirming migration completeness (§38.9). **Metrics:** Fraction of corpus on current vs. stale embedding version (§38.14's audit). **Logs:** Per-document re-embed job status/timestamps. **Investigation Steps:** Run §38.14's verification snippet directly. **Root Cause:** Missing migration-completeness verification as a deployment gate. **Mitigation:** Complete the migration; treat verification as blocking, not optional. **Prevention:** Zero-downtime-migration discipline (companion §34) applied explicitly to vector re-embedding, with a mandatory completeness check before declaring the migration done. **Lessons Learned:** This is Embedding Drift's (§77.3) acute, in-progress form — the same root mechanism, caught mid-migration rather than after the fact.

### 77.7 Vector DB Degradation

**Symptoms:** Retrieval latency or recall degrades as corpus size or query volume grows, independent of any embedding or chunking change. **Possible Causes:** ANN index parameters (§21.5) tuned for a smaller corpus, never re-tuned as scale grew; insufficient bin-packing/resource allocation for the vector database's own infrastructure (§28.3's fleet-scale concern, applied to a data-store rather than a model-serving fleet). **Metrics:** Retrieval latency and recall trend against corpus-size trend over time. **Logs:** Vector database resource utilization, index configuration history. **Investigation Steps:** Correlate degradation onset against corpus growth curve, not recent deployments (§34.10's "gradual, not sudden" diagnostic pattern). **Root Cause:** Index configuration not scaled alongside data volume. **Mitigation:** Re-tune ANN parameters or migrate to a vector database tier suited to the new scale (§22.9's selection framework revisited). **Prevention:** Periodic index-configuration review tied to defined corpus-size thresholds (§34.9). **Lessons Learned:** A capacity-planning failure, not a code-correctness failure — the same category of mistake as under-provisioning any data store, applied to vectors specifically.

### 77.8 Reranking Regression

**Symptoms:** Adding or changing a reranker doesn't improve, or actively worsens, overall answer quality and/or latency. **Possible Causes:** First-stage retrieval recall is already poor, so no reranker can recover a document never retrieved (§38.5); the reranker itself isn't validated on the specific domain (§38.5's general-benchmark-doesn't-transfer risk); candidate-set size (top_k) mistuned against the recall/latency tradeoff (§38.9). **Metrics:** Recall/precision with vs. without reranking, measured separately (§38.6). **Logs:** First-stage retrieval time and reranking time as separate spans (§31.2). **Investigation Steps:** §38.7 — measure first-stage recall alone before blaming the reranker. **Root Cause:** Most often, poor first-stage recall being misdiagnosed as a reranker problem. **Mitigation:** Fix first-stage retrieval if that's the actual cause; otherwise replace or re-tune the reranker for the specific domain (§38.9). **Prevention:** Regression-test the reranking stage's marginal contribution on every change (§38.11). **Lessons Learned:** Full treatment at §38 — one of the clearest examples in this handbook of a fix being applied to the wrong stage of a multi-stage pipeline.

### 77.9 Cross-Encoder Bottleneck

**Symptoms:** Reranking (a cross-encoder stage, §21.7) is the dominant latency contributor in the retrieval pipeline, disproportionate to its accuracy benefit. **Possible Causes:** Candidate-set size (top_k) too large for the cross-encoder stage, multiplying its inherently expensive per-pair computation (§21.7) across too many candidates; applying cross-encoder-level precision (§73.4's pattern) uniformly to low-stakes queries that don't need it. **Metrics:** Reranking-stage latency as a fraction of total retrieval-pipeline latency (§31.2). **Logs:** Candidate-set size per request, reranking latency per request. **Investigation Steps:** Measure the recall/latency tradeoff curve (§38.9) at several candidate-set sizes to find the actual efficient point. **Root Cause:** Candidate-set size set arbitrarily rather than tuned against this tradeoff curve. **Mitigation:** Reduce candidate-set size to the point where marginal accuracy gain no longer justifies marginal latency cost; consider query-complexity-based routing (§74.5) so only queries that need maximum precision pay the full cross-encoder cost. **Prevention:** Treat candidate-set size as a tuned, evaluated parameter (§29), not a default left unexamined. **Lessons Learned:** A specific, common instance of the general "applying a precision-maximizing pattern uniformly rather than selectively" over-engineering mistake (§73.4's own explicit warning).

### 77.10 Engineering Intuition

> **What's the fastest triage question across every failure in this chapter?** "Is the correct information actually being retrieved?" (§34.5's check) — this single question, answered directly against a golden dataset, correctly routes almost every retrieval-adjacent complaint to either this chapter (if no) or §78's generation-failure catalog (if yes).
