## 75. Reference Architectures I: Knowledge & Search Systems

### 75.1 How to Use These Reference Architectures

Each architecture below is a complete, production-shaped reference — not a new set of mechanisms, but a specific, named assembly of patterns from §68-74 and mechanisms from Parts I-IV, addressed across ten dimensions: Components, Data Flow, Latency Budget, Security, Guardrails, Evaluation, Observability, Cost Drivers, Failure Modes, Scaling Strategy. Use these as starting templates for an interview answer's Step 6 (§61), adjusted for the specific hidden constraints (§61's Step 2) a given question surfaces.

### 75.2 Enterprise RAG

**Components:** Document ingestion pipeline (chunking, §21.6), embedding pipeline (§20, with model-version tracking, §72.3), vector database (§22.9-selected for scale/tenancy needs), retrieval pipeline (§73.1-73.3's two/three-stage pattern with tenant filtering), generation with grounding/citation (§23.9), evaluation pipeline (§74.1). **Data Flow:** Documents → chunk → embed → index (with tenant metadata) → [query time] embed query → filter by tenant → retrieve → rerank → assemble grounded prompt → generate → cite. **Latency Budget:** Retrieval + reranking (§21.7) typically the largest controllable component beyond model prefill/decode (§15.7); target sub-second retrieval, leaving the majority of an acceptable end-to-end budget for generation. **Security:** Tenant-scoped access control enforced structurally at the retrieval layer (§73.2, §54.4), not just at the application layer. **Guardrails:** Grounding-strictness tuning (§23.9, §63.1's NotebookLM-style calibration) and injection-pattern scanning on ingested documents (§30.2, since uploaded content is untrusted). **Evaluation:** Faithfulness/groundedness and recall/precision (§29.6, §21.8) as the two primary, separately-tracked metric families. **Observability:** Retrieval recall trend, embedding-version-per-document tracking (§38.14), token analytics per tenant (§31.4). **Cost Drivers:** Embedding computation at ingestion scale, retrieval infrastructure (§22), and generation tokens — walk §15.13's chain per-tenant. **Failure Modes:** §34 (retrieval quality), §35 (hallucination), §38 (embedding/reranking regression) — this architecture's three most common production incidents. **Scaling Strategy:** Vector database tier upgrade path (§22.9), ANN re-tuning as corpus grows (§21.5), and — critically — the multi-tenant filtering discipline (§54.4) must scale correctly, not just performance.

### 75.3 Enterprise Knowledge Assistant

**Components:** Everything in §75.2 plus conversation memory (§45) and long-term memory (§48) layered on top, since this is a conversational product built on Enterprise RAG's retrieval foundation, not just a one-shot Q&A system. **Data Flow:** As §75.2, plus conversation history management (§45.4's hybrid approach) feeding into prompt assembly alongside retrieved context, competing for the same context-window budget (§24.7). **Latency Budget:** As §75.2, plus prompt-caching discipline (§24.6, §46.4) for the stable system-prompt/summary prefix across a multi-turn conversation. **Security:** As §75.2, plus per-user (not just per-tenant) memory isolation (§48.4's metadata scoping, extended to the individual level). **Guardrails:** As §75.2, plus policy-engine gating (§53.4) if the assistant has any tool/action capability beyond pure Q&A. **Evaluation:** As §75.2, plus trajectory-level evaluation (§39.7) for multi-turn conversation quality, not just per-turn faithfulness. **Observability:** As §75.2, plus conversation-length distribution and context-budget allocation tracking (§45.6's three-way tension made visible). **Cost Drivers:** As §75.2, plus conversation-history token accumulation (§45.6) as a distinct, monitored cost dimension. **Failure Modes:** As §75.2, plus §36 (if tools are present) and conversation-drift/memory-corruption failures (§79's catalog). **Scaling Strategy:** As §75.2, plus long-term memory store compression (§71.5) as tenured-user count and interaction history grow.

### 75.4 AI Search

**Components:** Real-time or near-real-time retrieval infrastructure (§58.3's inference — likely a search index plus reranking, distinct from a static pre-built vector index), grounded generation with citation (§23.9), query-complexity routing (§23.5, Adaptive RAG) between fast single-pass and slower multi-source-synthesis modes. **Data Flow:** Query → complexity classification → [simple: single-pass retrieval+generation] or [complex: multi-source retrieval, possibly agentic, §23.6] → grounded, cited generation. **Latency Budget:** Tightest of this chapter's four architectures for the "simple" path (search-engine-like responsiveness expected, §63.2); explicitly relaxed and communicated to users for the "complex"/deep-research path (§58.4's multi-minute precedent). **Security:** Lower access-control stakes than enterprise architectures if the corpus is the open web (§58.2), but real stakes if searching a private/internal corpus instead — this distinction should be established explicitly (§61's Step 2) before finalizing this dimension. **Guardrails:** Citation accuracy and source-attribution verification (§23.9) as the primary guardrail concern, given users' trust in cited claims. **Evaluation:** Citation accuracy and comprehensiveness (§58.5's documented evaluation practice) alongside standard faithfulness metrics. **Observability:** Query-complexity-routing accuracy (§23.5, §33.6's misrouting risk) and per-mode latency percentiles (§31.6) tracked separately for simple vs. complex paths. **Cost Drivers:** Real-time retrieval infrastructure cost and — for the complex/agentic path — multi-step retrieval token consumption (§15.9's variance, §58.4's accepted tradeoff). **Failure Modes:** §34 (retrieval quality, now against a live, changing corpus rather than static), §36 (if the complex path is agentic). **Scaling Strategy:** Real-time index freshness/update infrastructure scaling independent of query-serving scaling — a genuinely distinct scaling axis from the other three architectures in this chapter, since the corpus itself is continuously changing.

### 75.5 Document Intelligence (Structured Extraction + Analysis Over Documents)

**Components:** Document parsing/OCR (if source documents are scanned/image-based, a preprocessing step outside this handbook's core text-based mechanisms, analogous to §64.4's transcription step for audio), structured-field extraction (a narrower generation task than open-ended chat, similar in spirit to §65.2's structured-extraction consideration), optional RAG for cross-document Q&A (§47) layered on top of extracted structured data. **Data Flow:** Document → parse/OCR → structured extraction (fields, tables, entities) → validation → [optionally] index for cross-document retrieval → query/analysis. **Latency Budget:** Extraction is typically a batch/async operation (tolerant of higher latency, similar to §48.9's background-memory-extraction pattern) rather than a real-time, user-facing latency-critical path — a candidate should explicitly note this distinction from the other three architectures in this chapter, all of which have a real-time query-serving latency requirement. **Security:** Document content is frequently sensitive (contracts, financial records, medical documents, §65.3-65.4) — access control and PII handling (§30.4) apply with elevated stakes. **Guardrails:** Extraction-accuracy validation (a structured, checkable output, similar to §60.5's objectively-verifiable code-generation success signal) rather than open-ended faithfulness scoring alone. **Evaluation:** Field-level extraction accuracy against a golden dataset of correctly-labeled documents (§29.2), a more precise, checkable metric than general RAG faithfulness. **Observability:** Extraction-failure rate per document type/format, and — for scanned documents — OCR-quality metrics as a distinct upstream signal. **Cost Drivers:** Per-document processing cost (extraction model calls) at ingestion volume, generally a more predictable, batch-amortizable cost than a real-time query-serving system's variable per-request cost. **Failure Modes:** Extraction errors on unusual document formats/layouts not represented in the golden dataset (§29.2's coverage principle, directly applicable); OCR-quality-driven downstream extraction failures for scanned documents. **Scaling Strategy:** Batch-processing infrastructure scaling (parallelizable across documents, since each document's extraction is largely independent) rather than the real-time concurrency scaling the other three architectures require.

### 75.6 Engineering Intuition

> **What's the fastest way to distinguish these four architectures in an interview?** Ask: is the corpus static/enterprise-internal (Enterprise RAG/Knowledge Assistant, §75.2-75.3), live/open (AI Search, §75.4), or is the product's job to *produce* structured data from documents rather than answer questions about them (Document Intelligence, §75.5)?

> **What would over-engineering look like across this chapter?** Adding real-time conversational memory (§75.3) to a batch Document Intelligence pipeline (§75.5) that has no actual multi-turn interaction requirement — each architecture's components should be justified by that specific product's actual interaction pattern, not copied wholesale from a superficially similar-sounding architecture.
