## 83. Case Studies II: Fine-Tuning, Embeddings, Agents, Cost, Guardrails, Evaluation

### 83.1 Case: Fine-Tuning Made Quality Worse

**Symptoms:** A team fine-tuned a model on a curated set of 2,000 example support responses to improve tone consistency; post-deployment evaluation showed overall quality scores dropped, including on tasks unrelated to tone. **Possible Hypotheses:** (a) the fine-tuning dataset was poor quality, (b) catastrophic forgetting (§26.8) degraded general capability, (c) the evaluation golden dataset changed concurrently, (d) the fine-tuned model was deployed with the wrong prompt template (one designed for the base model). **Investigation:** Segmented evaluation scores by task type — tone-consistency-specific metrics *did* improve as intended, but general factual-accuracy and instruction-following metrics on unrelated tasks dropped substantially. **Measurements:** The training dataset, while high quality for tone, was narrow — it covered only a handful of support-ticket categories, and training had used a relatively high learning rate over several epochs without mixing in any general-capability examples. **Root Cause:** Catastrophic forgetting (§26.8) — the narrow, repeated fine-tuning signal overwrote general capability the base model previously had, exactly the risk §26.6's dataset-engineering discussion warned about. **Fix:** Retrained using LoRA (§26.3) instead of full fine-tuning (preserving more of the frozen base model's original behavior by construction), a lower learning rate, and a training set augmented with general-capability examples interspersed with the tone-specific ones. **Tradeoffs:** Slightly less dramatic tone-consistency improvement than the original (more aggressive) fine-tuning run achieved, accepted in exchange for preserving general capability. **Lessons Learned:** Before fine-tuning, ask whether the actual goal (tone consistency) could have been achieved via prompting or few-shot examples (§67.1's trap) — and if fine-tuning is genuinely justified, evaluate on general capability, not just the target behavior, since narrow-dataset training risks are invisible if only the target metric is checked (§26.6, §29.7).

### 83.2 Case: Switching Embedding Models Reduced Accuracy

**Symptoms:** A team upgraded their embedding model to a newer version with a better public benchmark score; retrieval recall (§21.8) on their own evaluation set dropped by 30% immediately after the switch. **Possible Hypotheses:** (a) the new model is genuinely worse for this specific domain despite its benchmark score (§20.7's "benchmark doesn't transfer" warning), (b) the corpus wasn't fully re-embedded, (c) the similarity metric configuration didn't match the new model's requirements, (d) a chunking change was bundled into the same deployment. **Investigation:** §38.7's process — checked re-embed completion status first (§38.14). **Measurements:** The re-embed job had, in fact, completed for 100% of documents — but retrieval quality was still poor specifically for shorter documents (under roughly 50 words), while longer documents retrieved well. **Root Cause:** The new embedding model used a different, unit-length-normalized output convention than the old one, but the vector database's similarity metric was still configured for dot product tuned to the old model's non-normalized output scale (§20.6) — a metric-configuration mismatch, not a re-embedding gap or a genuine model-quality problem. **Fix:** Reconfigured the vector database to use cosine similarity (or equivalently, confirmed normalization) matching the new model's actual output convention. **Tradeoffs:** None — this was a configuration bug, not a genuine tradeoff between two valid options. **Lessons Learned:** A full re-embed alone doesn't guarantee correctness after an embedding-model switch — the similarity-metric configuration must be explicitly re-validated against the new model's documented requirements (§20.6, §38.4's second listed cause), not just assumed to carry over from the previous model.

### 83.3 Case: Agent Loops Forever

**Symptoms:** A newly-launched research-assistant agent feature showed roughly 8% of requests hitting the `max_steps` limit without producing a satisfactory answer, far above the expected rare-edge-case rate. **Possible Hypotheses:** (a) the tasks given to this feature are genuinely too complex for reliable multi-step handling, (b) a specific tool's result format is ambiguous, (c) no goal-completion reflection step exists, (d) `max_steps` itself is set too low for legitimately complex tasks. **Investigation:** §36.5's process — pulled full step-by-step traces (§31.2) for the failing 8% and inspected exactly what the model saw after each tool call. **Measurements:** In the large majority of failing traces, a specific "search_documents" tool returned an empty list both when no results existed and when the search itself had silently failed due to a backend timeout — the model, upon receiving an empty list, would retry the same search repeatedly rather than recognizing a distinct failure state. **Root Cause:** Tool-result ambiguity (§36.6, §79.1) — the tool's response schema couldn't distinguish "genuinely no results" from "the search itself failed," giving the model no signal to change its approach. **Fix:** Changed the tool's response schema to explicitly distinguish these two cases (`{"status": "no_results"}` versus `{"status": "search_error", "detail": "..."}`), and added an explicit instruction for the model to try a different approach after two consecutive no-result searches rather than repeating the same query. **Tradeoffs:** None significant — this was a tool-design fix, not a capability tradeoff. **Lessons Learned:** Before concluding a looping agent reflects a genuine capability limitation, always inspect the actual tool-result content the model received (§36.5) — tool-result ambiguity is both the more common root cause and the cheaper fix, exactly as §36.10 predicted.

### 83.4 Case: Tool Calls Timeout

**Symptoms:** An enterprise-assistant feature using several internal-system tools began showing a rising rate of tool-call timeouts specifically during business hours, when overall system traffic was highest. **Possible Hypotheses:** (a) the internal systems being called are simply overloaded during peak hours, (b) the agent's tool-calling is generating more concurrent requests than expected, (c) a specific tool's timeout threshold is too aggressive for its actual response-time distribution, (d) a connection-pool exhaustion issue in the tool-execution layer itself. **Investigation:** Correlated timeout events against the target internal system's own load metrics and against the tool-execution layer's connection-pool utilization. **Measurements:** The internal CRM system's own p95 response time during business hours was genuinely higher (around 4 seconds) than the tool-execution layer's fixed 3-second timeout, which had been set based on off-peak testing only. **Root Cause:** A timeout threshold set from unrepresentative (off-peak) testing conditions, not accounting for the target system's real peak-hour latency distribution — a capacity-planning gap similar in kind to §82.4's GPU case, but for an external dependency rather than internal infrastructure. **Fix:** Raised the timeout to accommodate the target system's actual p99 peak-hour latency, and added a fallback path (§68.6's Fallback Pattern) informing the user gracefully when a tool call genuinely fails rather than only retrying blindly. **Tradeoffs:** Slightly higher worst-case latency for requests using this specific tool during peak hours, accepted since it's still far better than a failed request. **Lessons Learned:** Tool timeout thresholds should be set from the target system's real, peak-load latency distribution (§31.6's percentile discipline, applied to an external dependency), not from convenient off-peak testing conditions — and every tool should have an explicit, user-visible fallback behavior for genuine failure, not just a longer timeout.

### 83.5 Case: Costs Tripled

**Symptoms:** Monthly AI infrastructure spend tripled within a single billing period, with no corresponding 3x growth in user count or request volume. **Possible Hypotheses:** (a) a specific feature or customer segment is responsible for disproportionate spend, (b) a routing misconfiguration is sending traffic to an expensive model, (c) a retry loop is duplicating cost, (d) genuine, healthy growth that simply wasn't anticipated in the estimate. **Investigation:** §33.5's dimensional cost breakdown (§31.4) by feature, model, and user — immediately localized to one specific feature (a newly-launched "deep analysis" mode) accounting for over 70% of the cost increase despite representing only about 5% of total requests. **Measurements:** The "deep analysis" feature used a reasoning model (§19.7) and averaged roughly 12,000 reasoning tokens per request — a number never explicitly estimated at launch, since the launch cost projection had only counted visible output tokens. **Root Cause:** §33.6/§80.4's exact pattern — reasoning tokens invisible in the original estimate, now the dominant real cost driver for this specific feature. **Fix:** Added an explicit reasoning-token budget/cap for this feature and introduced usage-based pricing or rate limiting (§31.8) specifically for this higher-cost mode, rather than offering it at the same terms as the rest of the product. **Tradeoffs:** Some users hitting the new reasoning-token cap experience truncated deep-analysis results for unusually complex queries — evaluated (§29) as an acceptable tradeoff given the alternative (unsustainable, unbounded cost). **Lessons Learned:** Any feature using a reasoning model must have its actual reasoning-token consumption measured and budgeted explicitly from before launch (§81.4), not estimated by output length alone — this specific undercount is common enough to be this handbook's most frequently recurring cost-incident root cause (§33.10, §80.4, §81.2).

### 83.6 Case: Guardrails Blocked Legitimate Users

**Symptoms:** After tightening injection-detection guardrail sensitivity in response to a recent security incident, customer complaints about legitimate requests being rejected rose sharply, disproportionately affecting users writing in a specific non-English language. **Possible Hypotheses:** (a) the sensitivity increase was simply too aggressive across the board, (b) the guardrail's rule-based patterns (§30.5) were written and tested primarily against English text and misfire on other languages' phrasing, (c) a genuine new attack pattern is being (correctly) blocked, (d) the classifier-layer guardrail has a language-specific bias. **Investigation:** Sampled the flagged-and-rejected requests (§40.5) and reviewed them for false positives specifically, segmented by detected language. **Measurements:** The false-positive rate for the affected language was nearly 15%, versus under 1% for English — the tightened rule-based patterns (originally written and tuned only against English injection examples) were matching innocuous phrasing patterns common in the affected language but rare in English. **Root Cause:** A guardrail rule set validated and tuned against a non-representative (English-only) test distribution, then tightened further without re-validating against the full, actual multilingual user base (§40.8's sensitivity/false-positive tradeoff, realized without the necessary evaluation). **Fix:** Added language-specific tuning and test coverage to the rule-based layer, and shifted more of the injection-detection weight onto the classifier-based layer (§30.5), which generalized better across languages than the rigid rule patterns. **Tradeoffs:** Slightly higher latency/cost from relying more on the classifier layer versus cheap rule-based patterns, accepted in exchange for equitable false-positive rates across the user base. **Lessons Learned:** Any guardrail sensitivity change must be evaluated against the *actual* full user population's language/content diversity (§29.7's safety-dimension evaluation, applied here), not just the population that motivated the original tightening — an incident response that fixes one problem (an attack) while introducing another (inequitable false positives) is not a complete fix.

### 83.7 Case: Evaluation Scores Regressed

**Symptoms:** A routine weekly regression run (§29.5) showed golden-dataset quality scores dropping by 10%, but no prompt, model, or pipeline change had been deployed that week. **Possible Hypotheses:** (a) the model provider silently updated the model behind an API alias (§78.2's Prompt Drift), (b) the golden dataset itself was modified accidentally, (c) evaluation infrastructure itself has a bug, (d) a dependency (embedding model, retrieval index) changed independent of the main application deployment. **Investigation:** Diffed the golden dataset file against version control (unchanged) and diffed the evaluation harness code (unchanged); checked the model version/alias actually used, comparing against the provider's own changelog. **Measurements:** The provider had indeed pushed an update to the "latest" alias the team's pipeline was pinned to, a week before the regression was noticed, confirmed by the provider's own release notes. **Root Cause:** §78.2's Prompt Drift — an unannounced-to-the-team (though provider-documented) model update behind a floating alias, changing response behavior to the identical prompt set. **Fix:** Pinned the production pipeline to a specific, immutable model version rather than a "latest" alias, and added an explicit, periodic (not just deployment-triggered) evaluation run specifically to catch this class of drift going forward (§39.5's evaluation-cadence lesson, §78.2's prevention). **Tradeoffs:** Loses automatic access to the provider's ongoing model improvements without an explicit, evaluated opt-in — accepted as the correct tradeoff, since an unreviewed, unannounced behavior change reaching production is a worse outcome than deliberately delaying adoption of genuine improvements until validated. **Lessons Learned:** "We didn't change anything" is not the same as "nothing changed" — any pipeline pinned to a floating model alias is implicitly accepting silent, unreviewed changes from the provider, and periodic regression testing independent of any internal deployment is the only way to catch this class of drift.

### 83.8 Cross-Cutting Lessons Across This Chapter's Case Studies

A pattern worth naming explicitly: in five of this chapter's seven cases (§83.1-83.3, §83.5, §83.7), the root cause was something *external or invisible to the original estimate or configuration* — catastrophic forgetting from training data composition, a similarity-metric mismatch, ambiguous tool results, undercounted reasoning tokens, a provider-side silent model update — rather than a straightforward application bug. The unifying lesson: production AI incidents disproportionately trace back to gaps in *validation and measurement* (evaluate before and after every change, measure the full cost surface, verify configuration explicitly) rather than to obviously "wrong" code — reinforcing this handbook's repeated emphasis on evaluation (§29, §39) and dimensional observability (§31) as the actual first line of defense, not an afterthought.
