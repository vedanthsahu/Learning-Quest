## 80. Failure Catalog IV: Security & Infrastructure Failures

### 80.1 Guardrail Failure

**Symptoms:** A harmful, policy-violating, or manipulated output reaches a user despite guardrails being in place; conversely, guardrails block a large number of legitimate requests (false positives). **Possible Causes:** A novel attack pattern not covered by existing rule-based/classifier layers (§30.5); over-reliance on a single defense layer without the complementary layers §30.2 recommends; guardrail sensitivity tuned without evaluating the false-positive-rate cost (§40.8). **Metrics:** Guardrail flag rate segmented by type and identity (§40.4); false-positive rate via sampled human review; time-to-detection for confirmed bypasses. **Logs:** Full input/output around the flagged or missed event (§31.3). **Investigation Steps:** §40.5 — determine whether a flag-rate spike is concentrated (targeted attack) or diffuse (false-positive regression); for a discovered bypass, reconstruct which specific defense layer failed. **Root Cause:** Most often a single-layer defense with no complementary classifier/model-based layer, or a sensitivity threshold never validated against real false-positive cost. **Mitigation:** §40.7 in full — add the missing layer, or retune sensitivity based on evaluated tradeoff. **Prevention:** Maintained, regularly-updated adversarial test set (§40.9) incorporating every newly-discovered pattern. **Lessons Learned:** Full treatment at §40 — guardrails are probabilistic and must themselves be evaluated (§13.5's core warning), never trusted as an infallible safety net.

### 80.2 Prompt Injection

**Symptoms:** A response reflects instructions the system prompt never intended to honor, often traceable to user input or retrieved/uploaded content. **Possible Causes:** Direct injection via user message; indirect injection via a retrieved document or tool result (§13.2) — the harder-to-defend-against variant since the attacker never interacts with the system directly. **Metrics:** Injection-pattern-flag rate on ingested/retrieved content specifically (§30.2). **Logs:** Full content that entered context, with source attribution (user input vs. retrieved document vs. tool result). **Investigation Steps:** Identify whether the injected instruction originated from user input (direct) or ingested content (indirect) — this determines whether the fix belongs in input validation or content-ingestion scanning. **Root Cause:** Untrusted content lacking a structural instruction/data separation, since natural language provides no equivalent to parameterized queries (§13.2's core structural limitation). **Mitigation:** §30.2's layered defenses — delimiter structuring, instructional reinforcement, classifier-based scanning, and critically, privilege separation (limiting what a successful injection can actually cause, regardless of detection). **Prevention:** Treat every retrieved/uploaded/tool-sourced content item as untrusted by default (§13.1); least-privilege tool scoping as the defense that helps even when injection detection fails. **Lessons Learned:** Full treatment at §13.2, §30.2 — the most-cited AI-specific vulnerability class, and one no single defense layer fully closes.

### 80.3 Context Explosion

**Symptoms:** A single request's context grows dramatically and unexpectedly large — far beyond typical requests — causing a latency and cost spike for that specific request or class of requests. **Possible Causes:** A retrieval bug returning far more chunks than intended (§21.6 misconfiguration); a conversation-summarization failure causing full, unsummarized history to be sent instead of the intended compressed version (§45.4's mechanism failing silently); a tool result returning an unexpectedly large payload injected directly into context without size limiting. **Metrics:** Input-token-count distribution with explicit outlier/tail tracking (not just average or even standard percentiles — a true "explosion" may be rare enough to hide within a p99, requiring an explicit maximum-value alert). **Logs:** Full breakdown of context composition (retrieved-chunk count/size, history length, tool-result size) per request (§31.4's dimensional analytics). **Investigation Steps:** For flagged outlier requests, decompose exactly which context component (retrieval, history, tool output) accounts for the disproportionate size. **Root Cause:** Most often a retrieval or tool-result size-limiting bug rather than a genuine, legitimate need for that much context. **Mitigation:** Add explicit size caps at every context-contributing stage (maximum chunks returned, maximum tool-result size included, hard ceiling on history before forced summarization) rather than relying on downstream context-window truncation alone as the only safety net. **Prevention:** Treat context size as a validated, capped quantity at every injection point (§24.7), not an unbounded pass-through. **Lessons Learned:** A more acute, single-request version of §78.5's Long Context Latency — this failure is a bug (something returned far more than intended) rather than a gradual, expected-scale problem.

### 80.4 Token Explosion

**Symptoms:** Total token consumption (and therefore cost, §33) for a specific feature or request type spikes dramatically without a corresponding, deliberate change. **Possible Causes:** A reasoning-model feature (§19.7) consuming far more hidden reasoning tokens than estimated; a retry loop resending full, expensive requests repeatedly on transient errors (§33.6); an agentic loop (§79.1) generating many tool-calling round-trips, each consuming tokens, before finally terminating or hitting `max_steps`. **Metrics:** Token consumption per logical user action (not per raw API call — a single user action triggering five retries or agent steps should be measured as one action's true token cost, §31.4). **Logs:** Full token counts per API call, correlated back to the originating user action via a shared request/trace ID (§31.2). **Investigation Steps:** §33.5 — walk the token-economics chain with actual production counts for the affected feature; check specifically for retry-driven duplication and reasoning-token consumption, both of which are easy to undercount in a naive estimate. **Root Cause:** Most often reasoning tokens or retry duplication being invisible in the original cost estimate. **Mitigation:** §33.7 — add explicit reasoning-token budgets, fix retry logic to avoid full re-incurring of cost, cap agentic step count tightly. **Prevention:** §33.9's dimensional cost monitoring as a standing dashboard, explicitly including reasoning-token and retry-driven consumption as separate, visible line items. **Lessons Learned:** Full treatment at §33 — nearly always a visibility gap (the cost was always structurally possible, just never measured) rather than a genuinely new problem.

### 80.5 Runaway Cost

**Symptoms:** Total spend grows disproportionately to user/request growth, potentially triggering a budget alert or an unexpectedly large bill. **Possible Causes:** Any combination of §80.3 (context explosion), §80.4 (token explosion), a model-routing misconfiguration (§79.3) sending disproportionate traffic to an expensive model, or a genuine abuse/malfunctioning-client scenario (§13.6) generating excessive volume from a single source. **Metrics:** §33.4's dimensional cost breakdown (per user, feature, model, stage) as the primary diagnostic tool — this is the escalated, system-wide version of §80.3-80.4's single-request-scoped failures. **Logs:** Full cost-attribution logs (§31.4) at sufficient granularity to isolate the responsible dimension. **Investigation Steps:** §33.11's decision tree — localize to a specific dimension before investigating further; check for concentration (one user/feature/model) versus a genuine, proportional-to-growth increase. **Root Cause:** Nearly always traceable to one of §80.3-80.4's more specific mechanisms once the dimensional breakdown localizes it. **Mitigation:** Token-budget-based rate limiting (§31.8, §31.13) to bound worst-case exposure from any single source, alongside the dimension-specific fix identified. **Prevention:** Standing dimensional cost dashboards (§33.9) rather than a monthly-bill-only view — the single most preventable characteristic of this entire failure category. **Lessons Learned:** Full treatment at §33 — "runaway cost" is a symptom name, not a root cause; it always decomposes into one of this catalog's more specific failures once properly diagnosed.

### 80.6 GPU Saturation

**Symptoms:** Self-hosted inference (§27) shows sustained high GPU utilization with rising latency and request queuing; or, paradoxically, low compute utilization with queuing still present (§37.2's counterintuitive but common pattern). **Possible Causes:** Genuine compute-bound load at real capacity limits; KV-cache memory pressure limiting concurrency well before compute saturates (§18.4, §37.3 — the more common, less intuitive cause); missing or misconfigured continuous batching (§27.3) leaving real parallel capacity unused. **Metrics:** Compute utilization AND KV-cache/memory occupancy tracked simultaneously, never one alone (§37.4, §31.5). **Logs:** Request queue depth and wait time, batching configuration and actual achieved batch size. **Investigation Steps:** §37.5's process — pair compute utilization with memory occupancy before concluding this is a "need more GPUs" problem. **Root Cause:** Most often KV-cache-driven concurrency limits or a continuous-batching misconfiguration, not genuine raw compute exhaustion. **Mitigation:** §37.7 — right-size KV cache/context length, verify and correct batching configuration, before provisioning additional GPU capacity. **Prevention:** §37.9's paired-metric dashboard as the default view, and load-testing with realistic concurrency and context-length distributions before trusting any single-request throughput measurement. **Lessons Learned:** Full treatment at §37 — the clearest example in this entire catalog of a symptom ("GPU saturation") whose obvious-seeming fix (more GPUs) is very often not the correct one.

### 80.7 Engineering Intuition

> **What's the common thread across Context Explosion (§80.3), Token Explosion (§80.4), and Runaway Cost (§80.5)?** They form an escalating scope of the same underlying failure family — Context Explosion is a single-request symptom, Token Explosion is a per-feature/action symptom, and Runaway Cost is the system-wide aggregate symptom — the same dimensional-breakdown diagnostic technique (§33.4) applies at every scope, just applied to a progressively larger unit of analysis.

> **Why does GPU Saturation (§80.6) get grouped with security/infrastructure failures rather than the failure catalog's other chapters?** Because, unlike the model/retrieval-level failures in §77-79, its root causes live in the serving-infrastructure layer (§18, §27-28) — a genuinely different diagnostic vocabulary (memory occupancy, batching configuration) than anything in the model-behavior-focused chapters.
