## 76. Reference Architectures II: Assistant & Productivity Systems

### 76.1 AI Coding Assistant

**Components:** Dual-mode serving (§62.4, §59.4) — low-latency inline completion (small/fast model, minimal context) and agentic chat/edit (codebase-aware retrieval, §59.3, tool calling for file/terminal operations, §49). **Data Flow:** Two distinct paths sharing a codebase index: keystroke → inline completion (fast path); instruction → codebase retrieval → agentic plan/edit/test loop (§69.3-69.5) → diff review (§25.8). **Latency Budget:** Inline path near-instant (tens to low hundreds of ms); agentic path latency-tolerant (seconds to minutes). **Security:** Least-privilege tool scoping for file/terminal access (§13.6, §30.6); diff-review checkpoint before destructive changes apply. **Guardrails:** Test-execution as an objective correctness check (§60.5-style verifiable signal) before presenting agentic changes as complete. **Evaluation:** Completion-acceptance rate (inline path) and task-completion/test-pass rate (agentic path) as two structurally distinct metrics families. **Observability:** Per-mode latency percentiles (§31.6), tool-call repetition monitoring (§36.12) for the agentic path specifically. **Cost Drivers:** Inline completion's high request volume at low per-request cost versus agentic mode's low volume at high per-request cost (multi-step tool use, §15.9). **Failure Modes:** §36 (agent loops in the agentic path), destructive-action risk without review. **Scaling Strategy:** Per-mode model routing (§68.4, §74.5's latency-aware routing) scales independently for each path's distinct load profile.

### 76.2 AI CRM Assistant

**Components:** RAG over customer records/interaction history (§47, per-customer scoped, §54.4-style), tools for CRM actions (updating records, logging activity, §49), summarization of customer interaction history (§48's episodic-memory pattern, applied to customer relationship data rather than personal conversation memory). **Data Flow:** Query about a customer/account → retrieve customer-scoped records and interaction history → generate summary/answer/recommended action → optionally invoke CRM-update tools with policy-engine gating (§53.4). **Latency Budget:** Moderate — typically an internal sales/support-tool interaction, not a consumer-facing real-time constraint. **Security:** Strict per-account/per-territory access scoping (a sales rep should only retrieve accounts they're authorized for) — directly §54.4's tenant-scoping pattern applied at a finer, per-record grain. **Guardrails:** Structural constraints on CRM-write actions (§30.10's schema-capping pattern — e.g., can't reassign an account or change a contract value without approval). **Evaluation:** Faithfulness of generated account summaries against actual CRM data (§29.6), plus action-correctness for any tool-invoked CRM updates. **Observability:** Tool-call audit log (who changed what, §31.3) is a core requirement, not optional, given CRM data's business sensitivity. **Cost Drivers:** RAG retrieval over potentially large historical-interaction corpora per account, generation for summaries. **Failure Modes:** Retrieval crossing account/territory boundaries incorrectly (§13.4), stale record summaries if not regenerated after CRM data changes. **Scaling Strategy:** Per-account or per-territory retrieval scoping must scale correctly as account volume grows — the same tenant-scoping-completeness discipline (§54.6) as any multi-tenant system.

### 76.6 AI Analytics Assistant (Natural-Language Querying Over Structured/Business Data)

**Components:** Natural-language-to-query translation (converting a user's question into a structured query against a database or analytics warehouse, a structured-output generation task rather than open-ended RAG), a query-execution/validation layer, and result summarization/visualization generation. **Data Flow:** Natural-language question → generate structured query (SQL or equivalent) → validate query safety/scope (critically, before execution) → execute against the data warehouse → summarize/present results. **Latency Budget:** Dominated by the underlying query-execution time against potentially large datasets, not by generation latency — a candidate should note this explicitly, since it's a materially different latency profile than any RAG-based architecture in this catalog. **Security:** Query-scope validation before execution is the single most critical component — a generated query must be checked against the requesting user's actual data-access permissions before running, directly analogous to §30.6's schema-level tool constraint but applied to generated query text rather than a fixed-schema tool call, making it a harder validation problem. **Guardrails:** Preventing generated queries from accessing unauthorized tables/columns or performing destructive operations (no generated query should ever include a write/delete operation without explicit, separate authorization). **Evaluation:** Query-correctness rate against a golden dataset of question-to-expected-query pairs (§29.2, a more objectively checkable metric than open-ended faithfulness). **Observability:** Generated-query rejection rate (queries caught and blocked by the validation layer) as a security-relevant metric, tracked alongside query-execution latency/cost. **Cost Drivers:** Underlying data-warehouse query-execution cost (which can dwarf generation cost for large datasets) alongside generation cost for the translation step. **Failure Modes:** A generated query that's syntactically valid but semantically wrong (misinterpreting the question), producing a confident but incorrect analytical answer — a distinct hallucination-adjacent failure mode specific to structured-query generation. **Scaling Strategy:** Query-execution infrastructure (the underlying data warehouse) scales independently of the NL-to-query generation layer — these are two separate scaling axes requiring separate capacity planning.

### 76.7 AI Workflow Automation

**Components:** A workflow-pattern (§70.1) or agent-based (§25) orchestration layer connecting multiple business systems via tools (§49), triggered by events or schedules rather than direct conversational interaction. **Data Flow:** Trigger event (a new record, a scheduled time, an incoming request) → orchestration logic (fixed workflow or adaptive agent, §61's Step 6 derivation applies directly to choosing between them) → sequence of tool invocations across connected systems → completion/notification. **Latency Budget:** Typically asynchronous and latency-tolerant (background automation, not a real-time user-facing interaction), a materially different profile from every conversational architecture in this catalog. **Security:** Broadest tool-permission surface of any architecture in this catalog, since it often connects to many external systems — least-privilege scoping (§30.6) and policy-engine gating (§53.4) are maximally important here, not optional. **Guardrails:** Idempotency and retry-safety (ensuring a retried or duplicated trigger doesn't cause a duplicated real-world action) is a distinctive concern for this architecture not emphasized elsewhere in this catalog. **Evaluation:** Task-completion rate and error/exception rate per workflow type, tracked per connected system given the multi-system integration surface. **Observability:** Full audit trail per workflow execution (§31.3) is essential given the automation's real, unattended side effects. **Cost Drivers:** Tool/API call volume across connected systems, plus orchestration-model cost if agent-based rather than a fixed workflow. **Failure Modes:** §36 (if agent-based) plus integration-specific failures (a connected system's API changing or becoming unavailable, requiring the same fallback thinking as §68.6 applied to business-system integrations, not just model providers). **Scaling Strategy:** Per-connected-system rate limiting and circuit-breaking (companion §42.5) as trigger volume grows, independent of any model-serving scaling concern.

### 76.8 Enterprise Copilot (Broad, Cross-Application Assistant)

**Components:** The broadest assembly in this catalog — RAG across multiple internal knowledge sources (§75.2-75.3), tools spanning multiple business systems (§76.2, §76.7's integration surface), conversation and long-term memory (§45, §48), and model routing across task types (§68.4). Functionally, this is closest to Nova's full, mature Stage 11-12 architecture (§54-55) generalized as a named product category. **Data Flow, Latency Budget, Security, Guardrails, Evaluation, Observability, Cost Drivers, Failure Modes, Scaling Strategy:** Directly Nova's enterprise/global stage treatment (§54-55) in full — this architecture is, structurally, "build Nova" rather than a distinct new template. **Interview Discussion:** When an interview question asks for a broad "enterprise copilot" without narrowing scope, the strongest response is explicitly recognizing this equivalence and walking through Nova's stage-by-stage derivation (§43-56) rather than trying to design the mature system's full complexity from scratch in one pass. **Cross-References:** §43-56 in full, §75.2-75.3.

### 76.9 Engineering Intuition

> **Why do §76.3-76.5 point back to earlier worked examples instead of repeating them?** Because those worked examples (§63.4, §65.1, §64.4) already provided the full ten-dimension treatment in service of teaching interview derivation — repeating identical content under a different heading would violate this handbook's "cross-reference rather than repeat" discipline (per this Part's explicit writing-style mandate) without adding any new information.

> **What would over-engineering look like across this chapter?** Proposing the full Enterprise Copilot architecture (§76.8) when a question actually describes a narrower, single-purpose assistant (e.g., §76.2's CRM-specific scope) — recognizing when a question's scope is genuinely broad versus narrow is itself part of §61's Step 2 hidden-constraint analysis.
