## 82. Case Studies I: Latency, Throughput, Retrieval, Hallucination

### 82.1 How to Use These Case Studies

Each case study is a realistic, narrative incident — not a hypothetical — walked through the way an engineer actually experiences it: an ambiguous initial symptom, several plausible hypotheses, a narrowing investigation, and a fix with a real tradeoff. Use these to practice the Part III diagnostic chapters' frameworks in a form closer to how they actually arrive in production, rather than as a labeled catalog entry (§77-80).

### 82.2 Case: Latency Suddenly Doubled

**Symptoms:** Average end-to-end response latency for a RAG-based support assistant rose from ~1.8s to ~3.6s over the course of a single week, with no corresponding deployment on the team's own side. **Possible Hypotheses:** (a) a model provider-side slowdown, (b) growth in average conversation length, (c) a retrieval-side regression, (d) increased traffic exceeding serving capacity. **Investigation:** Distributed tracing (§31.2) segmented the 3.6s into stages: retrieval (0.4s, unchanged from baseline) and prefill+decode (3.2s, up from 1.4s baseline) — immediately ruling out retrieval (b was closer but needed confirming) and pointing at the generation call itself. **Measurements:** Input token count per request had grown from an average of ~800 to ~3,400 tokens over the same week — traced to a recent feature launch that added full previous-ticket history into every support conversation's context, without any summarization (§45.4) or truncation. **Root Cause:** Unmanaged context growth (§32.6, §78.5) from a new feature that bypassed the existing conversation-memory management entirely by injecting raw historical ticket data directly. **Fix:** Applied the same hybrid verbatim+summarization pattern (§45.4, §71.7) to the newly-added ticket history rather than including it raw. **Tradeoffs:** Some historical ticket detail is now compressed rather than verbatim — accepted, since faithfulness evaluation (§29.6) showed no measurable quality loss for the actual support-resolution task. **Lessons Learned:** Any new feature injecting content into an existing prompt must go through the same context-budget discipline (§24.7) as the original system — "it's just adding some history" is exactly how unmanaged growth enters production.

### 82.3 Case: Users Complain Responses Became Slower

**Symptoms:** A wave of user complaints about "the assistant feels slower" arrived, but the team's own p50 latency dashboard showed no change. **Possible Hypotheses:** (a) users are wrong/exaggerating, (b) a specific user segment or request type is affected while the aggregate is unaffected, (c) time-to-first-token specifically regressed while total latency didn't, (d) a client-side rendering issue unrelated to backend latency at all. **Investigation:** Segmented latency by percentile (§31.6) rather than trusting the aggregate — p50 was indeed flat, but p95 had risen substantially, and time-to-first-token specifically (not total generation time) was the affected metric (§15.7's distinction). **Measurements:** The p95 time-to-first-token regression correlated with requests that had a cache miss on the prompt's stable prefix (§24.6) — cache-hit rate had dropped from 85% to 40% over the same period. **Root Cause:** A recent prompt template change had inserted a per-request timestamp near the beginning of the prompt (for logging purposes) ahead of the stable system-prompt content, breaking prefix stability for caching (§32.6's exact root-cause pattern, §46.6's warned-about risk). **Fix:** Moved the timestamp to the very end of the prompt, after all stable content, restoring cache-hit rate to its prior level. **Tradeoffs:** None meaningful — this was a pure engineering oversight with no genuine tradeoff, a useful reminder that not every fix requires balancing competing concerns. **Lessons Learned:** "Users complain but the dashboard looks fine" is a strong signal to check percentiles and specific latency-chain stages (§15.7), not just the aggregate average — and any prompt-structure change should explicitly verify cache-hit rate before and after (§32.9's prevention discipline).

### 82.4 Case: GPU Utilization Remains Low

**Symptoms:** A self-hosted inference deployment showed GPU compute utilization consistently around 45%, well below the team's target of 75-80%, despite real user-facing latency and occasional request queuing. **Possible Hypotheses:** (a) genuinely low traffic not yet justifying full utilization, (b) a batching configuration issue, (c) memory/KV-cache constraints limiting concurrency independent of compute headroom, (d) poor fleet-wide bin-packing across multiple GPU instances. **Investigation:** §37.5's paired-metric check — KV-cache occupancy was consistently above 90% even while compute utilization sat at 45%, immediately identifying this as memory-constrained, not compute-idle (§37.3, §80.6). **Measurements:** Average context length per request had grown significantly since the serving capacity was originally sized, due to a RAG feature added after initial deployment, meaning each concurrent request now consumed substantially more KV-cache memory than the original capacity planning assumed. **Root Cause:** KV-cache capacity sized for pre-RAG average context length, never re-sized after RAG was added — a capacity-planning gap, not a code bug. **Fix:** Right-sized KV-cache allocation for the new average context length and reduced maximum context length accepted per request via context compression (§24.5) on the RAG side specifically. **Tradeoffs:** Slightly reduced maximum retrievable-context size per request, evaluated (§29) as having no measurable faithfulness impact for this specific corpus and query pattern. **Lessons Learned:** "Low compute utilization" is not the same signal as "spare capacity" — the paired compute/memory check (§37.4, §80.6) should be the very first diagnostic step, not an afterthought, whenever GPU-based capacity questions arise.

### 82.5 Case: Context Became Enormous

**Symptoms:** A specific user's conversation, after several hours of continuous use, began producing errors — the request was rejected for exceeding the model's maximum context window entirely. **Possible Hypotheses:** (a) a genuinely unusual, extremely long user session, (b) a bug in conversation-history truncation/summarization, (c) a retrieval bug returning far more content than intended, (d) a memory-extraction process appending rather than replacing prior state. **Investigation:** Prompt logs (§31.3) for the failing request showed the conversation-history component alone was over 40,000 tokens — far beyond what even several hours of normal conversation should produce given the summarization mechanism (§45.4) supposedly in place. **Measurements:** Tracing showed the summarization job had been silently failing for this specific conversation for the past two hours (an unhandled exception in the summarization call, caught by a broad try/except that logged nothing and simply skipped summarization, falling back to raw, unbounded history accumulation). **Root Cause:** A silent failure mode in the summarization pipeline — the fallback behavior on error was "include everything raw" rather than "fail the request visibly" or "truncate as a safe fallback," turning an isolated transient failure into an unbounded resource leak (§80.3's Context Explosion). **Fix:** Changed the summarization failure's fallback behavior to hard-truncate to the verbatim window (§71.7) rather than silently including everything, and added explicit alerting on summarization failures. **Tradeoffs:** A summarization failure now visibly loses more context than a successful summarization would have preserved — accepted, since a visible, bounded degradation is far preferable to an invisible, unbounded one. **Lessons Learned:** Error-handling fallback behavior for any context-management component must itself be bounded and safe by default — "fail open" (include everything) is the wrong default for anything touching context-window budget; "fail closed" (truncate safely) is correct here.

### 82.6 Case: RAG Quality Dropped After Adding Documents

**Symptoms:** After onboarding a new enterprise customer and ingesting their document set (roughly doubling the total corpus size), overall retrieval-quality evaluation scores (§21.8) dropped by about 15%, across all customers, not just the new one. **Possible Hypotheses:** (a) the new customer's documents are simply lower quality/more ambiguous, (b) the ANN index needs re-tuning at the new scale (§21.5, §77.7), (c) a tenant-scoping filter failure is letting the new customer's documents compete in other customers' retrieval results, (d) chunking quality issues specific to the new document set's formatting. **Investigation:** Segmented retrieval evaluation (§21.8) specifically by whether the retrieved documents' tenant matched the querying tenant — discovered a nonzero rate of cross-tenant document retrieval, immediately identifying this as a filtering failure (§13.4, §73.2), not a scale or quality issue. **Measurements:** The new customer's ingestion pipeline had used a slightly different code path that omitted the `tenant_id` metadata field on a subset of ingested chunks (§54.9's structural wrapper existed but wasn't applied uniformly across both ingestion paths). **Root Cause:** Inconsistent ingestion code paths — the newer customer's onboarding used a batch-import script that bypassed the standard, tenant-scoped ingestion function. **Fix:** Consolidated both ingestion paths to use the single, mandatory tenant-scoping wrapper (§54.9), and ran a corpus-wide audit (§54.8's decision tree) confirming no other documents were missing tenant metadata. **Tradeoffs:** None — this was a straightforward, severity-appropriate bug fix (§42.5's high-severity classification for cross-tenant leakage) with no competing consideration. **Lessons Learned:** "Adding documents reduced quality" should always trigger a tenant/access-control check first in any multi-tenant system (§67.5's trap, more severe variant) — not just a generic re-evaluation of retrieval tuning, since a filtering bug produces exactly this symptom and is both more severe and, once found, faster to fix than a genuine scale/tuning issue.

### 82.7 Case: Hallucinations Increased After Deployment

**Symptoms:** Faithfulness scores (§29.6) for a document-chat product dropped noticeably after a routine prompt-template refactor intended purely to improve formatting consistency, with no intended change to grounding behavior. **Possible Hypotheses:** (a) the refactor accidentally weakened grounding instructions, (b) retrieval itself regressed coincidentally, (c) the underlying model was updated by the provider around the same time, (d) evaluation golden-dataset itself changed. **Investigation:** §35.5's process — checked retrieval recall first (unchanged, ruling out a).(c) Then diffed the old and new prompt templates directly. **Measurements:** The refactor had moved the grounding instruction ("only answer using the provided context") from immediately before the retrieved content to the very start of the overall system prompt, several thousand tokens earlier in context once a typical amount of retrieved content was included. **Root Cause:** Instruction-dilution over a long context (§17.5, §30.2, §77.5) — the grounding instruction was technically still present, just positioned too far from the content it was meant to govern. **Fix:** Restored the grounding instruction to its position immediately adjacent to the retrieved content (§30.2's instructional-reinforcement principle), in addition to keeping a brief version at the start. **Tradeoffs:** A few additional tokens spent repeating the instruction near the content — a negligible cost relative to the faithfulness improvement, confirmed via evaluation (§29.6) before and after. **Lessons Learned:** A refactor with no *intended* behavior change can still have one — any prompt-structure change, however cosmetic in intent, should be regression-tested against faithfulness/quality metrics (§29.5) before being treated as purely stylistic.

### 82.8 Case: Streaming Appears Slower

**Symptoms:** After migrating to a new API gateway/proxy layer for infrastructure consolidation reasons, users began reporting that streamed responses "feel choppy" and slower to start appearing, even though backend generation-latency metrics showed no change. **Possible Hypotheses:** (a) the model genuinely got slower (ruled out immediately by backend metrics), (b) the new gateway buffers responses before forwarding, (c) client-side rendering changed, (d) network conditions changed for a specific user segment. **Investigation:** §37.5's end-to-end token-delivery-timestamp trace — timestamps at the model-serving layer showed tokens generated at the expected steady rate, but timestamps at the client showed tokens arriving in larger, delayed bursts rather than the expected steady trickle. **Measurements:** The new gateway's default configuration buffered response bodies up to a minimum size threshold before forwarding, a sensible default for ordinary API responses but directly defeating the purpose of token-by-token streaming (§19.6, §27.7) for this use case. **Root Cause:** A infrastructure-layer default (response buffering) misapplied to a streaming endpoint during a migration that didn't account for this specific endpoint's different requirements (§37.6's exact documented pattern). **Fix:** Disabled response buffering explicitly for the streaming endpoint's specific route in the gateway configuration. **Tradeoffs:** None meaningful — buffering provides no benefit for a route specifically designed around incremental delivery. **Lessons Learned:** Infrastructure migrations affecting any streaming endpoint must explicitly verify end-to-end streaming behavior, not just aggregate latency metrics — a "successful migration" by every standard metric can still silently break a UX property (perceived responsiveness) that those metrics don't directly measure.

### 82.9 Cross-Cutting Lessons Across This Chapter's Case Studies

Notice how many of these cases were resolved not by a deep model-level investigation but by a specific, well-chosen measurement (§31's instrumentation) that immediately localized the problem — cache-hit rate, KV-cache occupancy, tenant-tagged retrieval evaluation, end-to-end token-delivery timestamps. This is the practical payoff of Part III's instrumentation discipline (§31.11): the right metric, checked first, turns a vague symptom into an obvious root cause in minutes rather than hours.
