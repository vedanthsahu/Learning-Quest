## 68. Pattern Catalog I: Prompt & Routing Patterns

### 68.1 How to Use This Catalog

Each pattern below is a named, recognizable architectural unit — the AI-engineering equivalent of the companion Software Systems Handbook's design-pattern catalog. Every pattern is documented with: Business Problem, Engineering Motivation, Architecture, Tradeoffs, Failure Modes, Production Signals (what you'd see in monitoring, §31, if this pattern is present and behaving badly), When NOT to Use It, Real-World Examples, Interview Discussion, and Cross-References. These patterns are combinations and namings of mechanisms already taught in Parts I-IV — this catalog exists to give them memorable names for design discussions and interviews, not to introduce new mechanisms.

### 68.2 Single Prompt Pattern

**Business Problem:** A task that can be fully specified and answered in one model call, no additional context or steps needed. **Engineering Motivation:** Simplicity — the lowest-latency, lowest-cost, most predictable architecture available (§44.4's Nova Stage 1). **Architecture:** One system prompt, one user input, one model call, one response (§7.2, §24.2). **Tradeoffs:** Maximum simplicity and predictability; no ability to incorporate external/current information or multi-step reasoning. **Failure Modes:** Attempting to force a task requiring external knowledge or multi-step logic into a single call, producing hallucination (§35) or an incomplete answer. **Production Signals:** Consistently low latency and cost per request; failures correlate with queries needing information not in the model's training data. **When NOT to Use It:** Any task requiring current, private, or externally-sourced information (needs RAG, §6) or multi-step action (needs tools/agents, §25). **Real-World Examples:** Nova Stage 1 (§44); a simple classification or rewriting utility. **Interview Discussion:** The correct starting point (§61.2's derivation principle) — proposing anything more complex without first establishing this is insufficient is a common over-engineering tell (§67). **Cross-References:** §7.2, §24.2, §44.

### 68.3 Prompt Pipeline / Prompt Chaining

**Business Problem:** A task naturally decomposes into sequential sub-tasks, each best handled by its own focused prompt rather than one large, complex prompt. **Engineering Motivation:** Breaking a complex generation task into smaller, more reliable steps — each step's output becomes the next step's input — improves per-step reliability at the cost of added latency (multiple sequential model calls) and cost. **Architecture:** A fixed, deterministic sequence of prompts/model calls (e.g., extract → summarize → format), distinct from an agent (§8.2) because the sequence itself is fixed at design time, not decided dynamically by the model. **Tradeoffs:** Improved reliability per step versus added latency (sequential calls, §15.7) and cost (multiple calls instead of one). **Failure Modes:** Errors compounding across steps (a bad extraction in step one corrupts every subsequent step); no mechanism to recover if an intermediate step fails, unlike an agent's reflection (§25.4). **Production Signals:** Latency scaling linearly with pipeline length; quality issues traceable to a specific pipeline stage via tracing (§31.2). **When NOT to Use It:** When the task's steps aren't actually fixed in advance (needs an agent, §25.3) or when a single well-structured prompt already handles the task adequately. **Real-World Examples:** §48.9's memory-extraction (a two-part fixed extraction prompt); document-processing pipelines (extract fields → validate → format). **Interview Discussion:** The correct answer for "how would you improve reliability on this multi-part generation task" when the parts are known in advance — contrast directly with the agent pattern (§68.9) for when they aren't. **Cross-References:** §24.2, §25.1 (workflow-vs-agent distinction), §48.9.

### 68.4 Routing Pattern / Model Router

**Business Problem:** Different requests have meaningfully different complexity, cost sensitivity, or capability requirements, and using one model for all of them is either wasteful (overpaying for simple requests) or insufficient (underpowering complex ones). **Engineering Motivation:** Directly §1.5's capability/cost/latency triangle and §27.5's model routing — match each request to the cheapest/fastest model capable of handling it correctly. **Architecture:** A classification step (often a small, cheap model or a rules-based heuristic) examines each incoming request and routes it to an appropriately-sized downstream model. **Tradeoffs:** Cost/latency savings at scale versus routing-accuracy risk (a misclassified complex request routed to a weak model produces a quality regression, §33.6's routing-config-error root cause) and the added latency/cost of the routing step itself. **Failure Modes:** Routing misclassification silently degrading quality for a subset of traffic; routing configuration drifting out of sync with actual model capability changes over time. **Production Signals:** Quality metrics (§29) segmented by route/model showing an unexpected gap; cost dashboards (§31.4) showing disproportionate spend on one tier. **When NOT to Use It:** Low traffic volume where the routing infrastructure's engineering cost exceeds any realistic savings; a narrow product where all requests are genuinely similar in complexity. **Real-World Examples:** §59.4's coding-assistant inline-vs-chat routing; §54.4's Nova per-tenant model-tier routing. **Interview Discussion:** A strong signal in nearly every capacity/cost-focused interview answer (§61's Step 5) — proposing uniform model usage across a system with genuinely varied request complexity is a missed optimization. **Cross-References:** §1.5, §27.5, §54.4, §59.4.

### 68.5 Cascade Models Pattern

**Business Problem:** Most requests are simple and cheap to handle correctly, but a minority are genuinely hard — running every request through an expensive model wastes cost on the easy majority. **Engineering Motivation:** A refinement of the routing pattern (§68.4) that doesn't require upfront classification — instead, a cheap/fast model attempts the request first, and only escalates to a more capable model if the cheap model's output fails a confidence or quality check. **Architecture:** Cheap model attempt → confidence/quality check (often a lightweight classifier or self-reported confidence score) → escalate to expensive model only on failure. **Tradeoffs:** Avoids the routing pattern's upfront classification-accuracy risk (§68.4), but every escalated request now pays the latency cost of *two* model calls (the failed cheap attempt plus the expensive retry) rather than routing directly. **Failure Modes:** A poorly-calibrated confidence check either escalating too often (losing the cost benefit) or too rarely (letting poor-quality cheap-model output through uncaught). **Production Signals:** Escalation rate tracked as a first-class metric — a rising escalation rate may indicate request complexity is drifting upward, a useful early signal distinct from routing's classification-accuracy metric. **When NOT to Use It:** When request complexity can be reliably predicted upfront (routing, §68.4, is simpler and avoids the double-latency cost); when even a single expensive-model call's latency is unacceptable for the escalated path. **Real-World Examples:** A support-ticket triage system attempting resolution with a cheap model and escalating unresolved tickets to a stronger model or a human. **Interview Discussion:** A good answer to "how do you avoid always using the most expensive model, without upfront classification risk" — worth contrasting explicitly against §68.4 in an interview to show awareness of the tradeoff between the two. **Cross-References:** §1.5, §27.5, §29.3 (confidence/judge calibration).

### 68.6 Fallback Pattern

**Business Problem:** A primary model or service can become unavailable, degraded, or excessively slow, and the product must remain functional despite this. **Engineering Motivation:** Directly §14.5/§31.7's fallback-model mechanism — availability resilience, distinct from the cascade pattern's (§68.5) cost-optimization motivation even though both involve a secondary model. **Architecture:** Health/latency monitoring on the primary model path; automatic routing to a pre-validated secondary model or provider when the primary fails a threshold check. **Tradeoffs:** Availability resilience versus a real risk of quality inconsistency (the fallback model may respond meaningfully differently to the same prompt, §16.7's tokenizer/behavior differences) — and this risk is invisible unless the fallback path is proactively tested (§31.7), not just configured. **Failure Modes:** A fallback path that's never been tested in practice failing silently or producing broken output the first time it's actually needed, precisely when the system is already under stress. **Production Signals:** Fallback-activation rate and fallback-path quality metrics tracked separately from primary-path metrics (§31.7). **When NOT to Use It:** Extremely rarely inappropriate for a production system with any real availability requirement — the more common mistake is configuring it but never testing it. **Real-World Examples:** §31.7's general mechanism; any production LLM application with a documented secondary-provider fallback. **Interview Discussion:** Nearly always worth mentioning for Step 11 (Scaling/Resilience) of §61's framework — a design with a single model provider and no fallback path is a single point of failure a strong answer should flag explicitly. **Cross-References:** §14.5, §31.7, §16.7.

### 68.7 Engineering Intuition Across This Chapter's Patterns

> **How do Routing, Cascade, and Fallback differ if they all involve more than one model?** Routing decides *upfront* based on request classification (cost/capability optimization); Cascade decides *reactively* based on the cheap model's own output quality (cost optimization without upfront classification); Fallback decides *reactively* based on the primary path's health/availability (resilience, not cost optimization) — same surface shape (multiple models), three different triggers and three different purposes.

> **What would over-engineering look like here?** Implementing all three patterns simultaneously for a product with low, predictable traffic and a single reliable model provider — each pattern earns its complexity only under the specific condition (cost sensitivity at scale, unpredictable complexity distribution, or availability risk) that motivates it.
