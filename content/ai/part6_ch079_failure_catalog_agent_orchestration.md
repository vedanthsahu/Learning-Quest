## 79. Failure Catalog III: Agent & Orchestration Failures

### 79.1 Agent Loop

**Symptoms:** The same tool invoked repeatedly with near-identical arguments; `max_steps` hit routinely rather than as a rare edge case. **Possible Causes:** Ambiguous tool results the model can't distinguish success/failure/emptiness from (§36.6); absent goal-completion reflection (§25.4); genuine task-complexity/model-capability mismatch. **Metrics:** Steps-per-request distribution, tool-repetition rate (§36.4, §36.12). **Logs:** Full step-by-step tool-call trace (§31.2). **Investigation Steps:** §36.5 — inspect exactly what the model "saw" after each tool call before the loop began. **Root Cause:** Most often tool-result ambiguity. **Mitigation:** §36.7 in full. **Prevention:** Unambiguous tool-result design and mandatory goal-check reflection (§36.9) tested before any new tool ships. **Lessons Learned:** Full treatment at §36 — the defining reliability risk of autonomous, as opposed to deterministic-workflow, architectures.

### 79.2 Infinite Planning

**Symptoms:** An agent using explicit upfront planning (§25.3, §69.4) repeatedly regenerates or revises its plan without ever proceeding to execution, or oscillates between two incompatible plans. **Possible Causes:** The planning step has no termination condition distinct from "plan looks good enough" (an inherently fuzzier check than a tool-loop's goal-completion reflection, §79.1); conflicting or underspecified requirements causing the planner to perpetually find fault with its own plan; a planning prompt that invites excessive self-revision without a hard cap. **Metrics:** Plan-revision count per request, analogous to §36.4's steps-per-request but specific to the planning phase before any execution begins. **Logs:** Each generated plan version and the stated reason for revision. **Investigation Steps:** Inspect the sequence of plan revisions to determine whether the planner is converging (each revision genuinely improves the plan) or oscillating (revisions cycle between similar states without progress). **Root Cause:** Usually a missing hard cap on planning iterations, combined with a planning prompt that doesn't clearly define "good enough to proceed." **Mitigation:** Add an explicit `max_planning_iterations` safeguard (directly analogous to `max_steps`, §25.11) and a clearer, more concrete definition of plan sufficiency in the planning prompt. **Prevention:** Treat the planning phase with the same reliability rigor as the execution phase (§36.9) — a safeguard on one but not the other is an incomplete fix. **Lessons Learned:** A reminder that §36's agent-loop risks apply to *any* unbounded iterative LLM process, not only tool-calling loops specifically — planning-only agents need the same discipline.

### 79.3 Model Routing Failure

**Symptoms:** A request is routed to an inappropriately weak model for its actual complexity (producing a quality regression) or an inappropriately strong/expensive model for simple requests (producing unnecessary cost, §33). **Possible Causes:** The routing classifier (§27.5, §68.4) is poorly calibrated or trained on a request distribution that no longer matches actual production traffic; routing configuration not updated after a model-tier change (§78.4's model-regression risk compounding with routing). **Metrics:** Quality metrics (§29) segmented by route/model, checked for an unexpected gap; cost distribution across routing tiers (§31.4) checked against expectation. **Logs:** Routing decision and the request that triggered it, per request (§31.3). **Investigation Steps:** Sample misrouted-looking requests (low quality on a "simple" route, or high cost on a route meant to be cheap) and manually assess whether the routing classification was actually correct for that specific request. **Root Cause:** Most often routing-classifier drift relative to a changing request distribution, or a stale routing configuration after a model-tier change. **Mitigation:** Re-calibrate or retrain the routing classifier against current traffic; update routing configuration explicitly whenever underlying model tiers change. **Prevention:** Regression-test routing accuracy (§29) as its own tracked metric, not just downstream quality — a routing failure can hide behind acceptable *average* quality while still causing real per-segment regressions. **Lessons Learned:** Routing is itself a model/classifier subject to the same drift and evaluation discipline as any other AI component (§78.4) — "we added routing" doesn't mean routing correctness can be assumed and forgotten.

### 79.4 Conversation Drift

**Symptoms:** A long-running conversation gradually loses coherence — the assistant's responses stop reflecting earlier-established context correctly, or contradict earlier statements within the same conversation. **Possible Causes:** Conversation summarization (§45.4, §71.7) losing critical detail during compression; the verbatim-retention window being too short for the actual conversational dependency length; accumulated small summarization errors compounding across multiple summarization cycles in a very long conversation. **Metrics:** Faithfulness-to-earlier-context checks (a specialized evaluation, distinct from RAG faithfulness, comparing later responses against what was actually established earlier in the same conversation). **Logs:** Full conversation history including every summarization-cycle boundary (§31.3). **Investigation Steps:** Identify the specific point in the conversation where drift became noticeable, and inspect whether that point coincides with a summarization cycle (§45.4) that may have dropped or distorted relevant detail. **Root Cause:** Most often information loss during a summarization cycle, compounding as multiple cycles occur across a very long conversation. **Mitigation:** Widen the verbatim-retention window if drift correlates with recent summarization; improve summarization-prompt specificity to preserve more critical detail; consider offloading stable facts to semantic memory (§71.2) rather than relying on summarization to preserve them indefinitely within conversation history alone. **Prevention:** Evaluate conversation memory specifically for long-conversation coherence (§39.7's trajectory-level evaluation) rather than only per-turn quality, which won't catch this failure mode. **Lessons Learned:** A distinct failure mode from the tool-related agent loop (§79.1) — this is a memory/context-management failure, not an orchestration-control failure, even though both manifest as "the conversation seems broken."

### 79.5 Memory Corruption

**Symptoms:** Long-term memory (§48, §71.2-71.3) retrieves and presents information that's incorrect, outdated, or attributable to the wrong user — a distinct and more serious failure than mere staleness (§48.6). **Possible Causes:** A memory-extraction bug storing a fact incorrectly or attributing it to the wrong user/session; a tenant-scoping/access-control gap (§54.4) allowing cross-user memory leakage; a race condition in concurrent memory writes corrupting a stored entry. **Metrics:** Memory-retrieval accuracy spot-checks (a sampled human-review process, since automated faithfulness checks alone may not catch attribution errors); cross-user memory-leakage incidents specifically tracked as a distinct, high-severity metric (§42.5's severity weighting applies at maximum intensity here, directly analogous to §54.6's tenant-isolation severity). **Logs:** Full memory-write history including the source interaction and extraction process that produced each stored entry (§31.3). **Investigation Steps:** Trace a corrupted memory entry back to its originating extraction event; check specifically whether tenant/user scoping (§54.9's structural wrapper) was correctly applied at write time. **Root Cause:** Most often either an extraction-pipeline bug or a missing/incorrectly-applied scoping filter, rather than a retrieval-ranking problem. **Mitigation:** Fix the extraction pipeline or scoping gap; purge and, where possible, regenerate corrupted entries. **Prevention:** Treat every memory-write path with the same mandatory, structural tenant/user-scoping discipline as any other persistent store (§54.8's decision tree, applied to memory writes specifically, not just reads). **Lessons Learned:** The single most severe failure in this chapter given real privacy/trust consequences — a memory-corruption incident involving cross-user leakage should be treated with the same severity as any other data-leakage incident (§13.4), not as an "AI quirk."

### 79.6 Engineering Intuition

> **What's the common thread across Agent Loop (§79.1) and Infinite Planning (§79.2)?** Both are unbounded-iteration failures missing a hard safeguard — the fix pattern (an explicit step/iteration cap plus a clear, checkable completion condition) is identical even though one operates on tool-calling and the other on plan generation.

> **Why does Memory Corruption (§79.5) deserve the highest severity classification in this chapter?** Because unlike a quality regression (annoying but recoverable) or a cost spike (expensive but reversible), cross-user memory leakage is a genuine privacy/trust violation with consequences that don't fully undo even after the bug is fixed — directly the domain-consequence severity weighting §42.5 taught for production incidents generally.
