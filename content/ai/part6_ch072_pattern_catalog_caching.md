## 72. Pattern Catalog V: Caching Patterns

### 72.1 Prompt Cache Pattern

**Business Problem:** Many requests share an identical or near-identical prompt prefix (a system prompt, few-shot examples, a frequently-reused document), and reprocessing that shared prefix's prefill computation (§15.7) on every single request wastes latency and cost. **Engineering Motivation:** Directly §24.6's mechanism — a model provider caches the internal computation for a stable, repeated prefix, so subsequent requests reprocess only the variable suffix. **Architecture:** §24.10's prompt-structuring pattern — stable content first, variable content last. **Tradeoffs:** A direct latency/cost win with essentially no quality tradeoff, contingent entirely on correct prompt structuring (§32.6's caching-regression root cause if structure is broken). **Failure Modes:** Placing variable content before the stable prefix, silently invalidating the cache for everything after it (§46.6's Nova-specific instance of this risk). **Production Signals:** Cache-hit rate tracked as a first-class metric (§31.4) — a sudden drop is a specific, diagnosable regression (§32.11's decision tree). **When NOT to Use It:** Rarely inappropriate to enable when supported — the failure mode is misconfiguration, not overuse. **Real-World Examples:** §46.4's Nova Stage 3 restructuring. **Interview Discussion:** A near-mandatory mention for any latency/cost-focused interview answer (§61's Steps 4-5) involving repeated system prompts or documents. **Cross-References:** §15.7, §24.6, §32.6, §46.

### 72.2 Semantic Cache Pattern

**Business Problem:** Many distinct users ask semantically equivalent (though not textually identical) questions — "what's your refund policy" and "how do refunds work" — and generating a fresh, expensive model response for each phrasing wastes cost on requests that could reuse a previous answer. **Engineering Motivation:** Rather than an exact-match cache (only helps for byte-identical requests), a semantic cache embeds each incoming query (§20.2) and checks for a sufficiently similar *previously-answered* query in a cache store, returning the cached response if similarity exceeds a threshold rather than calling the model again. **Architecture:** Incoming query → embed → similarity search (§21.3, against a cache of prior query-response pairs, not the main document corpus) → if a close-enough match exists, return the cached response; otherwise, generate normally and store the new query-response pair for future reuse. **Tradeoffs:** Can produce substantial cost savings for products with high query redundancy, at real risk: an imprecisely-tuned similarity threshold can return a cached response to a query that's similar but not equivalent, producing a subtly wrong answer that looks confident (a distinct hallucination-adjacent risk, §35, specific to this pattern). **Failure Modes:** Threshold set too loosely, serving stale or mismatched cached responses to queries that actually needed a fresh answer; cached responses becoming stale as underlying facts change, with no invalidation mechanism (directly analogous to §20.7's embedding-drift risk, applied to cached answers rather than retrieval). **Production Signals:** Cache-hit rate alongside a sampled quality check specifically on cache-served responses (are they actually still appropriate for the queries that triggered the cache hit) — a semantic cache's hit rate alone doesn't prove its correctness, unlike prompt caching (§72.1), which is exact and lossless by construction. **When NOT to Use It:** Products with low query redundancy (most queries are genuinely distinct) where the cache rarely hits and its risk isn't offset by meaningful savings; any domain where a stale or slightly-mismatched answer carries real consequence (§65.3's healthcare, §65.4's financial examples) without very conservative thresholds and explicit invalidation. **Real-World Examples:** FAQ-heavy customer support systems (§63.4) with highly repetitive query patterns. **Interview Discussion:** A sophisticated cost-optimization answer specifically for high-redundancy query patterns — a candidate should proactively flag the staleness/precision risk unprompted, since it's the pattern's defining tradeoff. **Cross-References:** §20.2, §21.3, §20.7, §35.

### 72.3 Embedding Cache Pattern

**Business Problem:** Computing an embedding for the same piece of text repeatedly (e.g., re-embedding an unchanged document on every retrieval-pipeline rebuild, or re-embedding a frequently-repeated query) wastes compute on a deterministic, repeatable operation. **Engineering Motivation:** Cache the embedding output for a given input text (keyed on a hash of the text plus the embedding model version, critically — §20.7's drift concern makes model-version part of the cache key non-negotiable), avoiding redundant embedding-model calls for unchanged content. **Architecture:** Before embedding any text, check a cache keyed on (text-hash, model-version); on a hit, reuse the stored vector; on a miss, compute and store. **Tradeoffs:** Straightforward, low-risk cost/latency savings (unlike the semantic cache's precision risk, §72.2, this pattern is exact-match and lossless) at the cost of cache storage and invalidation-key management. **Failure Modes:** Omitting model version from the cache key, serving a stale embedding from a prior model version after an upgrade — directly reproducing §38.4's embedding-migration incident if this cache isn't correctly invalidated alongside a full re-embed. **Production Signals:** Cache-hit rate for embedding computation; explicit verification that cache entries are purged/versioned correctly during any embedding-model migration (§38.14's re-embed-completeness check applies directly to this cache too). **When NOT to Use It:** Rarely inappropriate — the risk is entirely in correct invalidation (especially around model upgrades), not in overuse of the pattern itself. **Real-World Examples:** Any RAG ingestion pipeline (§47) re-processing a partially-changed document corpus, where only changed documents should be re-embedded. **Interview Discussion:** A detail-oriented answer showing awareness that embedding computation itself, not just retrieval, has a real, cacheable cost — and that this cache's key must include model version to avoid §38's incident class entirely. **Cross-References:** §20.2, §20.7, §38.4, §38.14.

### 72.4 Engineering Intuition

> **How do these three caching patterns differ in risk profile?** Prompt caching (§72.1) is exact-match and lossless — essentially risk-free when correctly structured. Embedding caching (§72.3) is also exact-match and lossless, with risk concentrated entirely in invalidation correctness around model version changes. Semantic caching (§72.2) is fundamentally different — an approximate-match cache with a real, ongoing precision risk that must be actively managed, not just correctly configured once.

> **What would over-engineering look like across this chapter?** Building a semantic cache (§72.2) for a product with genuinely low query redundancy, where the engineering cost and staleness risk aren't offset by meaningful hit rate — verify actual query redundancy via analytics before investing in this specific pattern.
