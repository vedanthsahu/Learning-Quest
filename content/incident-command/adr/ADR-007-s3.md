# ADR-007 — S3 for Object Storage

## Status
Proposed

## Context
Large artifacts (uploaded documents, conversation archives, evaluation datasets, exported traces/reports) need a storage layer distinct from PostgreSQL. See [08-data-architecture](../08-data-architecture.md).

## Problem
Where do large/blob-shaped artifacts live, locally and in the eventual cloud phase?

## Options considered
- **S3 (via MinIO locally, real S3 in AWS phase)** — S3-compatible API lets local dev and cloud deployment share the same client code, easing the Level 8 transition.
- **Filesystem storage** — simpler locally but doesn't transition to cloud without a rewrite, and doesn't teach the object-storage patterns that are a stated learning goal.
- **PostgreSQL BLOBs** — explicitly rejected per source brief §11 ("do not force every piece of state into PostgreSQL").

## Decision
S3-compatible storage (MinIO for local dev, real AWS S3 at Level 8) for large artifacts.

## Rationale
MinIO's S3-compatible API means the object-storage abstraction is built once and used unchanged across local dev and cloud deployment — directly supporting the "correct locally first, then deploy" progression in [18-deployment-strategy](../18-deployment-strategy.md).

## Tradeoffs
One more local service to run (MinIO) versus plain filesystem storage — accepted for the cloud-transition benefit and the explicit S3 learning goal.

## Consequences
No Level 0-4 feature currently requires this (no document upload in [01-pdd](../01-pdd.md)'s core journeys yet) — S3/MinIO can be introduced when the first artifact-shaped feature (e.g., conversation archival, eval dataset storage) actually needs it, rather than stood up speculatively on day one.

## Reconsideration conditions
None anticipated.
