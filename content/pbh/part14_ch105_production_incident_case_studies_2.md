## 105. Production Incident Case Studies II

### 105.1 Case Study 3: The Migration That Locked the Table

**Timeline**: 02:00 (a scheduled low-traffic deployment window) — a migration adding a `NOT NULL` column with a default value to a large, actively-written-to `orders` table begins running. 02:01 — the migration is still running; application error rates begin climbing sharply. 02:03 — nearly every request touching the `orders` table is timing out; the on-call engineer is paged. 02:04 — the migration is identified as still in progress and is the suspected cause. **Investigation**: The database's own lock-monitoring view shows the migration holding an exclusive lock on the `orders` table for its full duration, blocking every concurrent read and write against that table for as long as the migration takes to rewrite every existing row with the new column's default value. **Root cause**: Adding a `NOT NULL` column with a default in a single migration step, on a database engine (or version) where this requires a full table rewrite under an exclusive lock, rather than using the three-step zero-downtime pattern (companion §28.6): add the column as nullable first, backfill in batches, then add the `NOT NULL` constraint only after every row already has a value. **Fix**: The migration was cancelled, and a corrected, three-step migration was run instead, each step individually fast and non-blocking. **Lessons**: (1) A migration that is perfectly correct in its *final result* (the schema companion §28.6 wants to reach) can still be a severe incident in *how* it gets there — reviewing a migration's final schema diff is not sufficient; its execution behavior against a large, live table must be reviewed separately. (2) "Low-traffic window" reduces an incident's blast radius but does not eliminate the underlying risk — this incident still caused real, user-visible errors even at 2 AM, for whichever requests were in flight. (3) This is precisely companion §28.6's own named pattern; an incident of this exact shape is close to unavoidable for a team that hasn't internalized that specific chapter, and close to entirely preventable for one that has — a clean illustration of why Part IV's database chapters emphasize this so heavily.

### 105.2 Case Study 4: The Silent Data Corruption

**Timeline**: A team notices, during a routine data audit weeks after a feature shipped, that a small percentage of records have an impossible combination of field values that the application's own validation logic should have rejected. No alert fired at any point; the discovery was accidental. **Investigation**: Git history and logs are reviewed for the relevant time window; the records in question were all created during a brief period when a specific validation function had a bug (a boundary condition using `<` where `<=` was intended, silently accepting one invalid case at the edge). The bug was already fixed in a later, unrelated commit, with no one realizing at the time that it had been masking active data corruption. **Root cause**: A validation bug at a boundary condition, combined with the complete absence of any invariant-checking mechanism *after* data is written — the application trusted its own write-time validation completely and never independently verified that written data actually satisfied its own invariants. **Fix**: Beyond correcting the already-fixed validation bug (already resolved before this investigation began), the team added a scheduled data-integrity check — a periodic query asserting the same invariant the validation function is supposed to enforce, alerting if any row ever violates it. **Lessons**: (1) Write-time validation and post-write invariant checking are different, complementary safety mechanisms, not substitutes for each other — validation prevents most bad writes; a periodic invariant check catches the rare cases where validation itself was buggy. (2) A bug can be silently active in production for an extended period with zero symptoms if nothing is actively checking for the specific failure mode it causes — the absence of an alert is not evidence of the absence of a problem, only evidence that nothing is currently watching for that specific problem. (3) This incident's discovery method — an unrelated, routine audit — is a weak, unreliable detection mechanism; the actual fix is making detection systematic and continuous rather than dependent on someone happening to notice during unrelated work.

### 105.3 The Pattern Across Both Chapters' Four Case Studies

Every incident across §104-105 shares one structural trait: the eventual root cause was a mechanism this handbook already taught explicitly in an earlier Part (§75's unbounded caches, §67's circuit breakers, §28.6's zero-downtime migrations, and validation-versus-invariant-checking as distinct disciplines) — none of these incidents required novel diagnostic technique to resolve, only recognizing which already-known pattern applied. This is deliberate: real production incidents overwhelmingly recur along a fairly small number of well-understood failure shapes, and the actual skill being built across this entire handbook is fast, confident pattern recognition against that shape catalog, not inventing new diagnostic approaches under incident pressure.
