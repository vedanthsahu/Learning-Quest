## 77. Why Are Uploads Timing Out, Why Is CPU Utilization High, Why Are Responses Inconsistent?

### 77.1 The Purpose of This Chapter

The preceding six chapters (§70-76) each diagnosed one specific, sharply-defined symptom. This closing Part XII chapter is deliberately different in shape: it consolidates three remaining, commonly-reported symptoms into a single triage chapter, both because each has a shorter diagnostic path than the preceding chapters and because presenting them together builds the general-purpose triage instinct — recognizing which of this Part's seven diagnostic frameworks actually applies to a new, not-yet-categorized complaint — that this Part's entire structure has been building toward.

### 77.2 Why Are Uploads Timing Out?

**Symptoms:** File upload requests specifically (as distinct from other endpoints) fail with a timeout, either at a proxy/load-balancer level or the application's own request timeout, disproportionately for larger files. **Possible Causes:** The entire file is being buffered into memory before any processing begins (companion §35.7's streaming-versus-buffering distinction) rather than processed as a stream, meaning the actual wall-clock time scales with file size in a way a fixed timeout wasn't calibrated for; a synchronous, blocking file-processing step (virus scanning, image resizing, companion §12.2) occurring inside the async request path without being offloaded to a background worker (companion §33) or executor (companion §11.5); a client's upload bandwidth being slower than the server-side timeout assumes, especially for large files over constrained client connections; or a genuinely oversized file with no upload size limit enforced (companion §35.8), taking disproportionately long simply because nothing bounds how large an accepted upload can be. **Root Cause (in practice):** Overwhelmingly, synchronous buffering of the entire file before streaming processing begins, combined with a fixed request timeout that was calibrated against small-file latency and never re-evaluated against genuinely large-file upload time. **Fix:** Process uploads as a genuine stream (companion §35.7) rather than buffering entirely in memory first; move any CPU-intensive or slow post-upload processing (virus scanning, transcoding) to a background job (companion §33.4) that the client polls or is notified about, returning an immediate "upload accepted" response rather than blocking the request on the full processing pipeline; enforce an explicit maximum upload size (companion §35.8) calibrated to what the timeout budget can actually accommodate. **Tradeoffs:** Streaming processing is more complex to implement correctly than simple buffer-then-process code (companion §35.7's added complexity) but is the only approach that scales to large files at all; moving processing to a background job requires a client-side polling or notification mechanism (companion §39) that a simple synchronous response didn't need. **Decision check:** Does the timeout scale with file size in a way that matches actual measured processing time per byte? If not, the timeout budget itself, not the processing logic, may be the actual mismatch to fix.

### 77.3 Why Is CPU Utilization High?

**Symptoms:** Server CPU utilization is persistently high, either uniformly or in periodic spikes, independent of whether request latency itself has degraded (high CPU with acceptable latency is a capacity-planning concern; high CPU *with* degraded latency is an active incident). **Possible Causes:** A genuinely CPU-bound workload (companion §9.5) has grown past the capacity provisioned for it — more traffic, or a computationally heavier per-request workload, than originally sized for; an inefficient algorithm or data structure (companion §53's Big-O discipline) performing far more work than the task actually requires, often only becoming visible as input size or traffic grew past what smaller-scale testing exercised; excessive, unnecessary serialization/deserialization overhead (companion §56.1) for large payloads; or — the specific case most easily confused with a genuine capacity problem — synchronous, blocking calls inside async code (companion §12.2) that appear as CPU activity on the specific core handling that blocked call, when the actual issue is architectural, not computational. **Root Cause (in practice):** A profiled hot function (companion §54.2) is the only reliable way to distinguish these causes — guessing without profiling frequently misattributes a blocking-call issue to "needing more CPU" (leading to an ineffective, purely-additive scaling response) when the actual fix is architectural. **Fix:** Profile first (companion §54.2), always, before choosing between "optimize the specific hot function," "move genuinely CPU-bound work to a process pool" (companion §10.6), or "this is actually a blocking-call issue disguised as high CPU" (companion §73's diagnostic pattern, generalized). **Tradeoffs:** Scaling up capacity (more cores, more instances) without first profiling risks masking, rather than resolving, an underlying inefficiency — the same total cost recurs and grows as traffic grows, whereas a genuine algorithmic or architectural fix removes the cost at its source. **Decision check:** Has a profiler actually identified the specific hot function or call, or is "high CPU" being treated as self-explanatory without this step? Skipping profiling is, by a wide margin, the most common process failure behind a mis-diagnosed high-CPU incident.

### 77.4 Why Are Responses Inconsistent?

**Symptoms:** Identical or near-identical requests produce meaningfully different latencies, or occasionally different results, across repeated calls — "inconsistent" here meaning high variance rather than a single, uniformly bad measurement. **Possible Causes:** Load is unevenly distributed across worker processes or instances (companion §16.8, Software Systems Handbook's load-balancing chapter), so some requests land on an already-busy worker while others land on an idle one; a shared, contended resource (a connection pool at partial exhaustion, companion §72; a lock, companion §11.7) causing some requests to wait while others proceed immediately, without the system being fully exhausted in a way that would produce uniform slowness; cache hit/miss variance (companion §47.5) — a cache-hit request completes quickly while a cache-miss request for the same logical resource incurs the full underlying cost, producing a bimodal (not evenly distributed) latency pattern rather than a single average; or non-deterministic behavior in the code itself (companion §5.6's mutable-default-argument-style hazards, or a race condition, companion §11.6) producing genuinely different *results*, not just different latencies, for ostensibly identical requests. **Root Cause (in practice):** A bimodal latency distribution — most commonly caused by cache hit/miss variance or partial resource contention — is far more common than genuine randomness in application logic; distinguishing "inconsistent latency" from "inconsistent results" early is essential, since they point toward entirely different investigation paths (performance/contention analysis versus a correctness/determinism bug hunt). **Fix:** For latency variance, examine the full latency distribution (companion §58.2's percentile discipline, not an average) to detect bimodality directly, then trace the bimodal split back to its specific cause (cache hit/miss, partial pool contention, uneven load balancing); for result variance, audit the specific code path for shared mutable state (companion §11.6) or any other source of genuine non-determinism. **Tradeoffs:** None specific to this symptom beyond the tradeoffs already inherent in whichever underlying cause (caching, contention, load balancing) is ultimately identified — this chapter's role is correctly routing the investigation, not introducing a new class of remediation cost. **Decision check:** Is the inconsistency in *latency* or in *actual returned results*? This single question, answered first, determines which of this handbook's frameworks (performance diagnosis versus correctness/concurrency-safety review, companion §11.6) actually applies.

### 77.5 Closing Note: Using This Part as a Triage Reference

§70-77 together form a reusable triage reference, not a linear reading sequence to be consumed once and set aside — the actual practice this Part is meant to instill is pattern-matching a new, unfamiliar production symptom onto the closest of these eight frameworks, then following that framework's specific Symptoms-through-Prevention structure rather than starting from an unstructured, first-principles investigation each time. A production incident that doesn't cleanly match any single chapter here is itself informative — it may combine two of this Part's causes simultaneously (a connection-pool issue, §72, triggered specifically because a blocking call, §73, is holding connections open far longer than necessary), and recognizing that combination is the mark of genuine diagnostic fluency this entire Part has been building toward.
