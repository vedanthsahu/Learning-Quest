## 28. Alembic & Migrations

### 28.1 The Problem: A Database Schema Must Evolve Without Losing Data or Breaking Running Code

A backend's database schema is never truly final — a new feature needs a new column, a new table, a changed constraint. Applying these changes by hand, directly against a production database, is exactly the kind of untracked, unrepeatable, unreviewable operation companion §113.3's real migration-incident case study warned about generally — a schema change needs the same rigor as any other production deployment: reviewed, versioned, tested against a copy of real data, and reversible if something goes wrong.

### 28.2 Engineering Constraint: Multiple Environments Must Share One Schema History, Deterministically

A development environment, a staging environment, and production all need to reach the *same* schema state through the *same* sequence of changes, in the same order, regardless of which environment applies them or when — otherwise "works on staging" provides no real confidence about production, since the two might have silently diverged in schema shape without anyone noticing until a query fails unexpectedly against a column that doesn't exist where it was assumed to.

### 28.3 Python Mechanism: Alembic Migrations as Versioned, Ordered Python Scripts

**Alembic** (the standard migration tool for SQLAlchemy-based Python backends) represents each schema change as its own versioned Python script, with an explicit `upgrade()` function (applying the change) and `downgrade()` function (reversing it) — each migration references the specific prior migration it builds on, forming a linear (or, when branches merge, a directed) history that can be replayed deterministically against any database currently at an earlier point in that history, bringing it forward to any later point.

### 28.4 Decision Framework: Autogenerate Migrations, But Never Trust Them Blindly

Alembic can **autogenerate** a migration by diffing your current ORM model definitions against the live database's actual schema — genuinely useful for catching the bulk of a change mechanically, but autogeneration cannot infer intent: renaming a column looks, to a diff, identical to dropping one column and adding an unrelated new one, and autogeneration will produce a migration that drops and recreates (losing all existing data in that column) rather than the rename that was actually intended. Every autogenerated migration must be read and, where necessary, hand-corrected before being trusted — treating autogeneration as a first draft, not a finished product, is the correct discipline.

### 28.5 Tradeoff: Backward-Compatible Migrations vs. a Single Atomic Cutover

A migration that adds a new required (`NOT NULL`, no default) column to an existing, populated table fails outright unless every existing row already has a value for it — the practical pattern for this specific, common case is a **multi-step migration**: add the column as nullable first, backfill existing rows with a sensible value in a separate step, then a later migration adds the `NOT NULL` constraint once every row genuinely has a value — trading one simple-looking migration for three deliberate, safer ones, directly the same zero-downtime-migration discipline the companion Software Systems Handbook develops generally (companion §34), now given its concrete Alembic-specific implementation shape.

### 28.6 Implementation

```python
"""add cancellation_reason to bookings

Revision ID: a1b2c3d4e5f6
Revises: 9f8e7d6c5b4a
"""
from alembic import op
import sqlalchemy as sa

revision = "a1b2c3d4e5f6"
down_revision = "9f8e7d6c5b4a"    # links this migration to its predecessor,
                                    # forming the ordered history (§28.3)

def upgrade() -> None:
    op.add_column(
        "bookings",
        sa.Column("cancellation_reason", sa.Text(), nullable=True),  # nullable
    )                                                                  # first
                                                                        # (§28.5)

def downgrade() -> None:
    op.drop_column("bookings", "cancellation_reason")


# A SECOND, later migration -- only after confirming the application is
# fully deployed and writing this field correctly on every cancellation:
def upgrade_step_two() -> None:
    op.execute("UPDATE bookings SET cancellation_reason = '' WHERE cancellation_reason IS NULL")
    op.alter_column("bookings", "cancellation_reason", nullable=False)  # NOW
                                                                          # safe
```

`down_revision = "9f8e7d6c5b4a"` is what makes Alembic's history a genuine, ordered chain (§28.3) — Alembic uses this reference to determine the exact sequence of migrations needed to bring any database from its current state to any target state, applying `upgrade()` functions in order (or `downgrade()` functions in reverse, if rolling back). The two-step pattern (nullable column first, `NOT NULL` constraint added only in a later migration after backfilling) directly demonstrates §28.5's zero-downtime discipline — a single migration adding a `NOT NULL` column immediately would fail against the table's existing, unpopulated rows.

### 28.7 Production Considerations

Migrations should run as an explicit, separate deployment step — never triggered automatically and silently as a side effect of application startup — because a migration failing partway through (a long-running `ALTER TABLE` on a large table, interrupted) needs to be a visible, investigated event, not something masked by the application simply retrying its own startup and potentially running the same migration attempt repeatedly. For genuinely large tables, even a seemingly simple schema change (adding an index, altering a column type) can take a long time and, on some databases, hold a lock blocking normal reads/writes for that duration — companion §63's data-platform-at-scale discussion and PostgreSQL's own `CONCURRENTLY` options for index creation exist specifically to mitigate this, and any migration against a large, actively-written table deserves explicit consideration of its locking behavior before being run against production.

### 28.8 Debugging

**Symptoms:** An application deployed to a new environment fails immediately with a "column does not exist" (or similar schema-mismatch) error; a migration that worked in staging fails or behaves differently in production. **Investigation:** Check whether all pending migrations were actually applied to the environment in question (`alembic current` shows the database's current migration version; compare against the latest migration in the codebase). For a staging-vs-production discrepancy, check whether the two environments' migration histories have actually diverged (a migration applied out of band, directly against production, without a corresponding versioned Alembic script). **Root cause:** A schema state that doesn't match what the deployed application code expects, because the migration history wasn't applied consistently across environments. **Fix:** Apply the missing migrations to bring the environment's schema in line with the codebase's expectations; establish (or enforce) a strict discipline that no schema change ever happens outside a versioned migration, in any environment, including production hotfixes.

### 28.9 Interview Thinking

"How would you add a required field to a table with a million existing rows, with zero downtime?" is testing the multi-step migration pattern (§28.5) specifically — a strong answer walks through all three steps explicitly (nullable column, backfill, then the constraint) and explains *why* a single-step migration would fail or cause downtime against existing data, rather than only naming "Alembic" as an unexplained tool.

### 28.10 Mini Lab

Set up Alembic against a small local PostgreSQL database with an existing, populated `bookings`-style table. Write a migration adding a new required `channel` column using the naive, single-step approach and confirm it fails (or, for a nullable-with-default approach, succeeds but requires care) against the existing rows. Then write the corrected three-step version (nullable column, a `UPDATE` backfilling existing rows, then a constraint-adding migration) and confirm each step applies cleanly in sequence, with the table ending in the same final, fully-constrained state.
