## 95. Worked Interview Examples II: Notification Service, Search Service, Auth Service, Chat Backend

### 95.1 Notification Service

**Phase 1 (Clarify):** Which channels (email, SMS, push)? Must delivery order across channels be preserved, or is each independent? **Phase 2 (Requirements):** Functional — accept a notification request, deliver it via the appropriate channel(s), track delivery status. Non-functional — a failure in one channel's provider must not block or delay other channels' delivery (a direct generalization of companion §86.3's fan-out reasoning from the capstone). **Phase 3 (High-Level Design):** An ingestion API that enqueues one task per (recipient, channel) pair, independent workers per channel type. **Phase 4 (Deep Dive):** Deduplication and idempotency — a strong candidate names that retries on a transient provider failure risk duplicate delivery (companion §86.7's exact hazard) and proposes an idempotency key derived from the notification's own ID, checked before send. **Phase 5 (Wrap-up):** Discuss a user notification-preferences system (opt-outs per channel) as a natural extension, and how it inserts a filtering step before fan-out without otherwise changing the architecture.

### 95.2 Search Service

**Phase 1 (Clarify):** Is this keyword search or does it need semantic/similarity matching? What's the acceptable staleness between a document being created and becoming searchable? **Phase 2 (Requirements):** Functional — index documents, query with ranking. Non-functional — indexing must not block the write path that creates the underlying documents (companion §84.1's identical reasoning from the capstone). **Phase 3 (High-Level Design):** Asynchronous indexing (a queue or the source database's own change stream) feeding a purpose-built search index, decoupled from the primary write path. **Phase 4 (Deep Dive):** PostgreSQL full-text search versus a dedicated engine (companion §88.3's ADR-10, this exact tradeoff) — a strong candidate states the decision criterion explicitly (relevance sophistication and search-specific scale needs) rather than defaulting to "always use Elasticsearch" without justification. **Phase 5 (Wrap-up):** Discuss keeping the search index consistent with the source of truth as data is updated or deleted — the same dual-write consistency problem companion §46.7's Outbox pattern addresses generally.

### 95.3 Authentication Service

**Phase 1 (Clarify):** Is this service used by first-party clients only, or must it support third-party integrations (implying OAuth2, companion §34)? Is instant session revocation a hard requirement? **Phase 2 (Requirements):** Functional — register, authenticate, issue and validate credentials. Non-functional — passwords must never be recoverable from storage (companion §62.2); credential validation must be fast enough not to become a bottleneck for every authenticated request. **Phase 3 (High-Level Design):** Password hashing with bcrypt/argon2 at rest, token issuance (JWT or session-based, companion §80.3's exact ADR-2 tradeoff) for subsequent requests. **Phase 4 (Deep Dive):** The revocation problem for stateless tokens — a strong candidate doesn't claim JWTs are simply "better," but names the specific tradeoff (§80.3) and proposes a concrete mitigation (short expiry plus a lightweight blocklist for the rare forced-revocation case) rather than treating the two options as mutually exclusive. **Phase 5 (Wrap-up):** Discuss multi-factor authentication and how it composes with the base token-issuance flow without redesigning it.

### 95.4 Chat Backend

**Phase 1 (Clarify):** One-to-one only, or group chat? Must messages be delivered in guaranteed order? Is offline message delivery (a user comes online later and sees missed messages) required? **Phase 2 (Requirements):** Functional — send a message, deliver it to online recipients in real time, persist it for offline recipients. Non-functional — a recipient's connection dropping must not lose in-flight messages; the system must scale to many concurrent open connections, not just many requests per second (companion §22.6's WebSocket-specific scaling concern). **Phase 3 (High-Level Design):** WebSocket connections for real-time delivery to online clients, a durable message store for persistence and offline replay, a pub/sub layer (companion §33.5's Redis-backed pattern) so a message from a client connected to one server instance reaches a recipient connected to a different instance. **Phase 4 (Deep Dive):** Cross-instance delivery is almost always where the interviewer pushes — a strong candidate immediately names that WebSocket connections are stateful and pinned to a specific server process, meaning a naive single-instance implementation breaks the moment there's more than one instance, and that a shared pub/sub backplane (exactly companion §33.5's mechanism) is the standard resolution. **Phase 5 (Wrap-up):** Discuss message ordering guarantees under this pub/sub design and what happens if the pub/sub layer itself briefly drops a message — is that acceptable given the stated requirements from Phase 1, or does it require a stronger delivery guarantee (companion §36.5)?

### 95.5 The Pattern Across All Eight Examples (§94 and §95 Together)

Every one of these eight systems, despite covering distinct problem domains, resolved its Phase 4 deep dive using one of a small handful of recurring mechanisms this handbook has already taught in depth: atomic counters for coordination (§61.4), durable queues for decoupling (§37), idempotency keys for safe retries (§32.6), eager decisions about read/write ratio driving caching (§47.2), and pub/sub for cross-instance coordination (§33.5, §35). Recognizing that a new, unfamiliar interview question is very likely a recombination of these same handful of mechanisms — rather than requiring some entirely new idea — is itself the single most transferable interview skill this Part can build.
