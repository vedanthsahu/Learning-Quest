## 94. Worked Interview Examples I: Rate Limiter, URL Shortener, Job Queue, File Upload Service

### 94.1 How to Read These Examples

Each example below is compressed through §93.2's five-phase framework, with Phase 1 and Phase 2 given in full (since they're most often skipped in practice) and Phases 3-4 summarized at the level of naming the key decision points and which companion chapters they draw from, rather than a full transcript — the goal is demonstrating the *shape* of a strong answer, not providing a script to memorize.

### 94.2 Rate Limiter

**Phase 1 (Clarify):** Rate-limit by user, by IP, or by API key? Is a slightly-too-permissive limit under a race condition acceptable, or must it be exact? **Phase 2 (Requirements):** Functional — reject requests beyond N per time window per key. Non-functional — the limiter itself must not become the bottleneck it's protecting the rest of the system from; must work correctly across multiple application instances, not just within one process's memory. **Phase 3 (High-Level Design):** A shared, external counter (not per-process memory, since multiple instances must agree) checked on every request before the request proceeds. **Phase 4 (Deep Dive — typically steered here):** The interviewer usually pushes on the race condition between checking and incrementing the counter — the correct answer is Redis's atomic `INCR` (companion §61.4), not a check-then-set pair, since the latter has the exact race a rate limiter's entire purpose is to prevent. A strong candidate also names the token-bucket versus fixed-window tradeoff (companion §61.3) — fixed window is simpler but allows a burst at window boundaries; token bucket smooths this at slightly higher implementation complexity. **Phase 5 (Wrap-up):** Name that this design adds a hard dependency on Redis's availability for every single request, and discuss fail-open versus fail-closed behavior if Redis itself is down.

### 94.3 URL Shortener

**Phase 1 (Clarify):** Custom aliases supported, or only generated codes? Do shortened URLs expire? What read:write ratio is expected? **Phase 2 (Requirements):** Functional — create a short code for a long URL, redirect on lookup. Non-functional — reads vastly outnumber writes in this system's typical access pattern (a strong candidate states this explicitly, since it drives every subsequent design choice); redirect latency should be very low. **Phase 3 (High-Level Design):** A key-value mapping from short code to long URL, a cache in front of it given the read-heavy pattern just stated (companion §47.2's caching-architecture justification, directly motivated by the stated access pattern rather than applied by default). **Phase 4 (Deep Dive):** Short-code generation — base62 encoding of an auto-incrementing ID versus a random string with a collision check (companion §24's ID-generation tradeoff); a strong candidate names that random generation requires a uniqueness check adding a write-path cost, while incrementing IDs are simpler but reveal creation order and total volume, a real, if minor, information-leak consideration. **Phase 5 (Wrap-up):** Discuss what happens as the single database scales past one instance — sharding by short-code hash, and how the read-heavy cache changes at that scale.

### 94.4 Job Queue

**Phase 1 (Clarify):** Must jobs run exactly once, or is at-least-once with idempotent handlers acceptable? Are jobs prioritized, or strictly FIFO? **Phase 2 (Requirements):** Functional — enqueue a job, have a worker pick it up and execute it, retry on failure. Non-functional — a worker crash mid-job must not silently lose that job (companion §37.4's exactly this concern). **Phase 3 (High-Level Design):** A durable broker (Redis or RabbitMQ, companion §36) holding enqueued jobs, a pool of workers pulling from it. **Phase 4 (Deep Dive):** Visibility timeout / acknowledgment design — a job must not be removed from the queue until the worker confirms completion, and must be requeued if a worker dies mid-processing without acknowledging (companion §37.4's retry-and-dead-letter mechanics); a strong candidate explicitly names that this makes at-least-once delivery the realistic guarantee, and that handler idempotency (companion §32.6) is therefore the caller's responsibility, not something the queue itself can fully solve. **Phase 5 (Wrap-up):** Discuss dead-letter queues for jobs that repeatedly fail, and how a poison-pill job (one that always crashes its worker) is diagnosed and isolated.

### 94.5 File Upload Service

**Phase 1 (Clarify):** What file sizes and types are expected? Is virus scanning or content validation required? **Phase 2 (Requirements):** Functional — accept an upload, store it durably, allow later retrieval. Non-functional — large files must not be fully buffered in memory (companion §35.7); uploads must be validated against their actual content, not just a claimed type (companion §41.4, §63's spoofing risk). **Phase 3 (High-Level Design):** Stream the upload directly to object storage (companion §87.3's identical reasoning from the capstone) rather than through the application's own disk or memory, with only a reference stored in the primary database. **Phase 4 (Deep Dive):** Handling a partially-completed upload if the client disconnects mid-transfer — a strong candidate names multipart/resumable upload protocols and the need to clean up orphaned partial objects in storage, directly connecting to companion §41.3's chunked-upload mechanics. **Phase 5 (Wrap-up):** Discuss malware scanning as an asynchronous, post-upload step (companion §77.2's upload-timeout lesson: never block the upload response on a slow scan) and what "the file is available" should mean to a client while that scan is still pending.

Pick one of these four systems and actually implement its Phase 3 high-level design in code, using this handbook's own earlier chapters as your implementation reference (companion §61 for the rate limiter, §37 for the job queue) — the goal is confirming that your interview-level design decisions survive contact with real implementation detail, not just sound plausible when spoken aloud.
