## 104. Production Incident Case Studies I

### 104.1 How to Read These Case Studies

Each case study is a composite, realistic incident narrative — not a real, specific company's postmortem, but a synthesis of the kind of incident this handbook's Part XII diagnostic frameworks are built to resolve. Read the Timeline section and try to name the root cause yourself before reading further, exactly as an on-call engineer would need to during the actual incident.

### 104.2 Case Study 1: The Slow Leak That Looked Like a Traffic Problem

**Timeline**: 09:00 — a new feature ships, adding a per-request cache of user preferences to avoid a repeated database lookup. 09:00-14:00 — no visible issue; memory usage climbs slowly but stays well within limits. Day 3 — the on-call engineer is paged for elevated response times; initial investigation shows nothing wrong with the database or any external dependency. Day 3, +2 hours — memory usage is discovered to be near the container's limit, and the container has actually been restarting periodically for the past day (unnoticed, since each restart briefly "fixed" the symptom before it slowly returned). **Investigation**: A `tracemalloc` snapshot comparison (companion §57.7, §75.5) taken hours apart shows the new preferences-cache dictionary's entry count growing without bound — every distinct user who made a request added one more permanent entry, with no eviction and no TTL. **Root cause**: The new cache (companion §75.2's exact unbounded-in-process-cache pattern) was added directly as a module-level dictionary, reviewed and approved because the feature "worked correctly" in testing — testing never ran long enough or with enough distinct users to reveal the unbounded growth. **Fix**: Replaced with a bounded LRU cache with a fixed maximum size (companion §47.3). **Lessons**: (1) A feature that is functionally correct in code review can still be a production incident waiting to happen — correctness and resource-boundedness are separate review criteria, and this incident's code review checked only the former. (2) The initial symptom (elevated response times) pointed toward the wrong system entirely (the database) for the first two hours, because the actual cause (memory pressure causing GC pauses and periodic restarts) produces a genuinely confusing, indirect symptom rather than an obvious one. (3) This incident directly matches companion §75's chapter — a team with that diagnostic framework already internalized would likely have reached `tracemalloc` far sooner than two hours in.

### 104.3 Case Study 2: The Retry Storm

**Timeline**: 14:00 — a downstream payment provider begins experiencing its own, unrelated outage, returning errors for roughly 20% of requests. 14:02 — the application's existing retry logic (three retries, no backoff, on any exception) begins retrying every failed call immediately. 14:05 — the retry traffic itself, now roughly 1.6x the original request volume against an already-degraded provider, pushes the provider's error rate up further, triggering more retries. 14:10 — the application's own connection pool to the payment provider is exhausted by the sheer volume of in-flight (mostly retrying) requests, and *unrelated* requests that also need this connection pool begin failing too. **Investigation**: Tracing shows retry attempts dominating outbound call volume, and connection pool exhaustion (companion §72) specifically for the payment-provider client, not the primary database. **Root cause**: Retry logic with no backoff and no circuit breaker (companion §67.2's exact justification for why retries alone are insufficient) turned a partial, 20% downstream degradation into a full outage for every feature depending on that same connection pool — this is companion §67's central lesson, that naive retries can actively worsen an already-degraded dependency rather than merely failing to help it. **Fix**: Added exponential backoff to retries (companion §67.5) and a circuit breaker (companion §67.6) that stops attempting calls entirely once the provider's error rate crosses a threshold, failing fast instead of adding to the retry storm. **Lessons**: (1) Retry logic without backoff is not a safety improvement over no retries at all — under a partial outage, it can be actively harmful, exactly as companion §99.5 warns for non-idempotent operations, but here even for genuinely idempotent operations, because the harm is to *capacity*, not correctness. (2) A circuit breaker's real value is protecting a degraded dependency from being made *worse* by the calling application's own well-intentioned resilience logic, not just protecting the calling application itself. (3) Shared connection pools mean an incident in one integration can blast-radius into unrelated features sharing that pool — a case for per-dependency resource isolation, not just per-dependency timeouts.

### 104.4 Mini Lab

For each case study, write the single metric or log line that, if it had been on a dashboard being actively watched *before* the incident began, would have surfaced the problem earliest — for Case Study 1, this is almost certainly the process's own memory-growth trend line; for Case Study 2, it's the retry rate or the connection-pool utilization for that specific downstream dependency. This exercise directly practices converting a resolved incident's lessons into a concrete, monitorable leading indicator, exactly as companion §70.10 and §74.10's "Engineering Intuition" sections model for their respective failure modes.
