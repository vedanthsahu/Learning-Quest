## 8. Logging, Packaging, Virtual Environments & Dependency Management

### 8.1 The Problem: Knowing What Happened, and Reproducing How It Ran

Two distinct, foundational backend problems this chapter closes Part I with: first, when something goes wrong in production, `print()` statements are not a viable observability strategy — there needs to be a structured, filterable, level-aware record of what the application was doing. Second, a backend has dependencies (specific library versions), and "it works on my machine" is a direct symptom of not having a reliable, reproducible way to pin and recreate exactly which versions are actually running anywhere else.

### 8.2 Python Mechanism: The `logging` Module's Levels and Handlers

Python's standard `logging` module provides severity **levels** (DEBUG, INFO, WARNING, ERROR, CRITICAL) so a single codebase can emit fine-grained detail during development while a production deployment filters to only WARNING-and-above, without changing any code — just the configured threshold. **Handlers** determine where log records actually go (console, a file, a remote log-aggregation service), and can be configured independently of the level filtering and the log-emitting code itself, which never needs to know or care where its output ultimately ends up.

### 8.3 Decision Framework: `print()` Is Never Appropriate in Backend Code Past a Local Script

`print()` has no level, no timestamp, no source-location context, and no way to be selectively enabled or disabled without editing code — every one of these is something `logging` provides for free. The only legitimate backend use of `print()` is a genuinely disposable, local debugging session about to be deleted before commit; anything reaching a code review, let alone production, should use `logging` exclusively, precisely because production debugging (§8.2's levels/handlers) depends entirely on this discipline having been followed consistently beforehand.

### 8.4 Python Mechanism: Structured Logging — Log as Data, Not Just Text

**Structured logging** emits log records as key-value data (commonly JSON) rather than free-form sentences — `logger.info("booking created", extra={"booking_id": "b-1", "user_id": "u-42"})` instead of `logger.info(f"Booking b-1 created for user u-42")`. This matters directly for production debugging at scale: a log-aggregation system can filter, group, and query structured fields precisely (`booking_id = "b-1"`), while a free-text log message requires fragile string-matching or regex to extract the same information back out — this handbook's Part XI (Production Backend Engineering) develops this further as first-class observability infrastructure, not just a formatting preference.

### 8.5 Engineering Constraint: Every Project Needs an Isolated, Reproducible Environment

Two different backend projects on the same machine may need two different, incompatible versions of the same library — installing packages globally makes this impossible to satisfy simultaneously, and worse, means the exact set of installed versions is whatever happens to be on that one machine, not a reproducible, declared fact. A **virtual environment** creates an isolated Python installation and package directory per project, so each project's dependencies are installed and resolved completely independently of every other project and of the system Python.

### 8.6 Decision Framework: Pinning Dependencies — Reproducibility vs. Staying Current

A dependency declared loosely (`fastapi>=0.100`) can silently resolve to a different, newer version on a fresh install than what was originally tested against — a real source of "it worked yesterday" production surprises when a transitive dependency ships a breaking change. A **lock file** (generated by tools like `pip-tools`, `poetry`, or `uv`) pins the *exact* resolved version of every dependency, direct and transitive, guaranteeing that every environment built from the same lock file gets byte-identical package versions. The tradeoff: pinned dependencies require a deliberate, periodic update process (reviewing and testing new versions) rather than silently receiving them — a real ongoing maintenance cost, but one paid on your own schedule rather than discovered by production breaking unexpectedly.

### 8.7 Implementation

```python
import logging
import json

def configure_json_logging(level=logging.INFO) -> None:
    """Configures the root logger to emit structured JSON to stdout."""
    handler = logging.StreamHandler()

    class JsonFormatter(logging.Formatter):
        def format(self, record: logging.LogRecord) -> str:
            payload = {
                "level": record.levelname,
                "message": record.getMessage(),
                "logger": record.name,
            }
            # `extra={...}` fields passed to logger calls land as attributes
            # directly on the record object -- surface any of our own keys:
            for key in ("booking_id", "user_id", "request_id"):
                if hasattr(record, key):
                    payload[key] = getattr(record, key)
            return json.dumps(payload)

    handler.setFormatter(JsonFormatter())
    logging.basicConfig(level=level, handlers=[handler])


configure_json_logging()
logger = logging.getLogger("bookings")
logger.info("booking created", extra={"booking_id": "b-1", "user_id": "u-42"})
# Output: {"level": "INFO", "message": "booking created", "logger": "bookings",
#          "booking_id": "b-1", "user_id": "u-42"}
```

`JsonFormatter` overrides `format` to emit a JSON object instead of a plain string — every field is now individually queryable by a log-aggregation system (§8.4), rather than embedded inside one opaque text blob. Fields passed via `extra={...}` in the `logger.info(...)` call attach directly to the `LogRecord` object as attributes, which is why `hasattr(record, key)` can pull them back out generically inside the formatter.

### 8.8 Production Considerations

Structured logging fields must be chosen deliberately — logging an entire request body or user object as a field risks capturing sensitive data (passwords, tokens, PII) into a log-aggregation system that may have broader access or weaker retention controls than the primary database (companion §62's security chapter develops this explicitly). For dependency management, a lock file must be committed to version control and actually used by the deployment process (not just present in the repo while the deployment installs from a loose `requirements.txt`) — a lock file that exists but isn't the actual install source provides zero real reproducibility guarantee despite looking like it does.

### 8.9 Debugging

**Symptoms:** A production incident is hard to investigate because log messages are free-text and can't be filtered or grouped by the specific booking/user/request involved; a deployment behaves differently than the last one despite "no code changes," traced eventually to a dependency resolving to a different version. **Investigation:** For the logging case, check whether structured fields (`extra={...}`) are actually being used, versus everything being embedded in an f-string. For the dependency case, diff the lock file (or `pip freeze` output) between the two deployments to find which package version actually changed. **Root cause:** Free-text-only logging losing queryable structure; an unpinned or partially-pinned dependency resolving differently across installs. **Fix:** Adopt structured logging with deliberately chosen fields going forward; ensure the deployment process installs strictly from a committed lock file, not a loosely-versioned requirements file.

### 8.10 Interview Thinking

"How would you debug an issue in production without being able to attach a debugger?" is testing whether structured logging with request-scoped identifiers (a `request_id` threaded through every log line for one request, foreshadowing companion §65's distributed tracing) is part of your default engineering habits, not an afterthought reached for only once already in an incident.
