## 112. Production Debugging Exercises II: Cost, Scaling, and Cascading Failure Incidents

### 112.1 Exercise: The Unexplained Cloud Bill Spike

**Alert:** "This month's cloud bill is 40% higher than last month, with no corresponding increase in user traffic or new feature launches." **What would you check first?** Consider §78's cost-optimization-at-scale chapter and its emphasis on a dimensional cost breakdown rather than trusting the aggregate figure. **Investigation:** Broke the bill down by service/resource type rather than looking at the total, and found the increase was concentrated almost entirely in data-transfer (egress/cross-AZ networking) costs, not compute or storage. **Root cause:** A recent, seemingly unrelated infrastructure change had moved a frequently-called internal service to a different availability zone than the services calling it, turning what had been free or cheap same-AZ traffic into billed cross-AZ (and in some call patterns, cross-region) data transfer at high internal call volume. **Fix:** Used availability-zone-aware service discovery/routing to prefer same-AZ instances when available (§28's load-balancing chapter's locality-aware routing), and added cost monitoring specifically on inter-service network traffic as a standing dashboard rather than only reviewing the aggregate bill monthly. **Lesson:** A cost spike with no traffic-volume correlation should immediately prompt a dimensional breakdown (by service, resource type, region/AZ) rather than investigating traffic or feature launches — the actual driver is very often an infrastructure-topology change with a cost consequence nobody explicitly considered at change time.

### 112.2 Exercise: Autoscaling That Doesn't Actually Scale

**Alert:** "Our autoscaling group is configured to scale out at 70% CPU utilization, but during last night's traffic spike, response times degraded badly before any new instances came online, even though the scale-out eventually did trigger correctly." **What would you check first?** Consider §69's Kubernetes-at-scale autoscaling chapter and the distinction between a scaling *trigger* firing correctly and new capacity actually becoming *useful* in time. **Investigation:** Confirmed the CPU-utilization-based scaling trigger fired at the correct threshold and on time — the gap was entirely in the time between a new instance being provisioned and it becoming genuinely ready to serve traffic (application startup time, dependency connection warm-up, and a slow-starting cache that needed to populate before the instance performed adequately). **Root cause:** The autoscaling configuration only accounted for infrastructure provisioning time, not application-level readiness time — new instances were added to the load balancer's rotation as soon as the VM/container was running, before the application inside it was actually capable of serving requests at full performance, causing a period where "more capacity" existed on paper but wasn't yet delivering real relief. **Fix:** Implemented a proper readiness check (distinguishing "process is running" from "application is ready to serve traffic at full performance," §45's Kubernetes readiness-probe concept) so new instances aren't added to the traffic rotation until genuinely warmed up, and additionally moved to a predictive/scheduled scaling component for known traffic patterns rather than relying solely on reactive, threshold-triggered scaling (§27's capacity-planning-based proactive scaling). **Lesson:** A scaling trigger firing "correctly" and "on time" doesn't guarantee the added capacity is immediately useful — readiness/warm-up time is a separate variable from provisioning time, and reactive autoscaling alone is often insufficient for traffic spikes that arrive faster than an instance's full warm-up time.

### 112.3 Exercise: The Cascading Failure from a "Non-Critical" Dependency

**Alert:** "Our entire checkout flow went down for twenty minutes. Investigation shows the root cause was our recommendation service (used to show 'you might also like' items) becoming unresponsive." **What would you check first?** Consider §42's bulkhead/circuit-breaker chapter and §64's real-incident case study on cascading failures from ostensibly non-critical dependencies. **Investigation:** Traced the checkout flow's code path and found that the call to the recommendation service was synchronous and unprotected by any timeout or circuit breaker — when the recommendation service began responding slowly (itself caused by an unrelated, smaller incident on its own database), every checkout request calling it also began blocking, exhausting the checkout service's own thread/connection pool, which then made checkout unavailable for requests that didn't even need the recommendation data to complete successfully. **Root cause:** No bulkhead isolation (§42.5) between an optional, "nice-to-have" dependency and the critical path — the recommendation call was architecturally treated with the same criticality as the actual payment and inventory calls it happened to share a thread pool with. **Fix:** Made the recommendation-service call asynchronous and non-blocking relative to checkout completion (checkout succeeds regardless of whether recommendations load), added a strict timeout and circuit breaker specifically for this call, and isolated its resource pool (a separate connection/thread pool, §42.5's bulkhead pattern) so its failure cannot exhaust resources needed by the actually-critical checkout path. **Lesson:** Any dependency call embedded in a critical path must be explicitly evaluated for whether the critical path can succeed without it — if yes, that dependency must be architecturally isolated (async, timeout-bound, separately resourced) so its failure cannot cascade into the critical path's own failure, exactly the case study pattern §64 documents repeatedly across real production incidents.

### 112.4 Exercise: The Thundering Herd After Recovery

**Alert:** "Our cache cluster went down for two minutes and was restored, but immediately after recovery, our database fell over too, even though the underlying incident (the cache outage) was already resolved." **What would you check first?** Consider §64's thundering-herd-after-recovery case study and what happens to all the requests that were waiting or retrying during the cache outage once the cache becomes available again. **Investigation:** During the cache outage, every request that would normally hit the cache instead fell through to the database directly (a reasonable fallback in isolation), and a large number of clients were simultaneously retrying failed requests — when the cache came back online, all of these requests (now including retries) hit the database simultaneously attempting to both serve the request and, in many implementations, repopulate the now-empty cache, overwhelming the database with a burst far larger than normal peak load. **Root cause:** The classic thundering-herd/cache-stampede pattern (Part V §91.A) compounded by uncoordinated client retries with no backoff or jitter, meaning the recovery moment itself became a bigger spike than the original outage. **Fix:** Added request coalescing/locking so that only one request per cache-key triggers a database fetch and cache repopulation while concurrent requests for the same key wait for that single fetch's result (§39.4's stampede protection), and added jittered backoff to client retry logic so retries spread out over time rather than synchronizing. **Lesson:** The moment of recovery from an outage is often more dangerous than the outage itself, because retries and fallback traffic accumulate during the outage and then arrive simultaneously the instant the failed component returns — recovery-time load must be explicitly modeled and protected against (stampede protection, jittered retries), not assumed to be equivalent to ordinary steady-state load.

### 112.5 Engineering Intuition

> **What's the fastest way to localize an unexplained cost spike?** Always break down by dimension (service, resource type, region) before investigating any specific hypothesis (§112.1) — the aggregate number alone never points at a root cause.

> **What's the common thread across §112.3 and §112.4?** Both are failures of *isolation* — a non-critical dependency wasn't isolated from the critical path (§112.3), and recovery-time load wasn't isolated/smoothed from steady-state assumptions (§112.4) — bulkheading and stampede protection are the same underlying discipline (contain a failure's blast radius) applied to two different failure shapes.
