## 111. Production Debugging Exercises I: Latency, Availability, Data Consistency Incidents

### 111.1 Purpose: Practicing Diagnosis on Someone Else's System

§57's incident-response chapter taught the general process (detection, triage, runbooks, postmortems). This chapter and §112 apply that process to specific, realistic incidents — presented the way a real page or alert would arrive, with ambiguous initial information. Attempt to form a hypothesis and identify what you'd check first before reading the resolution.

### 111.2 Exercise: The Gradual Latency Creep

**Alert:** "p95 API latency has increased steadily over the past three weeks, from 120ms to 340ms, with no corresponding deployment or traffic-volume change." **What would you check first?** Consider §50's performance-engineering chapter's distinction between a sudden regression (usually a deployment) and a gradual one (usually a resource or data-volume trend). **Investigation:** A gradual, deployment-independent trend points toward something growing continuously in the background — table size, index bloat, connection pool saturation, or a slowly-growing working set exceeding cache capacity. Checking database query performance specifically (via `EXPLAIN`, §33) showed a specific query's execution plan had shifted from an index scan to a full table scan. **Root cause:** The table had grown past the point where the query planner's statistics (last updated during a maintenance window that had since been disabled) still favored the correct index — the query planner was working from stale statistics and choosing an increasingly poor plan as the table grew. **Fix:** Re-enabled automatic statistics updates and, as a longer-term fix, added monitoring on query-plan changes for high-traffic queries specifically. **Lesson:** A gradual latency trend with no deployment correlation should immediately point at something growing continuously (data volume, index bloat, working-set size) rather than a code-level regression — checking growth-correlated metrics (table size over time) before code diffs is the faster diagnostic path here.

### 111.3 Exercise: The Intermittent Availability Drop

**Alert:** "Every day around 2 AM, our error rate spikes to 15% for about ten minutes, then returns to normal. This has been happening for a week." **What would you check first?** Consider what else typically happens on a fixed daily schedule — batch jobs, backups, certificate renewals, log rotation. **Investigation:** Correlated the exact spike window against the full list of scheduled cron jobs/batch processes and found a nightly analytics-export job that queried the primary production database directly, running at 2 AM. **Root cause:** The analytics export ran a set of expensive, unindexed aggregate queries directly against the primary database, competing for connection-pool slots and CPU with live production traffic, causing genuine request timeouts for real users during the export's runtime — a direct instance of the "OLAP query against an OLTP database" anti-pattern §20's data-pipelines chapter warns against. **Fix:** Moved the analytics export to run against a read replica (or, better, a dedicated data warehouse populated via the batch ETL pattern from §109.4) instead of the primary, isolating analytical load from transactional load entirely. **Lesson:** A precisely time-boxed, recurring incident is almost always caused by something else that runs on the same schedule — check cron/batch job schedules before investigating application code for a bug that would need to somehow only manifest at a fixed time of day.

### 111.4 Exercise: The Split-Brain Data Inconsistency

**Alert:** "Customer support is reporting that some users see different account balances depending on which region's app server they hit, and the discrepancy doesn't resolve even after refreshing several times." **What would you check first?** Consider §36's consensus/coordination chapter and §64's split-brain case study — this symptom (two different, non-converging answers depending on which node is hit) is a strong signature of a coordination failure, not an ordinary replication-lag issue (which would show convergence within seconds, not indefinitely). **Investigation:** Checked the leader-election status (§36.4) across regions and found that a network partition between two regions several hours earlier had caused both regions to independently elect their own leader for the same data partition, and — critically — the partition healing afterward had not triggered any reconciliation process. **Root cause:** A split-brain scenario (Part V §91.C) where writes had been accepted independently by two "leaders" during the partition, and no conflict-resolution or fencing mechanism existed to detect and reconcile the divergence once connectivity was restored. **Fix:** Implemented a proper fencing mechanism (ensuring a demoted leader cannot continue accepting writes even if it doesn't yet know it's demoted, §36.5) and a reconciliation process for detecting and resolving conflicting writes accepted during a confirmed split-brain window — and added explicit monitoring/alerting on leader-election events across regions, since the original partition event itself had gone unnoticed. **Lesson:** A data inconsistency that doesn't converge over time (unlike ordinary replication lag) is a strong, specific signal of a coordination/consensus failure, not a data-layer bug — the investigation should immediately pivot to leader-election and network-partition history, not query logic.

### 111.5 Exercise: The Silent Data Loss

**Alert:** "A customer reports that an order they placed three days ago is missing from their order history entirely — no error was ever shown to them at the time." **What would you check first?** Consider the outbox pattern (§41.2, §97.9) and what happens when a write to one store succeeds but a dependent write or event publish fails silently. **Investigation:** Traced the order-creation flow and found that the order was written to the primary orders table successfully, but the subsequent, separate call to publish an "order created" event (used to populate the customer-facing order-history read model, per a CQRS-style split, §41.4) had failed due to a transient message-broker connectivity issue — and the failure was caught by a broad exception handler that logged a warning and returned success to the original write path anyway. **Root cause:** A dual-write problem — the order record existed in the source-of-truth table, but the read-model/history view (populated only via the event) never received the corresponding update, and the error-swallowing exception handler meant no alert ever fired despite a real, silent failure occurring. **Fix:** Implemented the outbox pattern properly (§41.2) — writing the order and the outbound event atomically within the same database transaction, with a separate, reliable relay process publishing outbox entries, ensuring the event is never silently lost even if the message broker is temporarily unavailable. **Lesson:** Any two writes that must both succeed together (a primary record and a derived event/read-model update) need either a single atomic transaction or the outbox pattern specifically — a broad exception handler that logs and continues on a secondary write's failure is exactly how this class of silent data loss enters production undetected.

### 111.6 Engineering Intuition

> **What's the single fastest triage question for any latency/availability incident?** "Did this start suddenly (check recent deployments) or build gradually (check growth-correlated metrics)?" — §111.2 and §111.3 demonstrate the two different investigation paths this single question immediately opens.

> **What's the tell-tale sign of a coordination/consensus failure versus an ordinary data bug?** Non-convergence — if two reads of "the same" data give different, stable (not just momentarily lagging) answers depending on which node serves the request, suspect split-brain or a leader-election failure (§111.4) before suspecting application logic.
