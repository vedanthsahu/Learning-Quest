## 107. LLD Interview Framework Worked Examples II: Parking Lot Pricing Engine, In-Memory Key-Value Store

### 107.1 "Design a Parking Lot Pricing Engine" (LLD Depth, Contrasted with §105.2's HLD Treatment)

**Distinguishing this from §105.2:** §105.2 covered the parking garage as an HLD prompt (spot assignment, data modeling, scale-appropriate infrastructure). This is the same domain asked as an LLD prompt — the interviewer wants the actual pricing *algorithm's* class design, not the surrounding system. **Core entities:** `PricingRule` (an abstraction — flat rate, hourly, tiered, event-surge pricing), `ParkingSession` (entry time, exit time, vehicle type, spot type), `PricingEngine` (applies the appropriate rule(s) to a session to compute a final charge). **Key interface:** `PricingRule.calculate(session) -> amount` — a single, narrow interface every concrete pricing rule implements, directly the **Strategy pattern** (§94), genuinely justified here (unlike §106.3's library example) because pricing rules demonstrably vary in *behavior*, not just data: flat pricing is a constant, hourly pricing is a linear function of duration, tiered pricing has non-linear breakpoints, and surge pricing depends on external, time-varying occupancy data. **Primary use case walkthrough:** A vehicle exits after 3.5 hours during a stated "surge" window → `PricingEngine` must determine which rule(s) apply (possibly *combining* a base hourly rate with a surge multiplier) — this composition of multiple rules is the design's actual core difficulty, cleanly suggesting a **Decorator pattern** (§94) layered on top of the base Strategy, so surge pricing wraps and modifies a base rule's result rather than being a separate, mutually-exclusive rule requiring its own combinatorial explosion of rule classes (flat+surge, hourly+surge, tiered+surge, etc.). **Extension point:** Adding a new pricing model (e.g., a membership-discount rule) should require adding one new class, not modifying `PricingEngine` — directly testable by asking "how would you add rule X" and checking the answer doesn't touch existing rule classes (Open/Closed, §93). **This question is testing:** recognizing when Strategy alone is insufficient (multiple rules must compose, not just be selected among) and reaching for Decorator specifically to solve *that* problem — a candidate who tries to solve rule-composition by adding conditional branches inside `PricingEngine` has reinvented what Decorator exists to avoid.

### 107.2 "Design an In-Memory Key-Value Store (a Simplified Redis Core)"

**Distinguishing this from §103.7:** §103.7 covered a distributed cache as an HLD prompt (consistent hashing, replication, cluster membership). This version asks for the single-node data structure and eviction design specifically — an LLD prompt testing data-structure fluency (companion to §31's storage-engine internals, applied to an in-memory structure rather than a disk-backed one). **Core entities:** `Store` (the main key-value interface: `get`, `put`, `delete`), an internal hash map for O(1) average-case key lookup, and an eviction-tracking structure whose choice depends entirely on the stated eviction policy. **Key design decision — eviction policy drives data structure choice (§39.2's eviction policies, now at the implementation level):** For **LRU**, the standard, interview-expected implementation combines a hash map (key → node) with a doubly-linked list (maintaining access-recency order) so that both lookup and recency-update are O(1) — a candidate should explain *why* a doubly-linked list specifically (O(1) removal of an arbitrary node, which a singly-linked list or a plain array cannot provide). For **LFU**, the structure is more subtle — a hash map from key to frequency count, plus a secondary structure (commonly a hash map of frequency → a linked list of keys at that frequency) to find and evict the minimum-frequency key in O(1) without scanning. **Key interface:** `Store.get(key)`, `Store.put(key, value, ttl=None)` — supporting an optional TTL directly connects to a background or lazy expiration mechanism (checking/removing expired keys either via a periodic sweep or lazily on access, a real, named tradeoff between memory-cleanliness and CPU overhead). **Primary use case walkthrough:** A `put` when the store is at capacity must evict according to the chosen policy *before* inserting — a candidate should walk through this exact sequence (check capacity → evict if needed → insert → update recency/frequency tracking) rather than describing the structures in isolation. **Concurrency model:** If the store must support concurrent access (a realistic follow-up question), the naive approach (a single global lock around every operation) works but serializes all access — a stronger answer discusses sharding the key space across multiple independently-locked segments (directly foreshadowing §103.7's consistent-hashing-based distributed version, but applied within a single process to reduce lock contention). **This question is testing:** data-structure fluency under a stated constraint (O(1) operations) and the ability to justify *why* a specific structure combination achieves that bound — a candidate who proposes an unordered list scanned linearly for eviction has failed the core O(1) constraint the question is built around.

### 107.3 The Pattern Across These Two Examples

Both examples in this chapter demonstrate the same LLD-specific signal: a design pattern or data structure is only "correct" relative to a *specific, stated constraint* — Decorator is correct for the pricing engine because rules must *compose*, not merely be *selected among*; the doubly-linked-list-plus-hash-map combination is correct for LRU because the constraint is O(1) *and* recency-ordering, not because it's a memorized "correct" LRU implementation. An LLD answer that names the right pattern or structure without articulating the specific constraint that makes it the right choice has produced the correct output through pattern-matching, not engineering — an important distinction interviewers are specifically trained to probe with a "why not X instead?" follow-up.

### 107.4 Engineering Intuition

> **How do I know whether a design-pattern LLD prompt wants Strategy, Decorator, or something else?** Ask whether the behaviors are *selected among* (pick exactly one — Strategy) or *composed/layered* (apply several together, in an order that matters — Decorator) — §107.1's surge-pricing-on-top-of-hourly-pricing is a composition case, directly distinguishing it from §106.3's library member-type case, which is a pure selection case.

> **Why does the in-memory key-value store emphasize the O(1) constraint so heavily?** Because the entire point of the question is testing whether a candidate can derive a data-structure combination *from* a stated performance constraint, rather than reciting "LRU uses a hash map and linked list" as a memorized fact without being able to justify why that specific combination is what the constraint requires.

> **What would over-engineering either answer look like?** Proposing a distributed, sharded, multi-node architecture (§103.7's HLD treatment) when the question explicitly asked for the single-node internals — conflating the LLD and HLD versions of the same domain is itself a signal of not having correctly identified which one is being tested (§104.4's Signal 6).
