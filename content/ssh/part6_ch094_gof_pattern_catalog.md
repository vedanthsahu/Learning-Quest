## 94. The Classic Design Pattern Catalog (Gang of Four)

### 94.1 Why This Catalog Exists Alongside §93

§93 taught the reasoning principles (SOLID, GRASP) that tell you *when* a class needs to change its structure. This chapter catalogs the specific, named, reusable *shapes* that solution commonly takes — the "Gang of Four" (GoF) patterns, so named after the authors of the 1994 book that first cataloged them. Every pattern below follows the same format: the recurring problem that motivated it, the tradeoff accepted to solve it, and where it shows up in real production code — because, per this Part's preface, the goal is recognizing these shapes by name, not deriving them from scratch every time.

### 94.2 Creational Patterns: Controlling How Objects Get Created

**Factory Method** — *Problem*: code that directly instantiates a concrete class (`new VisaPayment()`) is tightly coupled to that specific class, and adding a new payment type means editing every call site. *Solution*: delegate creation to a method that subclasses or configuration can override, returning different concrete types behind one shared interface. *Tradeoff*: adds a layer of indirection for the benefit of adding new types without touching existing call sites (directly the Open/Closed Principle, §93.2). *Production usage*: nearly every plugin or driver system (database drivers, logging backends) uses a factory to construct the correct concrete implementation from a configuration string. *Common mistake*: introducing a factory for a type that will realistically never have more than one implementation — pure, unjustified indirection.

**Abstract Factory** — *Problem*: a system needs to create *families* of related objects (a UI toolkit needing matching buttons, checkboxes, and menus for either a "dark theme" or "light theme") without hardcoding which family. *Solution*: one factory interface producing an entire related family of objects, with a concrete factory per family. *Tradeoff*: solves family-consistency at the cost of a more complex creation hierarchy than a single Factory Method. *Interview usage*: distinguishing this from plain Factory Method is a common interview probe — the tell is "does creating one object require creating a matched set of others."

**Builder** — *Problem*: a class with many optional constructor parameters (a `HttpRequest` with method, headers, body, timeout, retries) becomes unreadable and error-prone to construct directly (`new HttpRequest(null, null, true, 30, null, false, ...)`). *Solution*: a separate object that accumulates configuration step by step via named methods (`.withTimeout(30).withRetries(3).build()`) and constructs the final, immutable object only at the end. *Production usage*: virtually every modern HTTP client and configuration object in widespread libraries. *Common mistake*: using a Builder for a class with only two or three simple, always-required parameters — the pattern's value is proportional to parameter count and optionality, not applied unconditionally.

**Prototype** — *Problem*: constructing a new object is expensive (heavy initialization, an expensive database read to populate defaults), but a very similar object already exists. *Solution*: clone the existing object and modify only what differs, rather than constructing from scratch. *Tradeoff*: avoids expensive re-initialization at the cost of needing careful, correct clone semantics (especially for objects containing references to other mutable objects — a shallow-copy bug here is a classic, hard-to-spot source of shared-state corruption).

**Singleton** — *Problem*: exactly one instance of a class (a configuration object, a connection pool manager) should exist application-wide, and every part of the code should reach the same instance. *Solution*: the class controls its own instantiation, exposing a single, global access point. *Tradeoff, stated plainly*: Singleton is the most widely *over*-used GoF pattern in real practice — global, mutable shared state is difficult to test (it persists across supposedly-independent unit tests) and creates a hidden dependency invisible in any constructor signature, directly working against the Dependency Injection discipline from §93.4. *Interview usage*: a strong candidate explicitly weighs Singleton against DI-managed single-instance objects (a dependency container configured to hand out one shared instance) — the latter preserves testability that a true Singleton discards.

### 94.3 Structural Patterns: Composing Objects Into Larger Structures

**Adapter** — *Problem*: an existing class's interface doesn't match what calling code expects (a legacy `XmlPaymentGateway` needs to work with code written against a `PaymentProcessor` interface expecting JSON). *Solution*: a thin wrapper class translating calls from the expected interface into calls the existing class actually understands. *Production usage*: extremely common at integration boundaries with third-party or legacy systems — directly the object-level analogue of the API contract translation discussed in §4.5.

**Facade** — *Problem*: a subsystem has many classes and a complex interaction sequence, and most callers only need a small, common subset of that complexity. *Solution*: one simplified interface hiding the subsystem's internal complexity behind a small number of high-level methods. *Tradeoff*: simplifies the common case at the cost of the facade itself becoming a dependency every caller now shares — a well-designed facade doesn't prevent callers who genuinely need the full subsystem's power from bypassing it.

**Proxy** — *Problem*: you need to control or augment access to an object — deferring expensive creation until first use, checking permissions before allowing a call through, or transparently making a remote call look local. *Solution*: a stand-in object implementing the same interface as the real object, adding its specific behavior (lazy loading, access control, remote-call marshaling) before or after delegating to the real one. *Production usage*: ORM "lazy-loaded" relationships (§33.6's N+1 problem is frequently caused by exactly this kind of proxy silently triggering unexpected queries) and RPC client stubs (§29.4's gRPC-generated client code is, structurally, a proxy).

**Bridge** — *Problem*: an abstraction (a `Shape`) and its implementation (how it's actually rendered — vector graphics versus raster) both need to vary independently, and inheritance alone would force an explosion of combined subclasses (`VectorCircle`, `RasterCircle`, `VectorSquare`, `RasterSquare`, ...). *Solution*: separate the abstraction and implementation into two independent class hierarchies, connected by composition rather than inheritance — directly §93.6's "favor composition" principle applied to exactly the scenario that motivates it.

**Composite** — *Problem*: client code needs to treat a single object and a group of objects uniformly (a file and a folder containing files, both needing a `getSize()` method that "just works" recursively). *Solution*: a shared interface implemented by both leaf objects and container objects, where containers delegate the operation to their children. *Production usage*: virtually every UI framework's view hierarchy (a `Button` and a `Panel` containing buttons both implement `render()`) and filesystem-like data structures.

**Decorator** — *Problem*: you need to add behavior to an individual object dynamically (add compression, then encryption, to a specific file stream) without subclassing every possible combination (`CompressedStream`, `EncryptedStream`, `CompressedEncryptedStream`, ...). *Solution*: wrapper objects implementing the same interface as the object they wrap, each adding one specific behavior and delegating the rest — layers can be composed and stacked in any order at runtime. *Production usage*: Java's `InputStream` wrapping chain (`BufferedInputStream(GZIPInputStream(FileInputStream(...)))`) is the canonical, widely-recognized real-world example.

### 94.4 Behavioral Patterns: Governing How Objects Interact and Communicate

**Strategy** — *Problem*: an algorithm needs to vary independently of the code that uses it (different sorting comparators, different pricing rules for different customer tiers), and hardcoding the choice with `if/else` violates Open/Closed (§93.2). *Solution*: encapsulate each algorithm variant behind a shared interface, and inject (§93.4) the desired variant into the client at runtime. *Production usage*: virtually every "pluggable algorithm" parameter in a standard library (a custom comparator passed to a sort function is a Strategy object). *Interview usage*: Strategy is very frequently confused with State (§94.4 below) — the distinguishing question is whether the object *chooses* its own behavior based on internal condition (State) or is *handed* a behavior externally by client code (Strategy).

**Observer** — *Problem*: one object's state change needs to notify an unknown, potentially-changing number of other interested objects, without the first object needing to know who they are in advance. *Solution*: subjects maintain a list of observers and notify all of them on a state change; observers register and unregister interest without the subject needing any compile-time knowledge of them. *This is the direct, foundational, single-process ancestor of the Publish-Subscribe messaging pattern* covered at network/systems scale in §97 — the same problem (a publisher shouldn't need to know its subscribers in advance) reappearing at every scale this handbook has covered, from one process's objects (here) to a distributed message broker (§40, §97).

**Command** — *Problem*: an action needs to be represented as an object itself — so it can be queued, logged, undone, or passed around as data rather than executed immediately inline. *Solution*: encapsulate a request (and everything needed to execute it later) as an object implementing a common `execute()` interface. *Production usage*: undo/redo stacks in editing applications, and — at systems scale — every message sitting in a queue (§11, §40) is, structurally, a Command object: a serialized representation of "do this," decoupled from immediate execution.

**State** — *Problem*: an object's behavior needs to change based on its internal state (an `Order` behaves differently when `Pending` versus `Shipped` versus `Cancelled`), and representing this with scattered `if (status == "shipped")` checks throughout the class becomes unmanageable as states and transitions grow. *Solution*: encapsulate each state as its own object implementing a shared interface, with the containing object delegating behavior to its current state object and explicitly managing transitions between them.

**Template Method** — *Problem*: several related algorithms share the same overall sequence of steps but differ in one or two specific steps (every data-import job reads a file, validates it, transforms it, and saves it — but the validation and transformation logic differs per format). *Solution*: define the invariant skeleton in a base class method, with the varying steps implemented as overridable methods subclasses provide. *Tradeoff*: this pattern relies on inheritance, and per §93.6's general preference for composition, Strategy is often chosen instead for the same problem when the varying pieces can be cleanly extracted as injectable objects rather than overridden methods.

**Chain of Responsibility** — *Problem*: a request may need to be handled by one of several possible handlers, but the sender shouldn't need to know in advance which one, and multiple handlers may need a chance to inspect or act on it in sequence. *Solution*: link handlers into a chain, each deciding whether to process the request, pass it along, or both. *Production usage*: HTTP middleware/filter chains (an authentication check, then a logging step, then the actual request handler) in almost every web framework are a direct, widely-recognized instance of this pattern.

**Mediator** — *Problem*: many objects need to communicate with each other, and letting each one hold direct references to all the others produces a tangled, tightly-coupled web where any object's change risks breaking many others (directly the opposite of GRASP's Low Coupling principle, §93.3). *Solution*: introduce a single mediator object that all the others communicate through, so individual objects only need to know about the mediator, not each other. *Production usage*: a chat room server coordinating messages between many connected clients, none of whom talk to each other directly, is a canonical Mediator.

**Visitor** — *Problem*: you need to add a new operation across a whole family of related classes (computing tax for every kind of `Product` subclass) without modifying each class's own source code every time a new operation is needed. *Solution*: define a `Visitor` interface with one method per class in the family, and have each class accept a visitor, calling back the method appropriate to its own type — new operations become new Visitor implementations, not edits to the existing class hierarchy. *Common mistake*: reaching for Visitor when the class family itself is still actively growing — Visitor makes adding new *operations* easy at the cost of making adding new *classes in the family* harder, the exact inverse tradeoff of ordinary polymorphism, and choosing it in the wrong direction of that tradeoff is a frequent, avoidable mistake.

### 94.5 Engineering Intuition for This Catalog as a Whole

> **How do I know which pattern applies to a given problem, in an interview, under time pressure?** Name the *problem* first, out loud, in your own words, before reaching for a pattern name — "I need to add behavior to individual objects at runtime without a subclass explosion" leads you to Decorator far more reliably than trying to pattern-match a name to a vague problem statement.
>
> **What is the single most common LLD interview mistake with this catalog?** Reaching for a named pattern because it sounds sophisticated, rather than because the specific problem it solves is actually present — precisely the anti-pattern this entire handbook has warned against since §1.5, now recurring one final time at the level of individual classes.
>
> **What would a senior engineer's answer sound like, differently from a junior one?** A senior engineer names the tradeoff being accepted (Decorator's runtime flexibility versus a harder-to-follow call chain; Singleton's convenience versus its cost to testability) — not just the pattern's name and mechanism.
