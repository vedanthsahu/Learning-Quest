## 121. Hands-On Engineering Labs II: Systems and Distributed Practice

### 121.1 How This Chapter Extends §120

§120's labs were largely single-process — a data structure, an in-memory pattern. This chapter's eight labs require simulating multiple independent nodes/processes (even if all run on your own machine as separate processes or threads communicating over local sockets/queues) — the goal is direct, hands-on exposure to the coordination and failure problems Part III's "at scale" chapters describe, at a small enough scale to build and debug yourself in hours, not months.

### 121.2 Lab: Leader Election Simulation

**Problem:** Simulate 3-5 independent processes that elect one leader among themselves, with automatic re-election if the current leader stops responding. **Acceptance criteria:** (1) Exactly one leader is elected at any given time under normal operation; (2) if the leader process is killed, the remaining processes detect this (via a heartbeat/timeout mechanism, not an external signal) and elect a new leader within a bounded time; (3) if two processes' leadership claims race, the system resolves to exactly one leader, not zero or two; (4) you can demonstrate acceptance criterion 3 by deliberately introducing a race (e.g., pausing one process briefly during an election). **Hints:** §36.4's leader-election mechanics; you do not need to implement full Raft/Paxos — a simplified bully algorithm or lease-based approach is sufficient to learn the core problem. **Done when:** you've caused and correctly resolved a simulated split-vote scenario, not just the clean, no-contention case.

### 121.3 Lab: Distributed Lock With Lease and Fencing

**Problem:** Implement a lock coordinated via a shared store (a real Redis instance, or a simple in-memory server simulating one) that multiple independent processes can contend for, with a time-bound lease so a crashed lock-holder doesn't block others forever. **Acceptance criteria:** (1) Only one process holds the lock at a time under normal contention; (2) if the lock holder crashes without releasing, the lease expires and another process can acquire it after the lease timeout, not before; (3) implement fencing — a process that acquired the lock, then experienced a long pause (simulating a GC pause or network delay) past its lease expiry, must be prevented from taking actions as if it still held the lock once it resumes (§111.4's split-brain lesson, applied at the lock level, directly the "fencing" concept named in that case study). **Hints:** §36.5, §105.4's job-scheduler lease discussion. **Done when:** you've specifically demonstrated acceptance criterion 3 — a "zombie" holder that thinks it still has the lock being correctly rejected when it tries to act.

### 121.4 Lab: Cache Stampede Simulation and Fix

**Problem:** Simulate a cache-aside setup where many concurrent requests for the same key arrive simultaneously against a cold (or just-expired) cache entry, and fix the resulting stampede. **Acceptance criteria:** (1) First, demonstrate the problem without protection — measure how many redundant backend calls occur for N concurrent requests to the same missing key (it should be close to N); (2) implement request coalescing (only the first request triggers the backend fetch; concurrent requests for the same key wait for that result) and re-measure — redundant backend calls for the same scenario should drop to 1; (3) additionally implement jittered TTL (slightly randomizing expiry per entry) and demonstrate it reduces simultaneous mass-expiry across many keys set at the same time. **Hints:** §39.4, §112.4's exact thundering-herd-after-recovery case study. **Done when:** you have both the "before" and "after" measured numbers from acceptance criteria 1 and 2, not just an implementation you believe should work.

### 121.5 Lab: Saga Orchestrator With Compensation

**Problem:** Implement a saga (§41.5) coordinating a simulated multi-step order flow: reserve inventory → charge payment → confirm order, where any step can fail and must trigger compensating actions undoing the already-completed steps. **Acceptance criteria:** (1) The happy path completes all three steps in order; (2) a failure at the payment step correctly triggers compensation for the inventory-reservation step (releasing the reserved inventory), not just halting; (3) a failure at the confirm-order step correctly triggers compensation for both prior steps in the correct reverse order; (4) each step and each compensation is logged/observable so you can verify the exact sequence that occurred. **Hints:** §105.5's payment-system saga discussion, §41.5's general mechanics. **Done when:** you can point to a log/trace of a failure scenario and confirm the compensating actions ran in the correct reverse order, not just that the system ended in a consistent state by coincidence.

### 121.6 Lab: Multi-Algorithm Load Balancer With Health Checks

**Problem:** Implement a load balancer in front of 3-5 simulated backend servers (simple HTTP servers you also write, with configurable artificial latency and an on/off "healthy" switch), supporting round-robin, least-connections, and a health check that removes unhealthy backends from rotation. **Acceptance criteria:** (1) Round-robin distributes requests evenly across healthy backends; (2) least-connections correctly routes more traffic to a backend once you simulate uneven per-backend processing time and confirm it converges to more even completion times than round-robin does in the same scenario; (3) marking a backend unhealthy removes it from rotation within one health-check interval, and requests are no longer routed to it; (4) restoring health returns it to rotation. **Hints:** §28.3-28.5 directly. **Done when:** you have a side-by-side measured comparison (not just an assertion) of round-robin versus least-connections' request-distribution evenness under the same heterogeneous-latency backend scenario.

### 121.7 Lab: Idempotent Payment Endpoint

**Problem:** Implement a simulated payment-charging endpoint that accepts an idempotency key with each request and guarantees that retried requests with the same key never result in a duplicate charge. **Acceptance criteria:** (1) A first request with a given idempotency key processes and charges normally; (2) a retried request with the *same* key returns the original result without charging again, even if the retry arrives concurrently with the original request still in flight (not just after it completes); (3) a request with a *different* idempotency key for the same logical payment is correctly treated as a separate charge (the key, not the payment content, is the deduplication mechanism); (4) the idempotency-key record itself expires after a reasonable window, not stored forever. **Hints:** §105.5, §110.2's exact payment-retry case study — pay particular attention to acceptance criterion 2, which requires handling a genuine race (two requests with the same key arriving nearly simultaneously), not just sequential retries. **Done when:** a test using concurrent (not sequential) requests with the same idempotency key demonstrates exactly one charge occurring.

### 121.8 Lab: Simulated Network Partition and Split-Brain Observation

**Problem:** Build a toy replicated key-value store across 3 simulated nodes with a simple leader-based replication scheme, then deliberately simulate a network partition (block communication between a subset of nodes) and observe the resulting behavior. **Acceptance criteria:** (1) Under normal operation, writes to the leader replicate to followers and reads from any node eventually converge; (2) simulate a partition isolating the leader from a majority of other nodes — observe and document what actually happens (does a new leader get elected among the majority side? does the isolated original leader keep accepting writes it believes are valid?); (3) after healing the partition, document what your implementation does with any writes accepted independently by both sides during the partition — does it detect the conflict, silently pick one side, or corrupt data silently? (4) write up, in your own words, what a production-grade fix (fencing, quorum writes, §111.4) would need to add that your toy implementation doesn't have. **Hints:** §37, §64's split-brain case study, §111.4's diagnostic exercise. **Done when:** you have an honest, specific written answer to acceptance criterion 3 — this lab is as much about observing your own implementation's actual (likely flawed) behavior as it is about building something production-ready.

### 121.9 Lab: Distributed Rate Limiter With a Shared Store

**Problem:** Extend §120.2's single-process token-bucket rate limiter to work correctly across multiple independent application server instances sharing one backing store (a real Redis instance is the natural choice here). **Acceptance criteria:** (1) The rate limit is enforced correctly in aggregate across all instances, not per-instance (a client shouldn't be able to get N times the limit by hitting N different instances); (2) the check-and-decrement operation against the shared store is atomic (no race condition where two near-simultaneous requests both read "1 token left" and both proceed); (3) the solution correctly handles the shared store being briefly unavailable (decide and justify: fail open, allowing requests through, or fail closed, rejecting them — §103.4's distributed rate-limiting discussion). **Hints:** §60.2, §103.4 directly. **Done when:** you can demonstrate acceptance criterion 2 specifically with a concurrency test that would have exposed a naive read-then-write race if you'd implemented it that way.

### 121.10 Engineering Intuition

> **Why do so many of these labs ask for a "before and after" measurement rather than just an implementation?** Because the actual engineering skill being built is recognizing and quantifying the problem before fixing it (§121.4, §121.6) — an implementation that "should" fix a problem you never measured is exactly the untested-assumption pattern §113 and §114's case studies repeatedly identify as a root cause.
>
> **What should I do once I've completed a lab?** Write a short note (2-3 sentences) on what surprised you or what you got wrong on your first attempt — this is the closest thing to a personal postmortem (§57.6, §116.4) and is often more valuable than the working code itself.
