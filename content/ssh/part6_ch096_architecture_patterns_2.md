## 96. Software Architecture Patterns Catalog, Part 2: Event-Driven and Specialized Styles

### 96.1 Event-Driven Architecture (EDA), Named Explicitly

§11.5 and §41 already derived, from first principles, why announcing "this happened" and letting independent consumers react is more decoupled than direct service calls. **Event-Driven Architecture** is the industry name for building a system's *core* structure around this idea, not merely using it for a few background operations. **Structure**: services communicate primarily by publishing and consuming events through a broker (§97), rather than calling each other's APIs directly. **Advantages**: maximal decoupling (a producer never needs to know what, if anything, consumes its events, §11.5) and natural resilience to a single consumer's downtime (§11.3). **Disadvantages**: harder to trace a single business transaction's full path (directly motivating distributed tracing, §48.4, as near-mandatory infrastructure for EDA specifically) and harder to reason about system-wide invariants, since no single service holds a synchronous, complete view of a multi-step process. **When to use**: Loop's own Stage 87 transition (§87.3) to event-driven feed updates is a worked example — adopted specifically once synchronous coupling caused measured cascading-failure risk, not by default. **Real-world examples**: Amazon's internal service architecture is frequently cited as heavily event-driven, specifically to allow thousands of independent teams' services to evolve without direct, synchronous dependencies on each other.

### 96.2 Serverless Architecture

§43.2 covered serverless as a compute option. As a whole-*architecture* style (not just one compute choice among several), **serverless architecture** commits to building a system entirely from managed, event-triggered functions and fully-managed backing services (a managed database, a managed queue), with no application server the team operates directly at all. **Advantages**: near-zero idle infrastructure cost (pay only for actual invocations) and no server patching/capacity-planning burden. **Disadvantages**: cold starts (§89.3, Part V §91.E) affecting latency-sensitive paths, and a real risk of vendor lock-in, since serverless architectures often lean heavily on a specific cloud provider's proprietary event-triggering and managed-service ecosystem. **When to use**: genuinely spiky, low-average-utilization workloads (§43.2) — exactly the profile that makes serverless's pay-per-invocation model favorable. **Failure mode**: a latency-critical, consistently-loaded path built entirely on serverless, discovering cold starts are an unacceptable, recurring tax exactly as §89.3 encountered for authentication and addressed via edge compute instead.

### 96.3 Service Mesh and API Gateway, as Architectural Roles

Both mechanisms were already covered in full (§42.2-42.3, §45.6, §67.3) — included here to name their *architectural role* explicitly: the **API Gateway** is the architecture's single external front door (north-south traffic, entering from outside), while the **Service Mesh** governs internal, service-to-service traffic (east-west traffic, between services). A common interview distinction: "north-south versus east-west" is the standard industry shorthand for exactly this boundary, worth recognizing even though the underlying mechanisms were derived from first principles many chapters ago.

### 96.4 Backend For Frontend (BFF)

**Problem it answers**: a single, general-purpose API serving both a data-hungry web client and a bandwidth-constrained mobile client forces an uncomfortable compromise — either over-fetching for mobile or under-serving web, precisely the tension GraphQL (§29.5) was one answer to. **Solution**: a distinct, thin backend service per client type (a web BFF, a mobile BFF), each shaped specifically around its own client's needs, sitting in front of the shared, general-purpose backend services. **Tradeoff**: solves the per-client-shape problem without GraphQL's added query-complexity risk (§29.5), at the cost of maintaining multiple, client-specific backend services rather than one shared API. **When to use**: a small number of meaningfully different client types with genuinely different data-shape needs; unnecessary overhead for a single client type.

### 96.5 Strangler Fig Pattern

**Problem it answers**: migrating a large, risky legacy monolith to a new architecture in one "big bang" rewrite is exactly the high-risk, all-or-nothing cutover this handbook has warned against since §46.4's canary-deployment reasoning — a rewrite that goes wrong risks replacing a working (if imperfect) system with a broken one, all at once. **Solution**: incrementally route specific pieces of functionality from the legacy system to new, replacement services one at a time — named after the strangler fig vine, which gradually grows around and eventually replaces its host tree without ever fully uprooting it during the transition. **Advantages**: each incremental piece is a small, contained, individually-reversible risk rather than one enormous bet. **Real-world examples**: widely cited as the standard, recommended approach for large enterprise legacy modernization efforts, specifically because it lets a team validate each extracted piece against real production traffic before the next piece is attempted.

### 96.6 Pipe-and-Filter Architecture

**Problem it answers**: a complex data transformation needs to be broken into a sequence of independent, reusable, composable processing steps, where each step's output feeds directly into the next. **Solution**: a series of independent "filters," each performing one transformation, connected by "pipes" carrying data between them — directly the conceptual shape underlying Unix command-line pipelines and, at systems scale, the map/reduce and stream-processing pipeline architectures already developed in §53. **Advantages**: individual filters are independently testable and reusable across different pipelines. **Disadvantages**: overall pipeline latency is the sum of every stage (directly connecting to §73.4's latency-budget reasoning, now applied to a pipeline rather than a service call tree).

### 96.7 Broker Pattern

**Problem it answers**: distributed components need to communicate without each one holding direct knowledge of every other component's location or availability. **Solution**: a broker component mediates all requests, handling routing, marshaling, and often failure masking, so clients only need to know how to reach the broker, not every individual service. This is the generalized architectural pattern underlying both the message broker infrastructure from §40 and, more broadly, service discovery mechanisms in general.

### 96.8 Actor Model

**Problem it answers**: §26's concurrency chapter showed that shared-memory concurrency (locks, atomics) is difficult to reason about correctly at scale. **Solution**: model a concurrent system as many independent "actors," each with private, unshared internal state, communicating exclusively via asynchronous messages — no actor ever directly reads or writes another's memory, sidestepping shared-memory hazards (§26.2) entirely by construction, in the same spirit as the event-loop's single-threaded avoidance of shared-memory races (§26.6), but now generalized to many independent, concurrently-running actors rather than one single-threaded loop. **Real-world examples**: Erlang/Elixir's telecom-grade concurrency model and Akka (JVM) are the most widely-cited production implementations, both prized specifically for fault isolation — one actor crashing doesn't corrupt another's state, directly a language-level instance of the bulkhead principle (§42.4).

### 96.9 Peer-to-Peer (P2P) Architecture

**Problem it answers**: a pure client-server model concentrates all serving capacity and availability risk in the server; P2P instead distributes both data and serving responsibility across many equal participants ("peers"), with no centralized server as a single point of failure or bottleneck. **Tradeoff**: eliminates the central bottleneck at the cost of much harder consistency and coordination (every one of Part II's distributed-systems chapters, §36-38, applies with full force and no simplifying "one authoritative server" assumption to lean on). **Real-world examples**: BitTorrent (file distribution) and blockchain networks (distributed ledger consensus, directly requiring the consensus mechanisms from §36) are the most widely-cited real applications.

### 96.10 Blackboard Architecture

**Problem it answers**: a problem requires several independent, specialized reasoning components (in classic AI systems: a speech recognizer, a language parser, a semantic interpreter) to collaborate on a shared, evolving partial solution without any single component knowing the full solution path in advance. **Solution**: a shared data structure (the "blackboard") that all components read from and write incremental contributions to, with a controller deciding which component acts next based on the blackboard's current state. **Modern relevance**: less common in ordinary web/backend systems, but directly recognizable in modern multi-agent AI systems (§22.6, §55.6) where several specialized model calls or tools contribute incrementally to a shared context before a final answer is produced — the same architectural shape, decades apart.

### 96.11 Cell-Based Architecture

**Problem it answers**: at hyperscale, even careful bulkheading within one region (§42.4, §74.2) can still allow a large-blast-radius incident, since all customers within that region typically share the same underlying infrastructure. **Solution**: partition the entire system — infrastructure, data, and traffic — into many independent, identical "cells," each serving a fixed subset of customers with zero shared infrastructure or failure domain with any other cell, so a single cell's complete failure only ever affects its own, deliberately bounded customer subset. **Direct connection**: this is blast-radius reduction (Part V, §91.A) taken to its logical extreme — an entire deployable, independently-failing unit of the whole system, not just a resource pool (bulkhead, §42.4) or an availability zone (§86.3). **Real-world examples**: AWS explicitly documents cell-based architecture as a core resilience strategy for several of its largest, most critical services.

### 96.12 Space-Based Architecture

**Problem it answers**: a traditional architecture's central database is frequently the hardest component to scale horizontally (§18.4's statelessness argument doesn't apply directly to the data tier itself), becoming the ultimate bottleneck under extreme load. **Solution**: eliminate the central database from the request-serving hot path entirely — processing units hold data in-memory, replicated and partitioned across the processing fleet itself (a distributed, in-memory "tuple space"), with durable storage updated asynchronously in the background rather than synchronously on the request path. **Tradeoff**: extreme horizontal scalability for the hot path, at the cost of the same eventual-consistency and durability-window tradeoffs already developed in §34.3 (write-behind, essentially) and §37.5, now applied to the entire primary data tier rather than a cache layer. **When to use**: extreme-throughput, bursty workloads (a ticket-sale flash event) where even a well-cached, well-sharded traditional database architecture would still bottleneck under the specific, extreme peak load.

### 96.13 Engineering Intuition for This Catalog

> **How do I know whether a system is "really" event-driven, or just uses a queue for a couple of background jobs?** Ask whether the *core* request flow depends on events as the primary coordination mechanism (EDA, §96.1) or whether events are used only for a small number of clearly-secondary, non-blocking side effects (§11.2's original, narrower motivation) — both are legitimate, but only the former earns the "event-driven architecture" label.
>
> **When is Cell-Based Architecture (§96.11) justified over "ordinary" multi-AZ/multi-region redundancy (§74.2)?** Once the blast radius of a shared-infrastructure failure within one region, even with good bulkheading, is still judged unacceptably large for the specific business's risk tolerance — a bar only a small number of the largest, most critical systems in the industry actually clear.
>
> **What's the tell that Space-Based Architecture is being over-applied?** It's proposed for a workload that a well-sharded, well-cached traditional database (§8, §35, §65) could already handle — Space-Based Architecture's added complexity is justified specifically by extreme, bursty throughput that traditional approaches genuinely cannot absorb, not as a default "fast" architecture.
