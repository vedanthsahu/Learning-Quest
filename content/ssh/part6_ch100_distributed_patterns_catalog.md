## 100. Distributed Systems Patterns Catalog

### 100.1 Previously Covered, Named for Catalog Completeness

**Leader Election, Quorum, Consensus, Raft, Paxos, Lease, Epoch, Lamport Clock, Vector Clock, CRDT** — all given full encyclopedia treatment in Part V, §91.C, with mechanism-level depth in §36-38. **Distributed Locking** deserves one additional, explicit warning beyond its implicit coverage so far: a distributed lock (commonly implemented via a coordination service like the ones in §64.2, or via a quorum-based scheme like Redlock) is subject to exactly the same lease-expiry hazard already flagged for leases generally (Part V, §91.C) — a lock holder that pauses for longer than the lock's lease (a long garbage-collection pause being the classic, real-world cause) can continue believing it holds the lock and proceed to act after another process has, correctly, already taken over — a well-documented, genuinely controversial failure mode in real distributed locking implementations, and the single most important thing to say about this pattern in an interview beyond simply naming it.

### 100.2 Gossip Protocol

**Problem it answers**: in a large cluster, having every node communicate directly with every other node to stay informed about cluster membership and state (an all-to-all communication pattern) doesn't scale — the number of connections grows quadratically with cluster size. A centralized coordinator (§64.2's Chubby/ZooKeeper model) solves this but becomes its own bottleneck and single point of failure at sufficiently large scale. **Solution**: each node periodically shares its known state with a small, randomly-chosen subset of other nodes, who in turn share with their own random subsets — information propagates through the cluster exponentially fast (much like a rumor spreading through a population, the pattern's namesake) without any node needing to communicate with every other node directly, and without any centralized coordinator at all. **Tradeoff**: gossip protocols are highly scalable and have no single point of failure, but information propagation is probabilistic and eventually consistent (§37.5) rather than immediate or guaranteed — appropriate for cluster membership and health information (where eventual, "good enough soon" convergence is acceptable) and not appropriate for anything requiring immediate, strong consistency. **Real-world examples**: Amazon's Dynamo (§34.9) and Cassandra both use gossip for cluster membership and failure detection.

### 100.3 SWIM Protocol

**Problem it answers**: a naive gossip-based failure detector (§100.4) that simply has nodes report "node X seems dead" based on their own direct observation can produce false positives under load (a node that's merely slow, not dead, per §9.2's fundamental ambiguity) and can be slow to converge on an accurate cluster-wide view. **Solution**: **SWIM (Scalable Weakly-consistent Infection-style process group Membership)** structures failure detection explicitly: nodes periodically ping a randomly-chosen peer directly; if that peer doesn't respond, the pinging node asks several *other* nodes to try reaching it indirectly (an "indirect probe") before declaring it suspected, specifically to distinguish "that one specific network path is briefly bad" from "that node is genuinely unreachable" — and suspected (not yet fully declared dead) status is itself gossiped through the cluster, giving the suspected node a window to refute the suspicion before being fully marked as failed. **Direct connection**: this is the concrete, named, production-grade mechanism for exactly the "distinguish slow from dead" problem §9.2 identified as fundamentally hard — SWIM doesn't solve that impossibility, it manages it as gracefully and quickly as the theory allows.

### 100.4 Failure Detectors (Phi Accrual)

**Problem it answers**: a naive failure detector using a fixed timeout (§28.5's health check timeout, generalized) forces an awkward choice: a short timeout produces false positives during ordinary, brief network jitter; a long timeout delays genuine failure detection unacceptably. **Solution**: a **phi accrual failure detector** doesn't produce a simple binary "alive or dead" — it continuously outputs a suspicion *level* (phi), calculated from the actual, historically-observed distribution of heartbeat arrival times for that specific node, such that the same absolute delay is judged more or less suspicious depending on that node's own normal jitter pattern. **Advantage over a fixed timeout**: adapts automatically to each node's own typical network behavior rather than applying one blanket threshold to every node regardless of its normal variance — directly addressing the same tension §28.5 raised about health checks that are either too strict or too lenient, now solved with a continuous, adaptive signal instead of a single fixed number.

### 100.5 Read Repair, Hinted Handoff, and Anti-Entropy

Three related mechanisms, all addressing the same underlying problem: in a quorum-based, eventually-consistent replicated system (§34.5, §37.5), replicas can drift apart, and something must eventually bring them back into agreement without requiring a full, disruptive resync.

**Read Repair** — *Problem*: a read quorum (§34.5) may discover that different replicas returned different (stale versus current) values for the same key. *Solution*: rather than simply returning the most recent value and moving on, the coordinating node also writes that corrected value back to whichever replica(s) returned the stale one — repairing the inconsistency as a natural byproduct of an ordinary read, spreading the cost of convergence across normal traffic rather than requiring a dedicated repair process.

**Hinted Handoff** — *Problem*: in a system designed to remain available even when a replica is temporarily unreachable (favoring A over C in CAP terms, §38.3), a write intended for that unreachable replica cannot simply be dropped. *Solution*: another, reachable node temporarily accepts and stores the write on the unreachable replica's behalf (a "hint"), and forwards it to the original replica once it comes back online — directly extending the availability-favoring choice from §38.3 with a concrete mechanism for not permanently losing writes made during the outage window.

**Anti-Entropy** — *Problem*: Read Repair (above) only corrects inconsistencies for keys that happen to be read; keys that are rarely or never read after going stale would drift permanently without some other mechanism. *Solution*: a background process that periodically compares replicas' entire datasets (efficiently, via Merkle trees, §100.6) and proactively reconciles any differences found, regardless of whether those specific keys have been read recently — the systematic, comprehensive complement to Read Repair's opportunistic, read-triggered correction.

### 100.6 Merkle Trees

**Problem it answers**: Anti-Entropy (§100.5) needs to efficiently determine *which specific keys* differ between two large replicas without comparing every single key's value directly, which would be prohibitively slow for large datasets. **Solution**: a **Merkle tree** is a hash tree where each leaf node is a hash of a data block, and each non-leaf node is a hash of its children's hashes, all the way up to a single root hash summarizing the entire dataset. Two replicas can first compare only their root hashes — if identical, the entire datasets are guaranteed identical, and no further comparison is needed at all. If the root hashes differ, only then do the replicas descend into the tree, comparing child hashes level by level, quickly narrowing down to the *specific* small subset of leaf blocks that actually differ, without ever needing to compare the bulk of identical data directly. **Real-world examples**: used extensively in Dynamo-style databases (§34.9) for anti-entropy, and independently, in Git's own internal object model and in blockchain systems for efficiently verifying data integrity.

### 100.7 Split-Brain Recovery

Part V (§91.C) defined split-brain and named epoch/term-based fencing as the *prevention* mechanism. **Recovery** — what to do once a split-brain has already occurred and produced two divergent sets of writes — is a distinct, harder problem: the two divergent branches of data must be reconciled, typically via one of three approaches: **last-writer-wins** (simplest, but silently discards one side's writes entirely, acceptable only when that data loss is genuinely tolerable); **manual/application-level reconciliation** (surfacing the conflict for a human or business-logic-specific resolution, appropriate when silent data loss is not acceptable); or, where the affected data type permits it, **CRDT-based automatic merging** (§37.4, Part V §91.C) — recognizing which of these three is appropriate for a given dataset is precisely the same per-dataset consistency judgment call this handbook has emphasized since §38.5, now applied specifically to the cleanup phase after a split-brain incident rather than to steady-state operation.

### 100.8 Engineering Intuition

> **How do I know if I need Gossip/SWIM instead of a centralized coordinator (§64.2) for cluster membership?** Gossip-based approaches scale better and avoid a single point of failure, but trade away strong, immediate consistency of membership view — appropriate once cluster size makes a centralized coordinator's connection/request load itself become a bottleneck, per §100.2.
>
> **How do I know if I need Read Repair, Hinted Handoff, or full Anti-Entropy, or all three?** These aren't mutually exclusive alternatives — real Dynamo-style systems typically run all three together: Read Repair for opportunistic, low-cost correction; Hinted Handoff for temporary unavailability; Anti-Entropy with Merkle trees as the systematic backstop catching everything the other two miss.
>
> **What's the single most important caveat to state about distributed locking (§100.1) in an interview?** That a lock's safety depends on bounded process pause/clock behavior, and a sufficiently long GC pause or clock skew can violate that assumption — stating this caveat unprompted is a strong, specific signal of genuine distributed-systems fluency.
