@@ A1 | Understanding requirements
A newsletter platform generates personalized weekly digests for 80,000 subscribers. Digests are produced on Sunday for Monday-morning delivery, and the budget is tight. Which approach best fits?
+ Generate them with Message Batches on Sunday and queue the emails
- Generate each digest synchronously at send time on Monday morning, streaming them out to subscribers as they finish

> There is a time window but no real-time need, and cost matters: that is the Batch API's sweet spot, about 50% cheaper and asynchronous. @@ A12 | Claude application design

@@ M4 | Technical fundamentals
A team's app adds or removes tools on every request depending on the user's page, and builds the tool list from an unordered set. Cache hit rates are near zero even though the system prompt is identical. Why?
+ Tools come first in the prefix, so any change to their set or order invalidates everything after them
- The system prompt must come before tools for caching to work
- Caching doesn't support tool definitions, so any request that includes tools is never cached at all

> The cache prefix order is tools → system → messages. Changing the tool set, or nondeterministic ordering, changes the start of the prefix and causes a miss on everything. Keep tool lists stable and deterministically ordered, and gate tool *use* with `tool_choice` or instructions instead.

@@ S2 | Guardrails and safe deployment
An app lets Claude run user-requested Python through a client-side code-execution tool on the company's own servers. What is the most important safeguard?
+ An isolated sandbox (container or VM) with no secrets, restricted network and filesystem, and resource limits
- Ask Claude to write only safe code
- Run it directly on the application server for speed, relying on the existing firewall and access controls to contain it
- Allow only code shorter than 100 lines, which keeps any damage it can do small and easy to review
> Executing model-written code needs real isolation. Prompt instructions and length limits aren't containment. Running directly on the app server exposes secrets and infrastructure.

@@ S3 | Claude hooks for guardrails
A team wants Claude Code to be unable to end its turn while the test suite is failing, so that Claude keeps working until the tests pass. Which hook fits?
+ A `Stop` hook that runs tests and blocks stopping on failure
- A `SessionStart` hook that runs the whole test suite once when each new session begins
- A `UserPromptSubmit` hook that reminds Claude about the tests before it starts every task
- A line in `CLAUDE.md` asking Claude to always run the tests before it finishes any change
> `Stop` hooks run when Claude tries to finish and can block, sending the reason back so Claude continues. That is deterministic enforcement. CLAUDE.md is advisory, and the other events fire at the wrong time.

@@ S4 | Identity, secrets, and key management
An external contractor team needs Claude API access for one project only, with a hard spending cap and no visibility into other projects' usage or keys. What is the best setup?
+ A separate workspace for the project with its own keys and spend limits, revoked when the work ends
- Share the organization's main production key with the contractors
- Give the contractors Console admin access so they can create and manage their own keys and limits directly
- Share a key and ask the contractors to self-report usage
> Workspaces partition keys, limits and spend inside an organization, which gives least privilege and a clean revocation path. Sharing production keys or granting admin access widens the blast radius, and self-reporting isn't a control.

@@ C1 | Session management
Before letting Claude Code change anything, a developer wants it to explore the codebase and propose a detailed implementation plan for review, with no file edits or commands that modify state. Which feature fits?
+ Plan mode
- `/clear`, followed by a request not to edit anything
- `bypassPermissions` mode, so planning isn't interrupted by prompts
- A `PostToolUse` hook that undoes any edits Claude makes
> Plan mode lets Claude research and propose without making changes. You review the plan, then switch modes to implement. `bypassPermissions` does the opposite, removing prompts, and `/clear` and hooks don't provide read-only planning.

@@ C2 | CLAUDE.md hierarchy
A team's root `CLAUDE.md` has grown long. They want to keep detailed API conventions in `docs/api-conventions.md` while still having Claude Code load them as memory. What feature supports this?
+ An `@docs/api-conventions.md` import line in `CLAUDE.md`
- Symbolic links named `CLAUDE.md` in every folder
- A `memory_files` key in `.claude/settings.json` that lists extra files to load as memory at startup
- A `CLAUDE_MD` environment variable
> CLAUDE.md supports `@path` imports to pull in other files. (For conventions that only matter for certain paths, `.claude/rules/` files with `paths:` frontmatter load only when relevant.) The other mechanisms aren't how memory is composed.

@@ E1 | Evaluation and debugging
A team will migrate from one Claude model to its successor next month. What must exist *before* they switch production traffic?
+ A frozen regression or eval set with success criteria, baseline results on the current model, and a rollback plan
- A new eval set written after the switch
- A manual spot check of five prompts
- Nothing, if public benchmarks look better
> Comparing old and new on the *same* frozen set against agreed criteria is what makes a migration decision objective. Public benchmarks don't reflect your task, a set written after the switch breaks comparability, and five spot checks aren't statistically meaningful.
