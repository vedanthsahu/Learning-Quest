@@ A7 | Claude API mechanics

@@ S4 | Identity, secrets, and key management

@@ C1 | Session management
A developer wants to run Claude Code from a shell script that generates a changelog summary on each release, with no interactive session. Which invocation fits?
+ `claude -p "<prompt>"` (headless mode)
- `claude --continue`, which resumes the most recent session and runs the prompt there
- `/compact` inside a running session, followed by the changelog prompt
- `claude --resume`, choosing the release session from the list
> `-p` runs Claude Code non-interactively and prints the result, which suits scripts and CI. `--continue` and `--resume` restore interactive sessions, and `/compact` is an in-session command.

@@ C2 | CLAUDE.md hierarchy
A project's `CLAUDE.md` has grown to about 2,000 lines, including several long procedures, and Claude seems to follow its key conventions less reliably. What is the best remedy?
+ Keep it concise; move long procedures into skills and path-specific guidance into `.claude/rules/`
- Make the file longer, with more emphasis on the key conventions so they stand out from the procedures around them
- Delete `CLAUDE.md` and rely on prompts in each session
- Convert `CLAUDE.md` into hooks
> CLAUDE.md loads every session, and it's advisory context. Bloat dilutes the important instructions and wastes context. Procedures belong in on-demand skills, and path-specific guidance in scoped rules. Hooks are for enforcement, not knowledge.

@@ E1 | Error classification and isolation
Trace analysis shows an agent consistently calling `get_invoice` with a customer ID where an invoice ID is required, then answering from the empty result. How should this failure be classified, and what is the first fix?
+ A tool failure: clarify tool and parameter descriptions, validate inputs, return actionable errors, re-run evals
- A reasoning failure; raise effort to maximum so the agent thinks harder about which kind of ID to pass in each call
- A platform failure; add retries with backoff
- A format failure; switch to structured outputs
> Wrong arguments to the right tool is a tool-contract problem. Better descriptions, `strict` schemas, validation and clear errors address it. Classifying failures correctly points to the fix. Effort, retries and output format don't fix an ambiguous parameter.
