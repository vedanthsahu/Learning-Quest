## 38. Object Storage as a Service

### 38.1 The Concept

Files — product images, user avatars, uploaded media — don't belong in a
relational database. This platform stores them in S3-compatible object
storage instead, and `media-service` is the one service that talks to it
directly. Part III §12.3 already read `S3ObjectStorageService` in full for
its constructor-injection style; this chapter revisits two specific
capabilities in that same file worth understanding on their own:
self-healing bucket creation, and presigned URLs.

### 38.2 Ensuring a Bucket Exists Without Being Told To

```java
@Override
public void ensureBucketExists(String bucket) {
    try {
        s3Client.headBucket(b -> b.bucket(bucket));
    } catch (NoSuchBucketException e) {
        createBucket(bucket);
    } catch (S3Exception e) {
        // RustFS / S3 return 404 (sometimes wrapped) when the bucket is missing.
        if (e.statusCode() == 404) {
            createBucket(bucket);
        } else {
            throw new StorageException("Failed to check bucket: " + bucket, e);
        }
    }
}
```

**Source:** `common-lib/common-storage/src/main/java/com/ecommerce/commonlib/storage/S3ObjectStorageService.java` (Part III §12.3)

`headBucket` is a lightweight existence check — it doesn't fetch anything,
just asks "does this bucket exist?" The **two separate `catch` blocks**
handling essentially the same underlying condition (a missing bucket) is
worth pausing on: the code comment explains why — `RustFS` (an S3-compatible
storage backend this platform can run against instead of real AWS) doesn't
always signal "bucket missing" through the same specific exception type real
AWS S3 does; sometimes it's a generic `S3Exception` with a 404 status instead
of the more specific `NoSuchBucketException`. Handling both is a real,
learned accommodation for working against more than one S3-compatible
implementation, not redundant code.

### 38.3 Presigned URLs

```java
@Override
public URL presignedGetUrl(String key, Duration ttl) {
    GetObjectRequest get = GetObjectRequest.builder().bucket(defaultBucket()).key(key).build();
    GetObjectPresignRequest presign = GetObjectPresignRequest.builder()
            .signatureDuration(ttlOrDefault(ttl))
            .getObjectRequest(get)
            .build();
    return presigner.presignGetObject(presign).url();
}

@Override
public URL presignedPutUrl(String key, String contentType, Duration ttl) {
    PutObjectRequest put = PutObjectRequest.builder()
            .bucket(defaultBucket())
            .key(key)
            .contentType(contentType)
            .build();
    PutObjectPresignRequest presign = PutObjectPresignRequest.builder()
            .signatureDuration(ttlOrDefault(ttl))
            .putObjectRequest(put)
            .build();
    return presigner.presignPutObject(presign).url();
}

private Duration ttlOrDefault(Duration ttl) {
    return ttl != null ? ttl : properties.getPresignDuration();
}
```

**Source:** `common-lib/common-storage/src/main/java/com/ecommerce/commonlib/storage/S3ObjectStorageService.java` (Part III §12.3)

A **presigned URL** is a time-limited, cryptographically signed URL that
grants temporary permission to read (`presignedGetUrl`) or write
(`presignedPutUrl`) one specific object — without the requester ever needing
real S3 credentials of their own. This is the mechanism that lets a browser
upload a file *directly* to object storage: `media-service` generates a
presigned PUT URL and hands it to the frontend, the frontend uploads the raw
file bytes straight to storage using that URL, and the actual file content
never has to pass through `media-service`'s own server at all — only the
small JSON response containing the URL does. `ttlOrDefault(ttl)` lets a
caller override the expiry per-call, or fall back to `StorageProperties`'s
own configured default (the same `@ConfigurationProperties` pattern from
Part I §1.2) if `null` is passed.

### 38.4 Try It

If a presigned PUT URL generated by `presignedPutUrl` were accidentally
logged somewhere (say, in an access log that captures full request URLs) and
that log leaked, how much of a security problem would that actually be —
total access to the whole bucket forever, or something narrower and
time-bound? Base your answer on exactly what `presignedPutUrl`'s three
parameters (`key`, `contentType`, `ttl`) scope the resulting URL to.
