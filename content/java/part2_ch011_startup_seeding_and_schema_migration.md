## 11. Startup Seeding & Schema Migration

### 11.1 The Concept

Two related but distinct problems: **"run this code once, right after the
application starts"** (seeding demo data, warming a cache), and **"apply
database schema changes in a controlled, repeatable, ordered way"** (adding a
column, creating a table) — the Java/database equivalent of Django migrations
or Alembic in the Python world. Spring Boot has a purpose-built answer to the
first (`CommandLineRunner`); this codebase uses a dedicated library, Liquibase,
for the second, rather than letting Hibernate auto-generate schema changes.

### 11.2 In This Codebase: Running Code at Startup

```java
package com.ecommerce.inventoryservice.util;

import com.ecommerce.inventoryservice.model.Inventory;
import com.ecommerce.inventoryservice.repository.InventoryRepository;
import lombok.RequiredArgsConstructor;
import org.springframework.boot.CommandLineRunner;
import org.springframework.stereotype.Component;

@Component
@RequiredArgsConstructor
public class DataLoader implements CommandLineRunner {

    private final InventoryRepository inventoryRepository;

    @Override
    public void run(String... args) throws Exception {
        Inventory inventory = new Inventory();
        inventory.setProductName("Iphone 13");
        inventory.setQuantity(12);

        Inventory inventory1 = new Inventory();
        inventory1.setProductName("Macbook Pro 13.3");
        inventory1.setQuantity(4);

        inventoryRepository.save(inventory);
        inventoryRepository.save(inventory1);
    }

}
```

**Source:** `inventory-service/src/main/java/com/ecommerce/inventoryservice/util/DataLoader.java`

`CommandLineRunner` is a Spring Boot interface with exactly one method,
`run(String... args)`. Any bean that implements it (this class is a
`@Component`, so Spring's component scan — Part II §7.2 — picks it up
automatically) has that method called once, automatically, right after the
application context finishes starting and right before it starts accepting
real traffic. Nothing calls `run(...)` explicitly anywhere in this codebase —
implementing the interface is the entire registration mechanism. This
particular one seeds two hardcoded inventory rows every time the service
starts, which is exactly the kind of thing you'd want gated behind an
environment check in a real production service (it isn't, here — worth
noticing as a rough edge, not a pattern to copy uncritically).

### 11.3 In This Codebase: Migrating the Schema

`auth-service` never lets Hibernate create or modify tables — recall Part II
§8.2's `ddl-auto: validate`. Instead, every schema change is an explicit,
version-controlled Liquibase changeset. The master file is a one-line pointer:

```yaml
databaseChangeLog:
  - includeAll:
      path: ddl
      relativeToChangelogFile: true
```

**Source:** `auth-service/src/main/resources/db/changelog/db.changelog-master.yaml`

`includeAll` tells Liquibase to load every changelog file inside the `ddl/`
folder, in filename order — which is why they're named `db.changelog-v1.0.0.sql`,
`db.changelog-v1.1.0.sql`, and so on, sequential and never renumbered.
The first real one creates the schema this whole book has been reading from:

```sql
--liquibase formatted sql

--changeset system:auth-service-v1.0.0-create-auth-tables validCheckSum:ANY
CREATE TABLE IF NOT EXISTS roles
(
    id        BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    role_name VARCHAR(60) NOT NULL UNIQUE
);

CREATE TABLE IF NOT EXISTS users
(
    user_id          BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    full_name        VARCHAR(100),
    user_name        VARCHAR(100) NOT NULL UNIQUE,
    email            VARCHAR(50)  NOT NULL UNIQUE,
    gender           VARCHAR(255) NOT NULL,
    phone_number     VARCHAR(11) UNIQUE,
    image_url        TEXT,
    keycloak_user_id VARCHAR(64)
);

CREATE UNIQUE INDEX IF NOT EXISTS uk_users_keycloak_user_id ON users (keycloak_user_id);

CREATE TABLE IF NOT EXISTS user_role
(
    user_id BIGINT NOT NULL,
    role_id BIGINT NOT NULL,
    CONSTRAINT pk_user_role PRIMARY KEY (user_id, role_id),
    CONSTRAINT fk_user_role_user FOREIGN KEY (user_id) REFERENCES users (user_id),
    CONSTRAINT fk_user_role_role FOREIGN KEY (role_id) REFERENCES roles (id)
);

INSERT INTO roles (id, role_name) VALUES (1, 'USER') ON CONFLICT (id) DO NOTHING;
INSERT INTO roles (id, role_name) VALUES (2, 'PM') ON CONFLICT (id) DO NOTHING;
INSERT INTO roles (id, role_name) VALUES (3, 'ADMIN') ON CONFLICT (id) DO NOTHING;
```

**Source:** `auth-service/src/main/resources/db/changelog/ddl/db.changelog-v1.0.0.sql`

`--liquibase formatted sql` at the top tells Liquibase to parse this as plain
SQL annotated with special comments, rather than requiring the more verbose
XML or YAML changeset format. `--changeset system:auth-service-v1.0.0-create-auth-tables`
is the unique ID Liquibase tracks in its own bookkeeping table
(`DATABASECHANGELOG`, created automatically in your database) — once this
exact changeset has run successfully against a given database, Liquibase
never runs it again, even across restarts, which is precisely what makes this
safe to apply automatically every time the service starts (`spring.liquibase.enabled: true`
from Part II §8.2) rather than being a manual, error-prone step a human runs
by hand. `ON CONFLICT (id) DO NOTHING` on the seed `INSERT` statements is a
second, independent layer of the same idea at the SQL level — safe to
re-attempt without erroring, even outside Liquibase's own tracking.

Directly compare this to `roles.id` here (`1`, `2`, `3` for `USER`, `PM`,
`ADMIN`) against `RoleName` from Part I §3.2 — the enum names and the seeded
row order are not a coincidence; they're the same three roles represented
twice, once as a Java-side type-safe enum, once as real seeded database rows.

### 11.4 Try It

If `DataLoader.run(...)` (§11.2) were changed to also throw a `BusinessException`
partway through (Part I §5) if the inventory table already contained more than
100 rows, would that exception happening stop the Spring Boot application from
starting entirely, or would the application still come up with just those two
inventory rows missing? Reason from what `CommandLineRunner` actually is —
a bean method Spring calls once during startup, not a background job running
independently of it.
